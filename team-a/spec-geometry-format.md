## 1. Overview and headline results

The engine's `c`/`g` (CPU-side / GPU-side) paired-file naming convention, first documented for `.cpeg_pc`/`.gpeg_pc` (`spec-texture-format.md`), turns out to be used far more broadly than just textures — but that convention alone doesn't mean each pairing is a *distinct format*. This pass's main value is sorting out which of the three assigned names are real, separate formats and which aren't:

| Format | Verdict |
|---|---|
| `.cvbm_pc`/`.gvbm_pc` | **Not a new format.** Confirmed, byte-for-byte, to be the exact same `.cpeg_pc`/`.gpeg_pc` texture-pair format (§2). Fully documented already; this section is a pointer, not a new spec. |
| `.ccmesh_pc`/`.gcmesh_pc` | **A genuinely new, only partially-resolved format.** The one real geometry format in this batch. `.ccmesh_pc` embeds a reused "material reference block" (the same structure found in `.matlib_pc`) followed by mesh-specific data; `.gcmesh_pc` holds what looks like an index buffer followed by unresolved vertex-attribute data (§3–§4). **[Superseded, desk review 2026-09-30: the index buffer starts at `.gcmesh_pc` `0x10` and is sized count × 2 (§4.1.2 item 10); the vertex-attribute channels that follow are resolved in `spec-vertex-format.md`.]** |
| `.cvtf_pc` | **Not geometry at all — reclassified.** Originally guessed (in `spec-vehicle-data.md` §1) to be a damage/collision index format, purely from its binary/index-table appearance. Direct string inspection this pass shows it's actually a **compiled, binary vehicle-customization component/color definition file** — the very thing `spec-customization-data.md` §3/§4 flagged as a missing, not-found `_cust.xtbl` reference (§5). This is a real correction to both of those documents, applied below. |
| `.clmesh_pc`/`.glmesh_pc` (added later, found via the world-streaming pass) | **A second, genuinely new static-prop mesh-pair format, structurally analogous to `.ccmesh_pc`/`.gcmesh_pc` but not proven identical** (§4.2). Same shape of open item: the CPU side's material block is confirmed, the GPU side's likely index buffer is confirmed by pattern, and the actual vertex-attribute layout is unresolved. **[Superseded, desk review 2026-09-30: `.clmesh_pc` embeds the shared Mesh sub-block and its vertex data is confirmed (12,628 blocks, `spec-vertex-format.md` §4.2; this spec §6 item 6).]** |

**Review status (2026-09-30): DESK-PASS, text fixes applied (front-matter method/clean-room claims corrected; two stale §1 rows marked superseded) — desk review (not re-derived from the executable).**

## 3. `.ccmesh_pc` — structure

Worked example: `cm_hand_f_leather.ccmesh_pc` (1,610 bytes), one of the mesh/texture/morph files found inside a per-item customization bundle (`spec-customization-data.md` §2.3), extracted as entry 0 of its mode-(b) nested `str2_pc` — fully reliable.

### 3.1 Embedded material reference block (offset `0x00`–end of its name table)

The file **begins with the exact same header/name-table structure already documented as `.matlib_pc`** (`spec-texture-format.md`, Appendix, as corrected this pass): the constant leading value `0x00043854`, a field giving the exact byte length of the name table that follows, a zero field, a texture-slot count, 16 bytes of zero padding, then that many null-terminated texture names. **[CONFIRMED — empirical, exact field-for-field match, including the corrected name-table-length field.]** In this sample: 5 names — `pat_primaryonly.tga`, `cm_hand_f_leather01_n.tga`, `leather_02_sb.tga`, `cm_hand_f_leather01_d.tga`, `missing-alpha.tga` (normal/diffuse/specular-style texture slots for this glove mesh, plus a pattern mask and a "missing" placeholder).

**This means `.matlib_pc`'s header/name-table structure is not specific to standalone `.matlib_pc` files — it's a general-purpose "material reference block" the engine embeds inline wherever something (a standalone material, or here, a mesh) needs to declare its texture references.** Recommend reading this section's structure as belonging to that shared block type, not as two coincidentally-similar formats.

**Further confirmed by a later pass (`spec-mission-packages.md`): the identical block also opens `.cefct_pc` particle/cinematic-effect files** — a real sample (`vfx_shockwave_kill_all.cefct_pc`, from a mission-package archive) starts with the same constant, the same name-table-length field, and a texture-slot count (3, in that sample: `vfx_corona_white.tga`, `vfx_smoke_anim_v01.tga`, `vfx_shockwave_01.tga` — a corona/smoke/shockwave sprite set, consistent with a particle effect's own texture needs). This is now a 3-for-3 confirmation (`.matlib_pc`, `.ccmesh_pc`, `.cefct_pc`) that this header is a truly general-purpose, format-agnostic texture-reference block, not tied to any one file type.

**Field offsets, stated explicitly (desk review 2026-09-30; the order above already fixes them, and §4.1.3's `material_block_end = 0x20 + u32(file + 0x04)` relies on them):** `+0x00` `u32` magic `0x00043854`; `+0x04` `u32` name-table byte length (sum of name lengths incl. NULs); `+0x08` `u32` zero; `+0x0C` `u32` slot count; `+0x10`–`+0x1F` zero; names from `+0x20`. **Validated by data:** Team B's material-block parser checks the magic, the `+0x04` length against the names actually read, the slot count and the `+0x20` name start on 1,803/1,803 `.ccmesh_pc`/`.csmesh_pc` files (`team-b/HANDOFF.md` §4.2) and again on 100,384/100,384 `.clmesh_pc` files. **[OPEN — desk review 2026-09-30: the "zero" fields at `+0x08` and `+0x10`–`+0x1F` are not read by any population check; to be settled against real data.]**

**Review status (2026-09-30): VALIDATED-BY-DATA: magic, name-table length, slot count and name start 1,803/1,803 (Team B) + 100,384/100,384 `.clmesh_pc`; offset list added — desk review (not re-derived from the executable).**

### 3.2 Footer (after the material block)

Real, structured, but only partially resolved:

- **A second copy of the same 5 texture names, in mixed/proper case** (e.g. `PAT_primaryOnly.tga`, `CM_Hand_F_Leather01_n.tga` vs. the all-lowercase first copy). **[CONFIRMED — empirical.]** Plausibly a display/tool-facing name list stored alongside the lowercase, case-folded names actually used for runtime lookup (consistent with the case-insensitive filename hash already documented in `spec-vpp-container.md` §2.2 — case doesn't matter for lookup, so both a "pretty" and a normalized copy being kept independently is a very plausible engine convention, though not directly proven).
- **A monotonic ascending `u32` array, `0, 1, 2, ... 0x43` (68 entries)**, immediately after the second name list. **[CONFIRMED present — HYPOTHESIS as to meaning.]** **[Superseded: this is the length-prefixed blob and array 4 of the six-array walk, §4.1.2 items 2–3; "immediately after" means after the next 16-byte alignment.]** Plausibly a bone/joint index table, a vertex-group-to-material mapping, or a wedge/attribute remap array — all standard things a skinned character mesh needs, but not distinguishable from this data alone.
- **A region of packed floating-point and integer values** further into the footer, including a repeated `1.0f` (`0x3F800000`) pattern consistent with a default white RGBA color, similar to values seen in the `.matlib_pc` footer. **Not decoded.**

**None of §3.2 was resolved to an exact field layout this pass** — flagged honestly rather than guessed at; this would benefit from disassembly (the mesh-loading code path), similar to how the container format's harder questions needed Ghidra rather than black-box inspection alone.

## 4. `.gcmesh_pc` — structure

Worked example: `cm_hand_f_leather.gcmesh_pc` (70,692 bytes), paired with the `.ccmesh_pc` sample above. Unlike `.gpeg_pc` (which has *no* header at all — pure concatenated pixel data), `.gcmesh_pc` has real structure at its start:

- **A 16-byte header:** a leading 4-byte value that is **confirmed to also appear verbatim inside the paired `.ccmesh_pc`'s footer** (§3.2) — strong evidence this is a **cross-reference/consistency value tying a specific `.gcmesh_pc` to its exact matching `.ccmesh_pc`** (plausibly a content hash or version stamp), not proven to be either specifically. Followed by 12 bytes read as zero in this sample. **[CONFIRMED — empirical, the cross-file value match; HYPOTHESIS — its purpose.]** **[Superseded location: the matching field is the Mesh sub-block's check value (version field `+0x04`), §4.1.2 items 5 and 7, and `g[0:4]` equals it on 1,937/1,937 pairs (`spec-vertex-format.md` §4.1).]** **[OPEN — desk review 2026-09-30: the 12 zero bytes (`g` `+0x04`–`+0x0F`) are one-sample observations, not population-checked; to be settled against real data.]**
- **What is very likely an index buffer immediately after the header:** starting at offset `0x10`, a long run of small, smoothly-increasing 16-bit values (consistent with a **triangle-list vertex-index buffer** — the value range climbs steadily from single digits up into the 500–800s across roughly the first ~4,000 sixteen-bit values, i.e. **roughly the first ~8,000 bytes**, before the value distribution changes character). **[HIGH CONFIDENCE — inferred from the value-range shape; exact boundary and interpretation (triangle list vs. strip, any additional sub-header) not nailed down.]** **[Superseded, desk review 2026-09-30: the "~4,000 values / ~8,000 bytes" boundary heuristic is replaced by the exact extent `0x10` + index count × 2 from the Mesh sub-block (§4.1.2 item 10; e.g. 3,976 × 2 = 7,952 bytes, ending at `0x1F20`).]**
- **The remainder of the file** — see §4.2, resolved in a follow-up Ghidra pass. *(Desk review 2026-09-30: for `.gcmesh_pc` the resolving text is §4.1–§4.1.2 (item 10) and `spec-vertex-format.md` §4; §4.2 covers the separate `.clmesh_pc`/`.glmesh_pc` format.)*

### 4.1 `.ccmesh_pc`/`.glmesh_pc`/`.gzn_pc` payload structure — resolved via disassembly, one shared mechanism confirmed

**Correction from the clean team, verified byte-for-byte against the real `cm_hand_f_leather` sample: the six-array/"Mesh"-sub-block structure documented in this section lives entirely inside `.ccmesh_pc` (the small CPU-side file), not `.gcmesh_pc` (the large GPU-side one) — the reverse of what this section originally assumed from the address trace alone.** `.gcmesh_pc` is presumably bulk payload data that fields inside this `.ccmesh_pc` structure point into or reference (mirroring the already-confirmed `.cpeg_pc`/`.gpeg_pc` split, where the small `c`-file holds metadata/offsets and the large `g`-file holds raw payload bytes) — not independently confirmed this pass, but the natural reading given the established `c`/`g` convention everywhere else in this project. Every field, offset, and array described below should be read as **within `.ccmesh_pc`**, not `.gcmesh_pc` — the section heading and body below are corrected accordingly, but any earlier notes elsewhere in this project referring to this structure as `.gcmesh_pc`'s payload are superseded by this correction.

**Also from the clean team's real-sample test:** on the actual `cm_hand_f_leather` mesh, **5 of the 6 arrays are empty (zero count) — only array 4 (the small, 4-byte-stride table) is populated.** The count×stride arithmetic proposed for the vertex buffer (array in the nested "Mesh" sub-block, §4.1.1) **did not land cleanly on this sample. This is inconclusive, not a negative result** — a small, simple mesh like a glove may legitimately not exercise most of these fields (e.g. no separate skinning/render-batch data if the mesh doesn't need it), so this doesn't rule out the count×stride reading, it just means this particular sample can't confirm it either. **A bigger, richer mesh sample (more bones, more render batches) is needed to actually test the arithmetic — flagged as the concrete next step, not "resolved."**

A dedicated Ghidra pass (motivated directly by all three formats independently showing the same "16-byte header, then an index-buffer-shaped run of `u16`s" black-box signature — `spec-terrain-format.md` §4) traced the actual loader code, starting from the resource-type registration table (§4.3) and following its constructor pointers for the `.ccmesh_pc`/`.gcmesh_pc` and `.csmesh_pc`/`.gsmesh_pc` types (both use the identical constructor/destructor pair, confirming they're the same underlying format under two different extension names for two different asset categories — character meshes and static props respectively). **This resolves the open item — the black-box guess was correct in shape, and the exact mechanism is now known (modulo the `.ccmesh_pc`-vs-`.gcmesh_pc` correction above):**

### 4.1.1 Following the trail one more level: a nested, literally-named "Mesh" sub-block with real vertex-count/stride fields

A follow-up pass traced `FUN_00e718b0` (flagged above as the next lead) two levels deeper, and it paid off. `FUN_00e718b0` is a thin, **generic, format-agnostic wrapper** (called from 8 unrelated places elsewhere in the binary, not mesh-specific) that resolves an embedded reference and, on success, hands the result to a renderer/resource-manager singleton via a virtual call through vtable slot `+0x10` — consistent with "hand this parsed data off to the graphics device." Its real work happens one level in, in a function this pass calls the **"Mesh" sub-parser** based on its own internal error message — a version-mismatch message that names the structure "Mesh" and reports the found version against a current and a least-compatible version *(paraphrased 2026-09-30, desk review; the verbatim engine string previously quoted here is not reproduced)* — raised when a version field here doesn't equal exactly **`9`**. **[CONFIRMED — disassembly, the error message's existence and the version check — this is a real, internally-named engine concept, not a name this project invented.]** *(Layout pointer, desk review 2026-09-30: the version field is followed by the check value, `c`-length and `g`-length, then the `0x70`-byte header padded to 8, whose `+0x00` is the flags byte; offsets in the bullets below are from that header — `spec-vertex-format.md` §2.)* This is a **second, independent sub-header nested inside the payload region already described above** — it has its own version tag, distinct from the outer `0x424BD00D` block's own version field.

This "Mesh" sub-block's own fields are, at this point, the strongest concrete lead yet for the actual vertex format:

- **`+0x10`**: a count of **24-byte "channel" records** (pointer at `+0x18`), each read once through a small per-record validation call, then re-walked to compute a per-record byte size as **`record_count × (byte_at_record+0x04 + byte_at_record+0x07)`** *(corrected 2026-09-11 from `+1` — see `spec-vertex-format.md` §3; the decompiler expression indexes an `int`-typed pointer, so the printed index advances four bytes, not one)* — i.e., each 24-byte record describes one **data channel/stream**, with two separate single-byte "component size" fields summed together and multiplied by a per-record element count. This is a very natural shape for **"one stream, made of two interleaved component types"** (e.g. a position channel plus a separate weight/index channel within one stream) — **[CONFIRMED — disassembly, exact arithmetic; HIGH CONFIDENCE inferred for the "stream descriptor" interpretation.]**
- **`+0x20` / `+0x30`**: a count field (`+0x20`, full `u32`) and a **single-byte stride field** (`+0x30`) whose product (`count × stride`) sizes the array stored at `+0x28`. **⚠ Corrected 2026-09-11: this is the *index* buffer, not the vertex buffer.** This bullet originally called it "exactly the shape of 'vertex count × per-vertex byte stride', the single strongest candidate found this pass for the actual interleaved vertex buffer" — that reading was wrong. The stride field reads **`2` in every shipped block across all six carrier formats (17,934 blocks)**, which no vertex buffer can be, and every value in the buffer indexes a real vertex (`spec-vertex-format.md` §8). **The actual vertex data is the per-channel arrays described in the bullet above, which follow this buffer in the `g`-file.** **[CONFIRMED — empirical: the index-buffer reading. The stride field reads `2` in 17,934 of 17,934 shipped Mesh sub-blocks across all six carrier formats, and every value in the buffer indexes a real vertex (`spec-vertex-format.md` §8).]** ⚠ *2026-09-13: the 17,934 population figure is now a known under-count (`spec-vertex-format.md` §4.2's own note, `spec-zone-data-format.md` §10.5–§10.7) — the true zone/level-mesh block count is substantially larger. This makes the invariant stronger, not weaker: re-measured over the corrected 38,152-block zone population alone, the stride byte still reads exactly `2` in all 38,152, zero exceptions.*

### 4.1.2 The count×stride hypothesis, resolved: a richer sample, an exact offset formula, and where the vertex data actually lives

This pass also went one level deeper into the disassembly than before: it decompiled `FUN_007524f0`'s actual caller (`FUN_007527b0`, not previously examined) and the two helper functions `FUN_00e71310`/`FUN_00e71740` referenced from the "Mesh" sub-block parser. This closed several gaps the earlier pass had left as candidate-shaped guesses:

**1. The fixed sub-header is exactly `0x88` (136) bytes — confirmed directly, not inferred.** `FUN_007527b0` (the real caller of `FUN_007524f0`) sets the parse cursor to `sub-header-start + 0x88` immediately before handing off. **[CONFIRMED — disassembly, exact literal offset from the calling function itself.]** This gives a complete, reusable, disassembly-derived formula for locating the start of the variable-length array-data region in any `.ccmesh_pc`/`.csmesh_pc` file: `array_region_start = (padded material-block end) + 0x88`, where "padded" uses the **mandatory-advance** rule in §3.1.1 below — **not** a plain round-up-to-16.

#### 3.1.1 The material block's trailing pad is *mandatory*, not conditional — correction

**An earlier version of this document described the gap between the material block and the `0x424BD00D` sub-header as "a 16-byte alignment pad", which a reader naturally implements as round-up-to-16. That is wrong, and it fails on real files.** The correct rule, contributed by the clean team from a full-archive validation sweep and independently re-verified here:

> The material block is **always** followed by 1–16 bytes of padding. When its end offset is *already* on a 16-byte boundary, a **full extra 16 bytes** of padding still follow.

In one formula: `sub_header_off = material_block_end + (16 - (material_block_end mod 16))` — which always advances by at least 1 and at most 16, and coincides with round-up-to-16 in every case *except* the already-aligned one. **[CONFIRMED — empirical, on a real sample whose material block ends exactly at `0x20`: round-up-to-16 lands on `0x20` and reads four zero bytes; the mandatory rule lands on `0x30` and reads `0x424BD00D` exactly.]** *(Desk review 2026-09-30: a block ending at `0x20` is header-only, i.e. a zero-texture mesh; the file is not named in the source record.)* **[OPEN — desk review 2026-09-30: (a) whether the alignment is of the cursor's offset from the buffer start or of an absolute address (PC primary buffers are only guaranteed 8-aligned, `spec-resource-dispatch.md` §8.4), and (b) whether the mandatory pad is applied to the raw material-block end or to the cursor after the round-up-to-4 step that precedes `FUN_007527b0` (§8; the two differ when the end is ≡ 13–15 mod 16). Team B's 105/1,803 files needing +16 fits (a) offset-based / (b) raw-end, but its reader searches rather than computes, so this is inference — to be settled against the executable (`FUN_007527b0`) / a per-file `material_end mod 16` histogram.]**

**Why this went unnoticed for so long, and why it matters:** the already-aligned case is rare and *silently* wrong rather than loudly wrong — it lands inside the pad, reads zeros, and looks exactly like "this file has no geometry block." Every sample used to derive the structure in this document happened to have a non-aligned material-block end, so none of them exercised it. Applying the corrected rule takes a full-archive test of `characters.vpp_pc` from **528/549 to 549/549**, and the clean team reports **1803/1803 across two independent archives** with this plus two other fixes. **[CONFIRMED — empirical, both teams independently.]**

**This supersedes an incorrect finding previously recorded by this team.** The 21 files that failed under the old rule were written up as "tiny degenerate meshes with zero material-block textures, likely placeholder/censor-bar meshes whose geometry payload is simply absent." **That explanation was wrong.** They are ordinary meshes — most carry 6–9 real texture references, and only 3 of the 21 have zero textures — and they parse completely once the mandatory pad is accounted for. The zero bytes that prompted the "empty payload" reading were the pad itself. Recorded here rather than quietly deleted, because the failure mode is instructive: *a wrong offset rule produced data that looked like a coherent alternative explanation.*

**⚠ The blob skip has a `+1` in it. Stated as code, because prose lost it and it cost the implementation team a 45% vehicle failure rate (§4.1.4):**

```
cur        = subheader + 0x88
ln         = u32(cur)                  // declared blob length
data_start = align16(cur + 4) + 1      // ONE BYTE past the 16-aligned position
cur        = data_start + ln           // ln counts from data_start
                                       // <-- AND NOTHING ELSE. No rounding here.
```

**Cross-check against Team B's reader (desk review 2026-09-30).** Team B does not compute `align16(cur + 4) + 1`; it uses a constant `blobDataStart = subheader + 0x88 + 4 + 5` = `subheader + 0x91` (`team-b/src/geometry_block.cpp` line 179, `kBlobAContentPad = 5` in `team-b/include/sr3geometry/geometry_block.h`; `team-b/HANDOFF.md` §4.2 rule 2: "a 4-byte length at geometry-block `+0x88`, then 5 pad bytes"). **The two agree exactly when the sub-header offset is 16-aligned** (`align16(sub + 0x8C) + 1 = sub + 0x91`), which the mandatory pad above guarantees for every `.ccmesh_pc`/`.csmesh_pc`. They disagree otherwise — e.g. a sub-header ≡ 8 mod 16 gives `sub + 0x99` here versus `sub + 0x91` in Team B's reader. Vehicle sub-headers are given by a stored offset and are only stated to be 8-aligned (`spec-vehicle-geometry.md` §3, `+0x04` row); both this rule (367/367, below) and Team B's constant (372/372) pass on vehicles, which is consistent only if those sub-headers are in fact 16-aligned — not measured. **[OPEN — desk review 2026-09-30: the general case (sub-header not 16-aligned) is unsettled — to be settled against the executable (`FUN_007527b0`/`FUN_007524f0`, alignment base of the blob skip) or a per-file `subheader mod 16` check over all vehicles.]**

**The "and nothing else" is load-bearing.** Each populated array applies its own 16-byte alignment when it is visited, and the trailer aligns to 8 — so an extra round-up after the blob is *redundant when arrays are populated* (silently absorbed) and *actively wrong when they are not* (it rounds past the correct 8-aligned landing site). That redundant round-up was the actual defect behind the 45% vehicle failure rate, sitting one line below a correctly implemented `data_start`. **[CONFIRMED — empirical, clean team: removing it takes vehicles to 372/372 and also closes 9 pre-existing `items.vpp_pc` failures.]**

That extra byte is a **leading NUL**, and it is a convention this format family uses elsewhere — the shared material-set block does the same thing ("names padded to 16 **plus one byte**, leading NUL"), recorded in this project's Ghidra bookmarks under `SHARED_BLOCK`. Scored against an independent oracle for the true Mesh sub-block on 367 vehicle pairs: this rule **367 / 367**; skipping 4 and rounding up to 16 **270 / 367**; skipping 4 with no alignment **86 / 367**. **[CONFIRMED — empirical.]**

#### 4.1.4 Why vehicles expose walk bugs that meshes hide

**Every one of the 367 vehicle pairs checked has arrays 1–4 *empty*** (counts at `+0x08`, `+0x38`, `+0x3A`, `+0x0A` all zero). ### 5.2 Registered type ID 8, `Character cvtf` — traced: a structurally different parse from ID 2's, not a stash (2026-09-18)

`spec-format-inventory.md` listed ID 8's constructor, `LAB_007543f0`, as “format yes (= ID 2); this variant's constructor untraced” — an assumption that ID 8 parses the same `.cvtf_pc` structure documented above for ID 2, just via a different entry point. Decompiling `LAB_007543f0` and its one callee refutes that assumption at the raw-instruction level.

**`LAB_007543f0` itself is a 6-instruction pass-through, not a parser.** Reading raw x86 (not decompiler output, given `spec-resource-dispatch.md`'s established warning that the decompiler under-counts arguments at these constructor-call boundaries): it takes its own incoming stack argument 1 (`[ESP+4]`, the dispatcher's “name” argument, per `spec-resource-dispatch.md` §4's unpaired-type convention) and argument 3 (`[ESP+0xc]`, the primary-file buffer), pushes them in that order, and makes exactly one call — to `FUN_0074f1b0(name, buffer)` — then unconditionally returns success (`AL=1`), discarding whatever `FUN_0074f1b0` itself returned. The dispatcher's 2nd argument (the “?” field in `spec-resource-dispatch.md`'s own notation) is loaded into a register but never used. **[CONFIRMED — disassembly, both functions' entry sequences read raw.]**

**`FUN_0074f1b0` is ID-8-specific — exactly one caller in the whole binary (`LAB_007543f0` itself), no other xref anywhere.** So whatever it does, it exists purely to serve this registration; it is not some shared generic utility incidentally reached from here. **[CONFIRMED — disassembly, exhaustive xref check.]**

**And what it does is a real parse — of a structure with no resemblance to §5.1's `'ftvc'`-tagged catalog.** Three concrete divergences from ID 2's already-documented real parser (`FUN_00aaf9a0`, reached via `FUN_00ab06c0`→`FUN_00ac17b0`, §5.1):

1. **No header check at all.** `FUN_00aaf9a0` validates magic `0x63767466` (`'ftvc'`) and `section_count == 2` as its literal first two comparisons before touching anything else in the buffer. `FUN_0074f1b0`'s first instructions (raw-confirmed) do neither — they read buffer offset `+0x00` directly as a signed loop count and buffer offset `+0x08` as a pointer to fix up. A buffer that actually began with `'ftvc'` (`0x63767466`, a huge positive `int`) would send this loop count into the billions; the code plainly isn't expecting that shape. **[CONFIRMED — disassembly, both entry sequences read raw.]**
2. **A much deeper, differently-shaped nested structure**, not §5.1's flat {16-byte header} + {Region 1: 28 × 16-byte quads} + {Region 2: 40 flat wheel-name strings} + {Region 3: un-indexed trailer}. `FUN_0074f1b0` walks top-level records at a 44-byte (`0x2c`) stride, each holding several sub-arrays reached through further pointer fields — strides `0x10`, `0xc`, `0x24` and `8` bytes appear at different nesting levels, each gated by its own small per-record byte count (fields at offsets like `+0x1c` and `+0x20`/`+0x21` within the relevant record) — at least 3–4 levels of nesting in total, all still following the same “`-1` sentinel → `0`, else `+= base`” pointer-fixup idiom §5.1's own parser also happens to use (a shared engine idiom across formats, not itself evidence of a shared file format). **[CONFIRMED — disassembly, full function decompiled, 1,067-address body.]**
3. **At least one field is resolved through a name/string lookup, not a plain pointer fixup** — a top-level record field is converted through a small helper (`FUN_00be2240`→`FUN_00db0c50`) into a resolved handle rather than just rebased, and deeper fields are resolved against a shared 4-category name/handle table (`FUN_00746c90`/`FUN_00746740`, backed by globals `DAT_015535a8`/`DAT_015535b8`) with a resolve-or-create-default fallback (`FUN_00dcecc0`→`FUN_00db0c50`/`FUN_00dce690`) for another field. This is real cross-reference resolution work, the kind a genuine parser does — not the flavor of “just stash the pointer” seen in ID 11/12's morph constructors (§8 below). **[CONFIRMED — disassembly, all four helper functions read.]**

**After the fixup pass, the buffer is registered into its own small global slot table** (`&DAT_015cd3d8`, running count `DAT_015cd458`), keyed by the value at buffer offset `+0x04`: an existing slot whose stored object matches that key is overwritten, otherwise the buffer is appended (or written into the first empty slot found while scanning). This is a distinct, working registration mechanism, separate from anything `spec-resource-dispatch.md` documents generically. **[CONFIRMED — disassembly.]**

**Net verdict: neither of the two outcomes this confirmation task was framed around.** Not “the same real parse as ID 2” (no shared header check, a categorically different and deeper record shape) — and not “stash-only” in ID 11/12's sense either (`FUN_0074f1b0` does substantive pointer-fixup and name-resolution work, not a bare stash of the incoming buffer pointer). ## 8. Registered type ID 9, `Pcust mesh` — traced: stash-only, deferred into the same parser as ID 5 (2026-09-20)

`spec-format-inventory.md` listed ID 9's constructor, `LAB_009f08c0`, as "format yes (= ID 5); this variant's constructor untraced" — the same open question §5.2 answered for ID 8, and `spec-rig-format.md` §11.18.1 had already inferred an answer for (its own words: "HIGH CONFIDENCE — inferred … did not separately re-verify `LAB_009f08c0` itself"). Decompiled in full and read raw: **the inference was right, and it is now verified at the instruction level.**

**`LAB_009f08c0` is stash-only — it parses nothing.** Its whole body (72 bytes, 24 instructions, one branch) is: load the customization current-job pointer `DAT_0263e0f4`; compare the constructor's 2nd argument (the streaming container being loaded) against job`+0x10` and return false on mismatch; copy the resource name (`0x41` bytes, bounded `strncpy` + NUL) to job`+0x16`; store the four raw incoming values — primary buffer, primary length, secondary buffer, secondary length — at job`+0x58`/`+0x60`/`+0x5c`/`+0x64`; return true. The only call is the bounded string copy; **no buffer is dereferenced.** So it is neither §3/§4's real parser (`FUN_00751f60`, ID 5) nor a differently-shaped parser (§5.2's ID 8). **[CONFIRMED — disassembly, complete body read raw.]**

**The bytes are parsed later, by the same code ID 5 uses.** The customization asset assembler `FUN_009f36d0` — the one reader of these four slots — copies the stashed c-file and g-file into two allocations and then runs, on the copies, the same two-stage sequence as `FUN_00751f60`: `FUN_00dd7d70(c, &cursor, 0)` (the material-block validator, §3), the identical 12-instruction round-up-to-4 idiom on the cursor (`0x00751f8c`–`0x00751faa` in ID 5's constructor; `0x009f3a67`–`0x009f3a85` in the assembler), then `FUN_007527b0(c, &cursor, g, &out)` — the `0x424BD00D` / version `0x29`–`0x2A` outer-block check and `FUN_007524f0` payload parse of §4.1. The two call sites push the same four arguments in the same order. The only structural difference: ID 5 then registers the result by name (`FUN_005ce910(name, container, result)`), whereas the assembler keeps it in its own output object and continues with `FUN_00752fc0`. **So a `.ccmesh_pc`/`.gcmesh_pc` reaching ID 9 is byte-for-byte the format documented in §3–§4; no separate "Pcust mesh" format exists, and nothing here changes the vertex or skinning specs.** **[CONFIRMED — disassembly, both call sequences read raw.]**

**Cross-check against `spec-rig-format.md` §11.18.1.** That section reported that `FUN_009f36d0` copies raw byte ranges out of its first argument's dword slots `[0x16]/[0x18]`, `[0x17]/[0x19]`, `[0x2b]/[0x2c]`, `[0x40]/[0x42]`, `[0x41]/[0x43]` into one buffer before `FUN_007527b0`. Those are exactly the stash slots of three constructors: `[0x16]/[0x18]` and `[0x17]/[0x19]` (byte offsets `+0x58/+0x60`, `+0x5c/+0x64`) are **this** constructor's; `[0x2b]/[0x2c]` (`+0xac/+0xb0`) is ID 10 `Pcust peg`'s primary buffer/length (it is appended after the mesh's c-side bytes in the same allocation); `[0x40]/[0x42]` and `[0x41]/[0x43]` (`+0x100/+0x108`, `+0x104/+0x10c`) are ID 11 `Pcust morph`'s. §11.18.1's "the `PCC_FINALIZE` chain is the type-9 loading path" is therefore **confirmed rather than inferred**, and its hedge on `LAB_009f08c0` can be dropped. **[CONFIRMED — disassembly.]**

**Why the same format arrives late.** The constructor's gate makes it a per-job mechanism: only a mesh delivered inside the container the current customization job is waiting on is accepted; anything else fails the load. The full job-record field map, the container-type callbacks ("Cust_Component", "Cust_Logo") and the sibling stashes (peg, morph, creation morph, rig, logo peg) are in **`spec-morph-format.md` §16**, which also corrects that document's own §12.3 (its type-11/12 constructor labels were one slot early). **Open:** how an entry becomes type 9 rather than type 5 — the extensions are identical, so it must come from the container or the entry's manifest type byte; not traced (`spec-morph-format.md` §16.8 item 1). **[OPEN.]**
