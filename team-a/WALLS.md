# WALLS — dead ends and false positives, read this before starting new investigative work

**Every agent brief for new Ghidra/disassembly/data-population investigation should say "read WALLS.md first."** This file exists so later waves stop rediscovering the same dead ends earlier ones already paid for. Adopted 2026-09-28 from an external research pass (`AI-WORKFLOW-INSTRUCTIONS.md`, §4) — moved out of `HANDOFF.md` §27.4 into its own file so it survives HANDOFF's own repeated compaction passes untouched, and so a brief can point at one short file instead of a long section buried in a much longer document.

**Format per entry: the attempt, why it failed, and what evidence would reopen it.** Add a new entry every time a real investigative path is closed as a dead end — don't just delete the record once something's refuted, since the NEXT agent needs to know not to re-try it.

---

## Whole-binary predicate/census dead ends

- **Whole-binary predicates over small struct displacements have no selectivity.** Failed 4+ times independently: 469/461/23/272 hits in early vehicle work; a register-tracked two-step dereference off the vehicle Mesh-header anchor gave 51 hits in 44 functions; the draw-range record's four-field `DrawIndexedPrimitive` signature funnelled down to 384 hits in 298 functions, mostly unrelated `ESP`-based stack frames. Adding a second tracked displacement does not buy selectivity — only a named structural anchor does. **Reopen if:** you have a genuinely unique, ≥3-field combined signature with a shuffled/negative control already run and passing.
- **Instruction-form censuses without a whole-binary control on the exact compiler form silently undercount.** The `0x14`/`0x30` stride predicates (`IMUL`/`LEA`/`ADD` with the literal) missed MSVC's `LEA r,[r+r*4]`·`SHL 2` and `LEA r,[r+r*2]`·`SHL 4` forms — 1,547 and 3,015 sites binary-wide, respectively. The vehicle `high16` consumer was found ONLY after repairing this; before the repair the search returned a clean-looking zero (see the note on that specific case below). Same failure mode later caused the D3D9 vtable census correction (`CALL [reg+disp]` misses the compiler's actual `MOV reg,[reg+disp]` + `CALL reg` idiom — see below). **Reopen if:** you've enumerated every compiler-emitted form for the operation, not just the most obvious one, and controlled the count against a known-present positive case.
- **Coincidental vtable-slot offset matches are a real, repeated failure mode — an offset number matching a public API's slot position is NOT evidence the call is that API**, unless the calling convention (argument count, stack cleanup) also matches and the base object's class is independently resolved (RTTI, or tracing where the pointer originates). Confirmed false positive: `DAT_0351f8f8`'s vtable offsets `0x98`/`0xAC` coincidentally matched `GetRenderTarget`/`Clear`'s D3D9 slots; the real tell was that `+0x28` was called with 0 arguments where the real device method needs 1 — a calling-convention mismatch caught only by checking, not assuming (`spec-render-pipeline.md` §16.1, §18.10). Also refuted the same way: a `SetRenderTarget`-shaped call at `0x00e70380` (§12's own "unverified offset hits" list) — 0 arguments passed where the public method needs 2. **All eleven of §12's remaining candidate sites, resolved 2026-09-29 (`spec-render-pipeline.md` §12.1): all REFUTED, ten by argument-count mismatch alone (0, 1, 3 or 5 explicit arguments where the real method needs 2) and two of those ten ALSO by base-object identity — `FUN_00d0c890`/`FUN_00d0e6c0`'s vtable-`0x94` slot is not a C++/COM vtable at all but an OpenSSL bignum/`EC_METHOD`-style sparse, explicitly NULL-checked callback table (one of the two cites the literal source path `.\crypto\ec\ecp_simple.c` in its own decompiled body); a real device vtable is never null-checked before use, and its slot `0x94` coincidentally matches `SetRenderTarget`'s offset by pure chance — a fresh confirmed instance of this exact failure mode.** **Reopen if:** you've confirmed the calling convention AND resolved the base object's class (RTTI or a traced constructor), not just the numeric offset. **Fourth confirmed instance, 2026-09-29:** `spec-render-pipeline.md` §8's own whole-binary `CreateVertexDeclaration`-offset (`+0x158`) census found two sites beyond the one already-confirmed real caller, left as "OPEN, plausible... not confirmed"; chasing them as a candidate tree/zone-specific declaration path (`spec-vertex-format.md` §12.10.4) found both take **zero explicit arguments** where the public method needs two, and the containing `0xf3xxxx` address region is Wwise audio middleware (a directly adjacent sibling calls the literal `AK::MemoryMgr::Malloc` API symbol under a critical section; three more siblings share a device/capability-negotiation body template) — not a renderer at all. **Do not re-chase `FUN_00f3a6d0` or the call site at `0x00f3bcf6` as a second vertex-declaration path; both are REFUTED** (`spec-render-pipeline.md` §8, corrected in place).
- **Same failure mode, a fifth confirmed instance: `spec-zone-data-format.md` §9.2's own exhaustive whole-binary census for a `.czn_pc` top-level `{tag,length}` walker required co-occurrence of the literal `0x80000000` plus an `AND`-mask by `0xFFFFFFF8` or `0xFFFF0000` — a clean, principled predicate that nonetheless missed the real compiled walker entirely.** The real function (`FUN_00864c60`/`FUN_007512f0`, found 2026-09-30 from the render side, not from re-running the census) uses `& 0x80000003` (not the bare `0x80000000` literal), a branching `(x-1|0xfffffffc)+1` round-up idiom (not an `AND`-mask instruction at all) for its alignment step, and `& 0x7fffffff` (not `0xFFFFFFF8`/`0xFFFF0000`) to strip/test the tag's high bit. The census was exhaustive over the instructions it looked for and still undercounted, because "exhaustive" only covers the enumerated forms, never the compiler's actual chosen one. **Reopen if:** before trusting a "no matching function exists" result from an instruction-form census, ask whether the predicate's literals are the ONLY way a compiler could reasonably emit that operation (sign-safe masks, branching round-ups, and de Morgan'd complements of an `AND` are all common alternates to a bare literal+`AND` pair) — if not, the census answers a narrower question than it appears to.
- **`TEST reg,0xf` is an alignment check, not a bound-against-15 comparison.** Use `CMP` only when searching for a genuine range-bound test.
- **A literal-immediate scan for a specific hardcoded shader register number, across every call site of the six known VSCF/PSCF producer functions, is a clean but narrow check — it only rules out a DEDICATED function that always uploads that exact register with a compile-time literal, not a data-driven producer.** Confirmed via `Tint_color`/PS c37 search (`spec-render-pipeline.md` §20.12.13): all 85 real call sites to `FUN_00475B50`/`BE0`/`C80`/`D80`/`E10`/`EB0` checked for a literal `PUSH 0x25` (37) immediately before the `CALL` (register is always the last-pushed, first-parameter arg at every real site in this binary) — zero hits; the only 9 literal-register call sites anywhere are the already-documented `0x14`-`0x1b` per-light block. The other 76 sites all push a runtime-computed register (from a global, struct field, or data-table entry) — completely invisible to this kind of scan. **Reopen if:** you have a specific data-driven candidate (a global slot or table-entry writer) to trace instead of hoping for a literal hit.

## Data-shape / naive-count traps

- **The `<root><Table>` shape is not universal, and neither is "every child of `Table` is a real row."** 260/2,222 real `.xtbl` files don't have the plain `<root><Table>` shape at all (`spec-xtbl-format.md` §8). Separately and just as important: many `.xtbl` files carry an editor-only `TableTemplates` and/or `TableDescription` sibling of `Table`, containing example/schema rows that are NEVER read by the real loader — a naive whole-document tag count or `iter()`/substring scan silently inflates row counts by including these. Confirmed to have caused real miscounts, independently, at least 4 times: `unlockables.xtbl` (403 counted vs. 312 real), `cheats.xtbl` (151 vs. 97), `vi_enter/exit/ride.xtbl` (668/822/464 vs. 657/813/454), `qte_sequences.xtbl` (a claimed "167 nodes vs 160 cap overflow" that evaporated once `TableTemplates`'s 7 example rows were excluded — the real data was nowhere near the cap). **Always count via `ElementTree`, explicitly find the real `Table` node, and only count/inspect ITS direct children — never a whole-document scan.** Also watch the opposite mistake: some tables have a legitimate NESTED row container inside `Table` (`anim_files.xtbl`: `Table>Files>Anim_files>Anim_file`×5,968; `customization_items.xtbl`: `Variants` is a sibling of `Wear_Options`, not nested inside it) — a shallow "count Table's direct children" check can UNDERcount those. Confirm the real structure directly before concluding a mismatch either way.
- **A file with no `<Table>` wrapper at all (`root`'s own children ARE the rows) needs its own row-tag filter — a generic "fall back to counting all of root's children" helper will sweep up a leaf count field as if it were a row.** Confirmed: `action_nodes.xtbl` has `root` children `num_objects` (a count leaf) then 44 `object` rows; a naive fallback counted 45 "rows." **Always filter by the row element's own tag name when there's no `Table` wrapper, don't just take every child.**
- **Two files existing under the same base filename in two different archives can be either byte-identical duplicates OR a genuine, different, larger/smaller superset — check, don't assume either way.** Confirmed both patterns exist: `combat_tricks.xtbl`/`store_weapons.xtbl`/`taunting.xtbl`/`hostage.xtbl`/`windshield_cannon.xtbl` are byte-identical across `da_tables.vpp_pc`/`misc_tables.vpp_pc`; but `ammo.xtbl`, `continuous_explosions.xtbl`, `vehicle_interaction_info.xtbl`, `audio_banks.xtbl`, `audio_personas.xtbl`, `foley_engine.xtbl`, `npc_color_palette.xtbl`, `customization_materials.xtbl` all have genuinely LARGER row counts in `patch_compressed.vpp_pc` than in `misc_tables.vpp_pc`. DLC copies of some tables also live under a `dlcN_`-prefixed filename rather than the shared base name (`dlc1_customization_items.xtbl`, `dlc1_audio_banks.xtbl`, etc.) — a plain-filename search across DLC archives will silently miss them. **Always check row-by-row byte content before calling two same-named files "duplicates," and check for prefixed variants before concluding a table has no DLC copy.**
- **Archive precedence when the same filename exists in two archives: `patch_compressed.vpp_pc`/`patch_uncompressed.vpp_pc` win over `misc_tables.vpp_pc` at boot** — traced to a 3-slot priority list populated exclusively by the two patch archives, checked at lookup time before the general mounted-archive collection (`spec-tables-progression.md` §14.2, CONFIRMED disassembly). When you find two copies with different row counts, the patch copy is very likely the one actually loaded — flag which copy validation ran against.

- **A per-channel (or per-object) bounding-box-inclusion test can look like a real positive even for the WRONG decode, if the reference box itself is too generic/local — and this bites a fixed, no-fitted-parameters decode just as easily as a fitted one.** Confirmed 2026-09-29/30 (`spec-vertex-format.md` §12.13 item 3): a `SHORT2÷1024` decode of code 24's unidentified `+16` slot scored 96.58% pooled in-bounds against each channel's OWN real position bbox — looking like a breakthrough — but a shuffled-mesh control (scoring the same values against a randomly-mismatched OTHER channel's bbox) scored 80.71%, nearly as high, because zone-chunk position boxes are apparently similar-sized/local enough that almost any small 2-vector passes against almost any chunk's box. The correct, decisive test was PER-VERTEX (does this exact vertex's decoded value track THIS SAME vertex's own real coordinate, not just "land inside the channel's overall box") — that came back at chance level for both the real pairing and a shuffled-vertex control, correctly refuting the candidate. **Reopen if:** you're tempted to accept a per-channel/per-object bbox-inclusion result without also running a shuffled control AND a per-vertex (not per-channel) tightness check — a per-channel-bbox test alone is not sufficient evidence, confirmed or refuted, for either a fitted (bias/scale) or fixed decode.

## Cleanroom / reporting failure modes

- **Never quote raw Ghidra decompiler pseudocode expressions or auto-named decompiler variables verbatim in a spec** (`(**(code**)(...))()`, `piVar8`, `iVar10`, `iStack_548`, etc.) — even though they're not this game's own source, quoting the decompiler's literal reconstructed C is a real cleanroom-policy violation this project caught and had to fix once already (`spec-render-pipeline.md` §16, corrected 2026-09-25). Describe behavior in plain English citing only function/data ADDRESSES, public documented API names, and short literal data strings.
- **A self-reported "checked against the clean-room rule, confirmed clean" claim is not sufficient — verify it yourself.** 2026-09-29: the CTAB register-order cross-check agent explicitly stated it had checked its own new §23.6.3 text against this exact rule and found it clean, but the text it landed (already synced to Team B before the orchestrator's own re-check) contained a live `fVar24 = -*(float*)(param_2+0x1c)` decompiler pseudocode expression. A grep sweep of the whole file for the common Ghidra auto-name patterns (`fVar`/`iVar`/`uVar`/`piVar`/`local_[0-9]`/etc.) also turned up three older, unrelated pre-existing instances (`uVar6`, `uVar2`, `local_3c`) that had been synced earlier without being caught. All four fixed in place (reworded to plain English citing only addresses/offsets), re-synced, confirmed by a fresh grep returning zero hits. **Run this grep pattern over the whole spec file as a standing check whenever an agent claims a clean-room pass on new render-pipeline text — don't rely on the agent's own self-certification.**
- **Some documents' clean-room rule bans BARE `DAT_`/`FUN_`/`param_`/`LAB_` tokens too, not only full pseudocode expressions and raw asm listings — check each document's own stated rule before assuming the project-wide convention applies.** `spec-lua-api-behaviour.md`'s own front matter explicitly lists `DAT_...` (and by the same "etc." reasoning, the sibling `FUN_`/`param_`/`LAB_` forms) as banned even as a bare address-citation token — stricter than most other specs in this project, which use `FUN_XXXXXXXX`/`DAT_XXXXXXXX` constantly and acceptably as a citation shorthand for "the function/global at address 0xXXXXXXXX" (confirmed: `spec-geometry-format.md`, `spec-vertex-format.md`, and `spec-tables-traffic-ai.md` all do this throughout, unremarked, in already-synced text). Found 2026-09-30 when a subagent's raw report (destined for `spec-lua-api-behaviour.md`) was full of bare `DAT_XXXXXXXX` tokens that passed the STANDARD cleanroom grep (which only targets pseudocode expressions/auto-named locals/raw asm lines) cleanly — the standard grep does not catch a bare Ghidra label used as if it were just an address. Also caught, already sitting in the live spec from an earlier edit in the same session: `param_1`/`DAT_0151d5a8` used directly. **Reopen if:** transcribing disassembly-derived content into `spec-lua-api-behaviour.md` specifically — re-grep for `\bDAT_[0-9A-Fa-f]+\b|\bparam_[0-9]+\b|\bFUN_[0-9A-Fa-f]+\b|\bLAB_[0-9A-Fa-f]+\b` on top of the standard pattern, and rewrite any hit as a bare `0xXXXXXXXX` address (matching that document's own established citation style everywhere else) before syncing. This is NOT a general project-wide rule — check the target document's own front matter first.
- **When hand-transcribing a multi-part tranche report into a spec via `specedit.append_section`, never write inline prose self-references using the real "§N.M" syntax as a placeholder for "my own future section number" — `append_section` only renumbers `### N.M` HEADING lines, not inline mentions inside sentences.** Found 2026-09-30 transcribing a 28-function Lua tranche into `spec-lua-api-behaviour.md` as new §15: the draft used "§1.N" throughout its own body text as a placeholder intending it to become "§15.N" once appended (matching how heading placeholders like `### 1.5` correctly become `### 15.5`), but inline sentences like "see §1.29 item 4" or "confirmed at §1.1/§1.4/§1.8" are plain prose, not headings — they were never touched by the renumbering regex, and silently collided with the REAL, external document §1 (a completely different, pre-existing section) once synced. ~15 instances shipped to Team B before an independent verification agent (re-deriving the same content from scratch for an unrelated reason) caught the collision by noticing some "§1.N" citations didn't match what real §1.N actually says. **Fix going forward: write inline self-references as plain text ("item 5", "the 3rd function above") while a section's real number is still unknown, and either convert them to the real "§N.M" form by hand in a final pass, or use a token that cannot collide with any real citation (never a bare "§1.M" placeholder, since §1 always exists in a spec with this many prior tranches).**
- **"Writes the boolean straight to a global (0xADDR)" can silently cite the wrong address — a one-line SETTER FUNCTION's own entry point, not the global it actually writes to — when the call site itself is trivial enough to look like an inlined write.** Found twice in the same 30-function tranche (`spec-lua-api-behaviour.md` §18.24/§18.25, adversarial review, 2026-09-30): `radio_global_block` was written up as writing straight to `0x00556730`, but that address is a real function (`void FUN_00556730(bool p) { DAT_013bb7d4 = p; }`) — the real global is `0x013bb7d4`, never mentioned. Same mistake, doubled, in `player_grenades_enable` (two setter-function addresses cited as if they were the two globals). Both slipped past the standard cleanroom grep (the addresses were already correctly written as bare `0x...`, so no banned token fired) and past a first read-through, because a `CALL 0xADDR` immediately followed by nothing else reads exactly like an inlined `DAT_ = value` write if you don't check whether `0xADDR` is itself a defined function. **Reopen if:** writing up any "writes/clears a global directly" claim from a decompile — check whether the address in question is a function entry point (has its own body/prologue) before citing it as a data address; if it's a one-line setter, the write's real target is one hop further in, inside that function's own body.
- **A generic-sounding function name based on how it's called from ONE site can be wrong** — `FUN_0049c890` was described as "a generic reserve-space helper" based on its 58 callers all needing buffer space, but decompiling its own body showed it's actually a fixed, single-opcode notify-poster; the real generic emit primitive was a different function (`FUN_00473770`) — and even THAT hypothesis was refuted on the next pass (it turned out to be a state-resolve-and-apply routine with no generic write capability at all; there is, in fact, no single generic reserve+write function — the pattern is a repeated compiled idiom, not one shared routine). **Don't name a function's ROLE from its callers' shared NEED alone — decompile its own body before asserting what it does.**
- **Ghidra's `undefinedN` type tokens (`undefined4`, `undefined8`, `undefined1`, etc.) in a CODE-SHAPED line (a fenced ```c block with a function signature/body, or an inline pseudocode statement) are raw decompiler pseudocode, not a bare address-citation token — the same violation WALLS.md's own first cleanroom entry already bans, just missed by every prior sweep because those swept for `FUN_`/`DAT_`/auto-named-variable patterns, never for Ghidra TYPE names.** Found 2026-09-30 (peer-caught, `purrsian-44`, after the repo went public): `spec-rig-format.md` (~lines 2172-2173) and `spec-physics-format.md` (line 411) each had a fenced ```c block rendering a full decompiled function signature/body (`undefined4 FUN_007542a0(p1,p2,p3,p4,p5) { undefined4 r = FUN_00753d40(...); ... }`) — both reworded to plain English citing only addresses. **A bare type-name MENTION inside ordinary prose is still fine** (e.g. "`DAT_024fa348`'s static image is all-zero (Ghidra: `undefined4`, length 4)" — a type annotation in a sentence, not a reconstructed code line) — the distinction is code-shaped (braces/semicolons-as-statements/a rendered function signature) vs. prose-shaped (a type name cited as one fact among others in a sentence), same distinction the existing DAT_/FUN_/param_/LAB_ entry above already draws. **Add `undefined[0-9]` to the standard pre-sync cleanroom grep going forward, on top of the existing pseudocode-expression/auto-named-variable pattern** — then manually judge each hit as code-shaped (fix) vs. prose (leave). Re-run after this fix found only the already-approved prose instances in `spec-rig-format.md`, `spec-render-pipeline.md` (×2), `spec-anim-format.md`, and `spec-lua-api-behaviour.md` (a signature description in a parenthetical, "(`undefined4*, int, int`)") — all left as-is.
- **A cleanroom grep pattern of the shape `\biVar\b`/`\buVar\b`/`\bpiVar\b`/etc. (no digit suffix in the pattern) can never match a real decompiler variable, because regex `\b` requires a transition between a word character and a non-word character — and a letter immediately followed by a digit (`iVar1`, `piVar8`, `local_28`) is NOT such a transition, so the trailing `\b` sits one character too early and the match silently fails every time.** Found 2026-10-02 re-testing this project's own standard sweep pattern (used throughout this whole session, including by several dispatched agents who were handed this exact pattern in their own briefs and self-reported "0 hits" clean passes). The `local_[0-9a-f]`/`undefined[0-9]` portions of the pattern were already written correctly (they embed the digit class inside the pattern itself, so the final `\b` falls after a digit, which IS a real boundary against following non-word text) — only the bare-name alternatives (`iVar`, `uVar`, `piVar`, `puVar`, `pvVar`, `fVar`, `sVar`, and this document's own `uStack`/`unaff_`/`extraout_` without embedded digit classes) had the flaw. Also found: a NEW `undefined[0-9]*` variant written during this same investigation (star instead of plus) matches the bare English word "undefined" with zero trailing digits — a different, opposite flaw (over-matching ordinary prose like "left undefined" instead of under-matching real tokens). **Correct pattern, verified against both a positive set (`iVar1`, `uVar2`, `local_28`, `piVar8`, `param_1`, `LAB_0088bbaf`, `undefined4`, `in_ECX`) and a negative set (plain English "undefined", "piVar8, iVar10" as a quoted front-matter example) before trusting it:**
  `\b(iVar[0-9]+|uVar[0-9]+|piVar[0-9]+|puVar[0-9]+|pvVar[0-9]+|fVar[0-9]+|sVar[0-9]+|cVar[0-9]+|bVar[0-9]+|pcVar[0-9]+|pbVar[0-9]+|local_[0-9a-fA-F]+|uStack_?[0-9a-fA-F]+|auStack_?[0-9a-fA-F]+|unaff_[A-Za-z0-9]+|extraout_[A-Za-z0-9]+|undefined[0-9]+|param_[0-9]+|in_[A-Z]{2,4}|LAB_[0-9a-fA-F]+)\b`
  **Re-swept every spec touched this session under the corrected pattern: all of today's NEW content (`spec-vint-doc-format.md`, `spec-tables-vehicle-world.md`, `spec-tables-audio-radio.md`, `spec-tables-progression.md`, `spec-tables-ui-controls.md`, `spec-tables-animation.md`) is genuinely clean (0 hits); `spec-lua-api-behaviour.md` still only its one accepted front-matter example.** Four pre-existing files (`spec-lua-bindings.md`, `spec-rig-format.md`, `spec-physics-format.md`, `spec-world-streaming.md`) showed non-zero hits under the corrected pattern, but **on inspection every one of them is accepted, not a real violation**, for two separate reasons already on record just above in this same file: (1) **bare `LAB_XXXXXXXX` address-label citations (the large majority of the hits, e.g. `spec-lua-bindings.md`'s 3, most of `spec-rig-format.md`'s and `spec-world-streaming.md`'s) are the same accepted address-citation shorthand this project uses for `FUN_`/`DAT_` everywhere except `spec-lua-api-behaviour.md`'s own stricter front-matter rule** (the entry two above this one, "Some documents' clean-room rule bans bare `DAT_`/`FUN_`/`param_`/`LAB_` tokens too") — confirmed by independent cross-check (peer `purrsian-d3`, 2026-10-02) against a differently-shaped but equally correct pattern, and (2) the small remainder (`spec-rig-format.md`'s `sVar1`/line ~2745 and three `unaff_EBX`/`unaff_ESI`/`unaff_EDI` at line ~1684, `spec-world-streaming.md`'s `param_1`/line ~1118) are each, on direct inspection, a prose mention describing a historical fix or a methodological "tell" (e.g. "whose decompile leaked `unaff_EBX`/`unaff_ESI`/`unaff_EDI` — the tell that the boundary is wrong," or a Changelog line recording "replaced the `param_1` auto-name with 'the tier argument'") — the exact same accepted category as this document's own entry above about the lua-api-behaviour.md front matter's "piVar8, iVar10" example, not a live pseudocode leak. **Net finding: the pattern bug was real and worth fixing, but it did not hide an actual cleanroom violation anywhere in the corpus — only a weaker-than-intended verification tool, now fixed.** **Reopen if:** running any future cleanroom sweep, use the corrected pattern above (not the old one); if normalizing every `LAB_` citation to a bare `0x...` address for stylistic consistency across the whole project is ever wanted, it's a real but low-priority mechanical filler task (not an urgent fix), per the peer's own assessment.

## Specific refuted claims (do not re-cite as fact)

- ~~D3D9 vertex-shader COM vtable calls (`CreateVertexDeclaration`/`DrawIndexedPrimitive`) — zero calls found; renderer is wrapped behind its own abstraction.~~ **REFUTED — `CreateVertexDeclaration` IS called** (`FUN_00476ca0`, vtable `+0x158`); the original scan searched for `CALL [reg+disp]` (293 sites, 0 hits) when the compiler emits `MOV reg,[reg+disp]` then `CALL reg` (17,916 sites, the real call among them).
- Vehicle `high16`'s factoring as `high16 = a*5 + b` (fixed divisor 5) — refuted in favour of `3a + b` (65.1% vs 99.0% concentration on the dominant cut points); and *that* "the field is an index" story was itself eventually superseded by disassembly + a real-data population join proving `high16` is a vertex-CHANNEL index, not a divisor-factored composite of anything (`spec-vehicle-geometry.md` §11.1/§11.5, `spec-render-pipeline.md` §16.4/§18.6, 2026-09-28).
- Continuation-search "ambiguity 1.00" as evidence of anything — an artefact of a wide (512-candidate) search space, not a real signal; the actual mechanism was a missing skip-table.
- Tangent-4th-byte handedness as carrier-independent — fails on vehicles specifically (~17.9%, independently reproduced by Team B); CONFIRMED label now scoped to characters/items only.
- `.anim_pc` translation as a per-bone rest-offset check — 90.5% of tracks carry zero translation keys; translation is stored only for bones that move, not per bone per frame.
- Mode-a container decompression beyond entry 0 — closed dead end (3 static + 1 dynamic pass) — **superseded entirely** by the later physical-offset rule (`spec-vpp-container.md` §7), which resolved the whole question a different way; don't re-attempt the decompression angle.
- Denominator-mismatch explanations for the terrain/zone-data 93.1%/0% figures — refuted by Team B's own arithmetic/code; real causes narrower and still partly open (`spec-zone-data-format.md`'s own note).

## Emulator-harness (Unicorn) dead ends, 2026-09-29 — first session using this capability

- **A global data structure that "looks like" a static compile-time table (a hash table, a registry, a lookup array) may actually be populated by RUNTIME initialization code, and a cold full-image emulation will not fail loudly when it reads one — it will silently return "empty/not found," which looks exactly like a real (but wrong) answer.** Confirmed while scoping `notoriety_force_no_spawn`'s (`spec-lua-api-behaviour.md` §3.6) name→code hash table (VA `0x02623a80`) as an emulation target: the table's own address lands past its section's `SizeOfRawData` (into the zero-fill tail out to `Misc_VirtualSize`) — i.e. it does not exist as bytes in the file at all, only as reserved, zero-initialized space the real process fills in at some point after the image loads. **Before trusting ANY emulated call that reads global state, check whether that SPECIFIC memory is file-backed** (`Emu.va_is_file_backed(va)` in `tools/harnesses/unicorn_call.py` does this check) — don't assume "it's a global, so it's static." **Reopen if:** the relevant initializer function is also run under emulation first (not attempted this session), or a real populated-table memory dump becomes available another way.
- **A function-pointer array's entry ADDRESS (where the `{namePtr,funcPtr}` MOV-immediate pair for one specific registrar slot happens to be written) is not the same thing as the FUNCTION'S OWN entry point (the funcPtr VALUE those instructions write) — and citing the former as if it were the latter is a real, confirmed mistake in `spec-lua-api-behaviour.md` §4.7/§4.8 (`continuous_spawn_stop`/`continuous_spawn_start`), corrected 2026-09-29 while tracing an emulation candidate.** Both cited addresses (`0x00a21b62`, `0x00a21b36`) decompiled, in a Ghidra copy where the real function boundary had never been force-fixed, to a location INSIDE the giant registrar-array-construction function (`FUN_00a20840`, itself ~2,028 unrolled `MOV [stack],imm32` instructions covering the whole 1,014-entry table ~~**[the "~2,028"/"1,014" figures here were an undercount from a partial read — CORRECTED 2026-10-02: the function is exactly 2,032 stack-store instructions over a 1,016-slot table (0x1fc0-byte stack allocation ÷ 8 bytes/pair); see the dated entry below for the full re-count and what the 2 extra slots turned out to be]**) — not to the two real functions' own bodies. The real entry points (`0x00a42b50`/`0x00a435a0`) were found by reading the SECOND of the two consecutive MOV instructions at the cited address (the funcPtr immediate, not the namePtr one), and confirmed by decompiling THAT address and matching it word-for-word against the section's own already-written body text. **Reopen if:** any other function in this document's per-function address citations was derived the same error-prone way (an address search that happened to land inside the registrar-builder's own 0x00a20840–0x00a25f7e range is the tell) — every OTHER function in this document's §1–§4 lies well outside that range, so this appears to be isolated to these two.

## Gameplay-registrar row count resolved, 2026-10-02 — 1,016 slots, 1,015 unique names, not 1,014

**The gameplay registrar `FUN_00a20840` genuinely builds 1,016 `{name, function}` pairs, not 1,014 — confirmed by reading every one of its 2,032 stack-store instructions end to end (range dump `0x00a20840`-`0x00a25f46`), not by re-counting a partial grep.** The function allocates exactly `0x1fc0` bytes of stack (`MOV EAX,0x1fc0` / `__alloca_probe` at entry) = 1,016 × 8-byte `{name,func}` slots, and the trailing registration loop (`0x00a25f47`-`0x00a25f73`) confirms it by running `0x3f8` = 1016 times over that exact span. A full offset-by-offset check of every one of the 2,032 individual stack-slot writes found zero gaps and zero accidental duplicates in the *stack offsets themselves* — every slot is written exactly once. The earlier "~2,028 MOV / 1,014-entry" figure (WALLS.md, the entry just above) was an undercount from a dump that was cut one instruction short at its tail end, not a real structural fact about the table.

**Of the 1,016 registered slots, exactly 1,015 are unique names.** The one real duplicate is a byte-for-byte, harmless literal: `on_mission_item_drop` is registered **twice**, at two different stack slots, but both times with the identical name-string address (`0x0117b000`) and the identical handler address (`0x00a57000`) — confirmed by reading both registration sites directly. It is not two different functions competing for one name, and not a conflict; the second `lua_setfield` just overwrites the Lua global with the same value it already had.

**The one genuinely new, previously entirely un-rostered name is `on_mission_item_drop` → handler `0x00a57000`.** It does not appear in `tools/lua_gameplay_names_only.txt`, `tools/lua_gameplay_api_1014.txt`, any of the four project-wide `tools/lua_all_registered_14XX_tagged.txt` rosters, or Team B's own 1,181-row call-count reconciliation table (`lua_reconciliation_called_and_registered_1181.tsv`) — meaning it has zero observed call sites in Team B's instrumented corpus, which is exactly why the call-count-ordered ranking-tranche methodology never surfaced it. **Published a corrected roster: `tools/lua_gameplay_names_only_1015.txt`** (the old 1014-line file plus this one line, in its correct registration-order position; verified by diff to differ from the old file by exactly that one inserted line).
