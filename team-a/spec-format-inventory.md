# Saints Row: The Third — Resource-Type Registration Inventory

**Prepared by:** SPEC TEAM (cleanroom reverse-engineering process)
**Phase:** 1, infrastructure pass — a lookup table so future "what's worth looking at next" decisions are a table read instead of a fresh disassembly walk.
**Scope:** Every resource type the engine registers at startup: its numeric type ID, its internal name, its file extension(s), its constructor/destructor addresses, and whether this project has characterized that format yet.
**Method:** Full decompilation of the registration function (`FUN_00700780`, `spec-geometry-format.md` §4.3), then programmatic reconstruction of each registration record. The record's name field is written by the compiler as inlined byte immediates that deliberately reuse the previous entry's trailing bytes, so the records were reconstructed by replaying every partial write in order against a simulated buffer, rather than decoded by hand — a hand pass would have silently produced wrong names (two such artifacts were caught and fixed this way; see §5). Extension strings that the decompiler showed as indirections were resolved by reading the underlying pointer tables out of the binary.
**Cleanroom compliance:** No decompiled code appears below. The **type names** catalogued here (e.g. `Character mesh`, `Low Mips`) are literal human-readable strings stored as *data* in the executable, and are the load-bearing content this document exists to catalog — the same convention already applied to Lua hook names in `spec-lua-bindings.md` and to `.xtbl` field names throughout this project. Function addresses are cited as evidence, not reproduced as identifiers.

**Confidence key** (as in prior specs): **CONFIRMED — empirical**, **CONFIRMED — disassembly**, **HIGH CONFIDENCE — inferred**, **HYPOTHESIS — unconfirmed**, **OPEN / UNKNOWN**.

## 1. Headline facts

- **43 resource types are registered**, not the "~45" previously estimated. **[CONFIRMED — disassembly, exact count.]**
- Type IDs run 1–45, but **IDs 6 and 28 are absent** — no registration exists for either anywhere in this function. **[CONFIRMED — disassembly.]** Whether they're reserved, registered elsewhere, or vestigial is **OPEN**.
- **Every file extension is platform-selected at registration time.** Where the decompiler showed an indirection, it's an index into a per-platform extension table. Reading those tables out of the binary gives, at every index: `0 = pc`, `1 = ps2`, `2 = ps3`, `3 = xbox`, `4 = xbox2` (Xbox 360). **[CONFIRMED — disassembly, read directly from the pointer tables; the same five-way split appears in all 13 extension tables.]** **[OPEN — desk review 2026-09-30: count conflict. §2 below shows 30 distinct non-empty `pc` extension strings (`.ccar_pc`, `.gcar_pc`, `.cvtf_pc`, `.cpeg_pc`, `.gpeg_pc`, `.cvbm_pc`, `.gvbm_pc`, `.cefct_pc`, `.gefct_pc`, `.ccmesh_pc`, `.gcmesh_pc`, `.cmorph_pc`, `.gmorph_pc`, `.rig_pc`, `.cvbl_pc`, `.gvbl_pc`, `.csmesh_pc`, `.gsmesh_pc`, `.anim_pc`, `matlib_pc`, `.xtbl`, `.csc_pc`, `.czn_pc`, `.gzn_pc`, `.clmesh_pc`, `.glmesh_pc`, `.csrt_pc`, `.gsrt_pc`, `.cfmesh_pc`, `.ctdg_pc`). To be settled against the executable: enumerate the five-pointer arrays `FUN_00700780` references.]** The shipped PC executable therefore still carries every console platform's extension strings. All extensions in §2 below are the **`pc` (index 0)** variants, which are the ones this build actually uses.
- **Five registered types have no constructor and no destructor at all** (both null): `Zone (fast)`, `Zone (slow)`, `Buffer`, `Zone header (fast)`, `Zone header (slow)`. **[CONFIRMED — disassembly.]** This independently confirms and extends the earlier `spec-terrain-format.md` finding that `.czn_pc`/`.gzn_pc` has no dedicated constructor — it applies to the zone *header* types too.

## 5. Methodology note worth keeping

The record's name field is assembled by the compiler as a series of partial byte writes into a stack buffer that **deliberately reuses whatever the previous entry left behind** — a size optimization. Two consequences, both of which bit during this pass and were caught:

1. **Naive decoding produces plausible-looking wrong names.** A first pass read type 9 as `Pcust meshcvtf` (its real name, `Pcust mesh`, plus four stale bytes from the preceding `Character cvtf` entry) and type 36 as `Treel Mesh` (real name `Tree`, plus stale bytes from the preceding `Level Mesh`). Both are *readable* and *thematically plausible*, which is exactly what makes them dangerous — neither would have looked wrong in a finished table. They were only caught by modelling the null-terminating writes explicitly.
2. **Some entries clear the whole record and some don't.** Entries that begin with a full-record clear reset the extension and constructor fields too; entries that don't, inherit them. A reader that tracks only the name buffer will attribute a previous entry's constructor to a later one — this produced three wrong constructor attributions (types 43, 44, 45) before being fixed.

**Standing lesson, consistent with this project's existing discipline** (`HANDOFF.md` §5): when reconstructing compiler-emitted data, replay the writes; don't read the immediates. A plausible-looking decoded string is not evidence that the decode was right.
