## 1. Overview and Filenames

All three files live in the platform save-data location as loose files (not inside any `.vpp_pc`/`.str2_pc` container) and are read/written through a generic "remote storage" I/O abstraction in the executable — the same code path is used regardless of whether the underlying backend is Steam Cloud or local disk, which is why the code repeatedly calls through what decompiles as a `SteamRemoteStorage`-shaped interface even on this non-Steam (GOG) distribution; a different backend is plugged in underneath the same interface. **[CONFIRMED — disassembly.]**

| File | Size | Role |
|---|---|---|
| `savedir.sr3d_pc` | **exactly 608 bytes**, fixed | Index of up to 24 save slots: which are occupied, plus per-slot metadata. |
| `sr3save_NN.sr3s_pc` (`NN` = 2-digit zero-padded slot number, e.g. `sr3save_00.sr3s_pc`) | **exactly 108,776 bytes**, fixed | One save slot's full snapshot: player/world state plus display metadata (level, date, time, playtime, etc.). |
| `sr3def_profile` | **exactly 16,968 bytes**, fixed | User settings/profile data, independent of any specific save slot. |

All three sizes are **exact literals confirmed two ways**: they match the real sample files byte-for-byte, and each size also appears as a literal constant in the code that allocates the read/write buffer for that file. **[CONFIRMED — disassembly + empirical.]** None of the three formats showed any evidence of compression — each is read and written as one single fixed-size raw buffer, with no framing, chunking, or codec involved. **[CONFIRMED — disassembly: the read and write calls for each format pass the buffer straight to/from the generic file I/O call with no decompression step in between; also consistent with `sr3save_NN.sr3s_pc` samples containing directly-readable ASCII/UTF-16 text at fixed offsets, per §3.]**

**Filename construction, confirmed from code:**
- `sr3save_NN.sr3s_pc` is built from the literal pieces `"sr3save"`, a 2-digit zero-padded slot number, and `"sr3s_pc"`, joined with a `"%s_%.2i.%s"` format pattern — i.e. `sr3save_<NN>.sr3s_pc`. **[CONFIRMED — disassembly.]**
- `sr3def_profile` is built from the literal prefix `"sr3"` and a second identifying string joined with `"sr3%s"` — the file is opened for both saving and loading using the same generated name. (Windows filenames are case-insensitive, which is why this reconciles cleanly with the real file's all-lowercase name despite the identifying string appearing uppercase in the code that requests it.) **[desk review 2026-09-30: read this as one construction — the prefix `sr3` is applied once; the resulting on-disk name is `sr3def_profile` (table above, §7.1), not "sr3" followed by "sr3%s".]** **[CONFIRMED — disassembly.]**

**Review status (2026-09-30), §1: DESK-PASS, text fixes applied — desk review (not re-derived from the executable).**

## 2. `savedir.sr3d_pc` — Save Slot Directory/Index

**Fully resolved this pass — every byte of the 608-byte file is accounted for, and the model was validated exactly against a real sample.**

### 2.1 Layout

```
offset 0x000, 4 bytes : checksum/hash of the 600-byte slot table that follows
offset 0x004, 4 bytes : active slot count
offset 0x008 onward   : 24 fixed-size slot records, 25 bytes each (24 × 25 = 600 bytes)
                         → file ends at 0x008 + 600 = 0x260 = 608 bytes exactly
```

| Field | Confidence | Evidence |
|---|---|---|
| **Total file size: exactly 608 (`0x260`) bytes.** | **CONFIRMED — disassembly + empirical.** | The read function rejects the file unless exactly `0x260` bytes come back from the read call; the real sample file is exactly 608 bytes. |
| **Offset `0x0`, 4 bytes: a checksum/hash of the 600-byte slot table.** | ~~**CONFIRMED (that it's a hash of the table) — disassembly. Exact algorithm — OPEN/UNKNOWN.**~~ **CORRECTED 2026-09-20 (Agent R, §6.1): CONFIRMED — disassembly + empirical, 4/4 real directories: CRC-32, reflected polynomial `0xEDB88320`, initial value 0, no final XOR, computed over bytes `0x008`–`0x25F` only (the count at `0x004` is not covered).** | ~~The save routine builds the 600-byte slot table first, passes it through a hashing/transform routine, and writes the first 4 bytes of that routine's result as this file's leading 4 bytes; the load routine's counterpart step reads this file's leading bytes and processes the table through the same routine (the exact comparison the decompiler showed here was ambiguous — it may validate the checksum, or something adjacent to it — so treat "this field is a checksum of the table" as confirmed, but not the exact pass/fail check performed against it). The specific hash algorithm was not traced in this pass (same class of "small custom transform" as the filename hash found in the container-format spec, but not confirmed to be the *same* routine — no evidence either way). An implementation can safely treat this as opaque/informational unless byte-for-byte-identical output to the original tool is required.~~ **Corrected: the load routine does verify it — a mismatch rejects the read (error 4) and the whole directory is then treated as empty; the active-flag recount against `0x004` happens afterwards (error 5). | **Offset `0x4`, 4 bytes: active slot count.** | **CONFIRMED — disassembly + empirical, exact match.** | The load routine independently recounts how many of the 24 slot records have a non-zero flag byte (§2.2) and rejects the file if that count doesn't match this field. **Review status (2026-09-30), §2.1: VALIDATED-BY-DATA: 608 = 4 + 4 + 24 × 25; CRC 4/4 and active-count recount 4/4 (2, 5, 2, 3) by Team B — desk review (not re-derived from the executable).**

### 6.2 Play-time field at `0x0A0` — the counter is **whole seconds**; the save list shows **minutes**

**[CONFIRMED — disassembly + empirical, 16/16.]** *This corrects §3's "tick count" wording and the brief's expectation that dividing by a constant "displays seconds".*

- **What is stored.** The header serializer copies the 20-byte game-clock structure (in-world date/time-of-day fields, then a `float32`) to `0x08C`–`0x09F`; the `float32` play-time clock lands at `0x09C`. A second helper (code at `0x00B97290`) then writes **`0x0A0 = the same clock truncated toward zero to an int32`** (it switches the x87 rounding mode to truncate first). **Empirical: `int(float32@0x09C) == uint32@0x0A0` in 16/16 samples** (e.g. `185165.890625` → `185165`, `132012.75` → `132012` — truncation, not rounding).
- **Unit.** The clock is advanced once per frame by the frame time **in seconds**: the frame timer converts a microsecond counter to seconds (divisor `1,000,000.0`), clamps a single frame to at most `0.25` s, divides by a global time-scale (default `1.0`), and the main loop passes that to the clock-advance routine, which adds it into the `float32` clock. So `0x0A0` is **game-time seconds** (scaled by any time-scale; the main loop skips the clock advance on frames where it takes an early-out branch, apparently the paused state — not investigated — and the sample pairs below show it not counting menu time).
- **What the save list shows.** The descriptor builder (`0x00B99C50`) computes `minutes = truncate( float(uint32 @0x0A0) / 60.0 )` — the divisor is the 8-byte constant `60.0` in the read-only data (`0x0111E478`); a value with the sign bit set is first biased by `2^32` (unsigned interpretation); the x87 rounding mode is again forced to *truncate*. The result is stored as an **integer number of minutes** in the descriptor and handed to the UI as slot 6 of the per-row value array (HIGH CONFIDENCE for the slot number: read off the caller's stack layout). **No hours/minutes/seconds breakdown exists in the executable on this path**; splitting minutes into hours is done, if at all, by UI content outside the executable, which I did not examine.
- **Why "seconds", not 1/60-second ticks (the natural first guess):** the code path above is unambiguous; and the data agrees only under this reading. Late-game saves (level 49–50, currency-shaped value 1.67–1.99 billion raw, §6.5) hold `85785`, `87637`, `150778`, `185165` → **23 h 49 m, 24 h 20 m, 41 h 52 m, 51 h 26 m**; read as 1/60-s ticks these would be 24–51 *minutes* of play for a maxed-level character. The brand-new-game save (level 0, 1,080 respect) holds `948` (15 m 48 s). Two saves from one session 200 s of wall-clock apart (`13:38:02` → `13:41:22`) hold `39688` and `39857`: **169 s** of game clock (85 %), where the tick reading would give 2.8 s. Another pair 249 s apart (`22:00:42` → `22:04:51`) differs by 87 s. In all such pairs game-time ≤ wall time, as it must.
- Worked values: `39688` s = 11 h 01 m 28 s → descriptor **661 min**; `39857` s → **664 min**; `150778` s = 41 h 52 m 58 s → **2512 min**.
- Precision note (HYPOTHESIS, unobserved): the clock is a single-precision float accumulating ~0.017 s per frame, so it must stop advancing correctly at very large values (about 72.8 h of game time, where the float spacing exceeds the per-frame step). No sample is near that.

**Review status (2026-09-30), §6.2: VALIDATED-BY-DATA: `0x0A0` = trunc(float@`0x09C`) 16/16; 39,688 / 39,857 / 150,778 s → 661 / 664 / 2,512 min (Team B) — desk review (not re-derived from the executable).**

### 6.3 How the file is built — a table of 32 per-subsystem serializers, not one copy

**[CONFIRMED — disassembly.]** This answers the "one memcpy or many serializers" question: **many**, each writing at fixed absolute offsets of one shared buffer.

- **Save entry** (code at `0x00B94A10`): allocate `0x1AA00` bytes from a dedicated save arena, **zero the whole buffer**, run the serializer driver (`0x00B98BB0`), build the display descriptor from the finished buffer (`0x00B99C50`, the function found in §3), compute the hash (§6.1), then queue an **asynchronous platform-write task** (`0x00B96540`). That task writes **the first `0x1A8E8` bytes** as `sr3save_NN.sr3s_pc` (raw write, `0x00B95F30`), then marks the slot occupied in the directory, stamps its slot record, increments the count, and rewrites the directory (§6.1).
- **Serializer table:** **32 entries × `0x14` bytes at VA `0x0118BE58`**. Entry = five 32-bit words: `[0]` save routine (null for entry 31), `[1]` load routine, `[2]` alternate save routine (null unless present; 9 entries have one — entries 2, 3, 7, 9, 16, 19, 23, 25, 28), `[3]` alternate load routine, `[4]` **minimum file version at which the load routine applies**. The save driver calls each entry's `[0]` in table order with the buffer base and one further flag argument (not identified), substituting `[2]` when a global session-state object exists **and** two counters inside it differ **and** `[2]` is non-null ~~(meaning of the condition not investigated)~~ *(§11.7: the local machine is a guest in someone else's hosted online session; the alternates read/write a shadow copy of the block)*. The load driver (`0x00B98C00`) calls `[1]`/`[3]` for every entry with `[4] ≤` the file's version field.
- **Version thresholds present in `[4]`:** entries 0, 2, 3, 5–9, 11–14, 17–20, 22, 23, 29 use `1`; the others use `0x06` (24), `0x12` (25), `0x19` (26), `0x1A` (4), `0x27` (21), `0x2D` (1), `0x2E` (15), `0x34` (10), `0x35` (16), `0x3A` (27), `0x44` (30), `0x5C` (28, 31). Because the load entry point rejects any version other than 94 (§6.1) the thresholds are inert in this build: **every entry's load routine runs on a valid file.** They look like a record of when each subsystem's block was added (the newest, `0x5C` = 92, is entry 28, which also filters registry names by a "dlc" prefix and repeats several block shapes of entries 1, 6 and 13 — apparently the DLC-side counterpart; HIGH CONFIDENCE for the repetition, ~~inferred for the reading~~ **CONFIRMED 2026-09-20 (§11.4, agent X): each repeated block is the DLC-restricted twin of its base-game block, through a shared helper or table with a selector; entry 28's sub-version gate is the word at `0x11D88` (§11.3); the "dlc" filter is a name-prefix test on the mission-object list**).
- **The file ends exactly where the last serializer ends:** entry 29 copies `0x388` dwords to `0x19AC8`, i.e. **up to `0x1A8E8` = the file size** (`0x1AA00 - 0x1A8E8 = 0x118` bytes of buffer are never written by anything).
- **Header (entry 0):** stores `94` at `0x008`, `1` at `0x00C`, the literal `0x000F0F6E` at `0x010`; copies the current zone-name string (NUL-terminated ASCII) to `0x014` — *this is the write that §3 said had not been traced*; the time string (`HH:MM:SS`, wide characters, from the C runtime's time call) at `0x060`; the date string (from the runtime's date call, `MM/DD/YY`, with each `/` replaced by `.`) at `0x072` — **this explains the `MM.DD.YY` form**; the play-time words (§6.2); an 8-byte object handle at `0x058`; and a 256-bit flag set at `0x0A4`.

**Headline correction to §4.** The file is **not a tagged/typed record stream at file level.** It is a **raw memory image of one in-memory profile object**: both the save path and the load path move the object to/from the 16,968-byte buffer with a single plain copy, followed by one pointer fix-up. ### 7.4 Stat-record area (regions A0/A1) — length-prefixed records, one per *serialisable* stat

**Framing [CONFIRMED — disassembly; exact on 3/3 files].** Chunk `c` (`c` = 0 or 1) starts at file offset `0x1000·c`; its used byte count is the u32 at header `+4·c`. Records are back to back: `[u8 length L][L payload bytes]`, `L <= 0xFF`. Chunk 0's records consume **exactly** `used0` bytes (891 = 179 records) with nothing left over; chunk 1 is empty. The writer starts chunk 1 when the next record would not fit (`used + 1 + L > 0xFFF`), and fails the save if a third chunk would be needed. A record whose payload would be `>= 0x100` bytes is skipped by the writer (none occurs). Bytes after `used` are never read (all zero in the samples).

**Which records exist and in what order [CONFIRMED — disassembly + empirical].** Stats are identified by an id `0..216` (the static name/id table at `0x01141BD0` holds exactly 217 entries and its ids are exactly the permutation `0..216`). The serializer visits ids in **ascending order** and emits one record for each stat whose *type handler* has a serialise slot; stats without one emit nothing. A stat's handler type comes from its declared value type in the stat-definition data (integer → 0, float → 1, distance → 2, time → 3, money → 4, boolean → 5, percent → 6), except stats declared "complex", whose handler type is fixed by a switch on the stat id inside the executable. **Only handler types 0–6, 8–12 and 42 have a serialise slot.** The 38 ids whose handler type has none — and which therefore have **no record** — are:

`18`–`41` (24 ids), `43`, `50`, `51`, `58`–`61`, `66`, `67`, `69`, `126`, `150`, `163`, `164`.

That leaves `217 − 38 =` **179 records**, which is exactly the count found in every real file. The 38 omitted stats are the aggregate / derived ones (examples of their names: "best weapon", "favorite transportation", "most hated gang", the four city-takeover counters, "total collectibles found", "cash earned per day"); **HIGH CONFIDENCE** they are recomputed at run time rather than persisted (not traced further).

|---|---|---|---|
| 0 | integer | 4 bytes, int32 | per stat-definition data |
| 1–4 | float, distance, time, money | 4 bytes, float32 | per stat-definition data |

### 8.1 Where it comes from (evidence)

* On slot creation the worker at `0x00B96540` sets the slot's active flag to 1, then calls the fill routine `0x00B95380` with the address of the 24 bytes following the flag, increments the active count, and rewrites the directory (`0x00B963F0`, §6.1).
* The summary the fill routine serialises is a `0x58`-byte structure built by `0x00B99C50` (the descriptor builder of §3/§6.2) **from the save snapshot that was just produced plus a few live game-state values**; the same structure is later expanded for the UI by `0x00B948F0`.
* The fill routine zeroes the 24 bytes, initialises a bit-stream writer over them (capacity `0x18`), and writes 21 bit-fields in a fixed order with fixed widths, then one raw 4-byte value. The writer (`0x00881110` for n-bit fields, `0x004D4690` for 1-bit booleans, `0x00881040` for raw bytes) packs **least-significant bit first**, with one non-obvious rule, reproduced exactly by the harness: **for an n-bit field, the `n div 8` whole bytes of the value are stored byte-aligned starting at the next unused byte (after any partially filled byte), and only the remaining ~~`n mod 8` low bits~~ `n mod 8` HIGH bits continue the partially filled byte** (the whole bytes carry the low bits) **[CORRECTED (desk review 2026-09-30) — HIGH CONFIDENCE, derived from §8.2's own table: simulating this rule over the 21 widths in write order (6, 7, 9, 5, 17, 2, 1, 1, 7, 8, 7, 5, 4, 5, 7, 5, 6, 6, 32, 6, 9) reproduces all 21 byte.bit lists of §8.2 when the whole bytes take the value's low `8·(n div 8)` bits and the partial byte its top `n mod 8` bits (e.g. row 3: bits 0–7 at `2.0`–`2.7`, bit 8 at `1.5`), and fails rows 3, 5 and 21 with the low-bits reading. ### 10.1 What the sources are

### 11.6 The `0x246C`-byte CRC-guarded structure — an online "avatar" upload blob

**It is a self-checking copy of the player's customised character, used by an online gallery feature — not a co-op packet, not a cached profile.** [CONFIRMED — disassembly, with literal strings.]

- **Builder `0x00B990B0`**: zero `0x246C` bytes; fill the record with the *same per-player serializer that fills the snapshot's `0x900` record* (`0x00B98F00`); set byte `+4` = 2 and byte `+5` = 1; store the CRC (same routine as §6.1: CRC-32 reflected `0xEDB88320`, init 0, no final XOR) of bytes `[4, 0x246C)` — `0x2468` bytes — at `+0`. **Check `0x00B99100`**: byte `+4` must equal 2, then the CRC must match (byte `+5` is not tested). A separate byte-returning routine (`0x00B97730`) returns the constant 2 and is sent as an "avatar version"; another (`0x00B97720`) returns the size `0x246C`.
- **Layout.** `+0` CRC; `+4` type/version byte (2); `+5` byte (1); `+8`…`+0x225B` the `0x2254`-byte character record; `+0x225C`…`+0x226B` a 16-byte tail (the same 16 bytes the snapshot keeps at `0x2B54`); `+0x226C`…`+0x246B` = 512 bytes the builder never writes (zero). ### 11.7 The alternate ("guest-mode") serializers

**The predicate. [CONFIRMED — disassembly.]** The drivers pick a table entry's alternate routine when **(a)** a network session object exists, **(b)** two fields of it differ — `+0x58` and `+0x5C` — **and (c)** the alternate is non-null. The session object: the active-session global `0x024D8534` (read by the getter `0x0087BA20`, set only by `0x0087C340`, which also writes byte 4 of a per-slot flag array at `0x02609394` with `1` when the two fields are equal and `0` otherwise) points into a pool of `0x2D0`-byte session objects at `0x024D8570`; a fresh session is built by `0x0087D1D0`, which creates the local peer and stores **the same pointer into both `+0x58` and `+0x5C`**. The peer-removal routine (`0x0087E400`) clears `+0x58` when the departing peer *is* `+0x58` (host loss), and performs its host-only work (notifying the departing peer, session-wide broadcasts) only when `+0x5C == +0x58` before the removal. **Therefore `+0x58` = the session's host peer, `+0x5C` = the local peer, and "differ" = this machine is a *guest in someone else's hosted online (co-op) session*.** A solo game (no session object) and a host (equal) both use the primary routines. [HIGH CONFIDENCE for the names host/local — every use is consistent with them, none contradicts.]

### 12.2 What the object-class entries have in common (entries 2, 19b, 20, 21, 22)

**[CONFIRMED — disassembly.]** Five of the entries do not copy a table; they *walk one class list of the world-object manager*. The manager is one global pointer (`0x03171A64`); it holds a pool (pointer array at `+0x58`, indexed by the `u16`s of each list) and a fixed set of **class lists**, each an array of `u16` pool indices with the member count 8 bytes after the array pointer. The five lists used here: entry 2 at `+0x10C`/`+0x114`; entry 19b at `+0x178`/`+0x180`; entry 22 at `+0x190`/`+0x198`; entry 20 at `+0x2F8`/`+0x300`; entry 21 at `+0x304`/`+0x30C`. Every object carries a **64-bit handle** in its dwords at `+8`/`+0xC`; the snapshots store it as `(lo, hi)`.

- **Save**: for each member in list order: write the handle, then the object's flag bits (each entry picks its own bits, listed below). The order is therefore the class-list order, and the handle lists are *identical in all 16 samples* (154/154, 33/33, 64/64, 26/26 constant), i.e. the handles are world constants of the shipped map, not per-save values. Entries whose list is filtered (entry 20 keeps only objects whose *discovered* byte is non-zero) are packed from index 0.
- **Load**: for each stored handle that is non-zero, resolve it through the handle table (`0x031D152C`, lookup at `0x00458230`), and apply the stored bits **only if** the object exists, its "deleted" bit (`+0x33`, `0x10`) is clear, the per-type descriptor selected by the byte at `+0x34` (table `0x02CC9900`) has the class's capability bit set, and the object is not destroyed (`0x00853B10`). A handle that resolves to nothing is silently skipped. (So a snapshot written from a different map would load as a no-op.)
- The `hi` dword of a handle is not free-form but its structure was not decoded: its **low 16 bits take a small set of values with bit 15 always set** (e.g. `0x80E4` ×148 and `0x81D8` ×6 among entry 22's 154; `0x80D6` for all 26 of entry 21; `0x80E4` ×28 and `0x80CA` ×2 for entry 20; `0x80CA` ×29 and a dozen other values for entry 19b) and its **high 16 bits are a small integer** (`0x32`–`0x39` dominate). The low value is *not* one tag per class (`0x80E4` occurs in entries 20 and 22, `0x80D6` in entries 2 and 21).

### 12.3 Conventions used below

*Sentinels.* Two dwords in the executable's data (`0x029C9960`, `0x029C9964`) hold the "invalid id" value used for unfilled slots; **it is 0 in every snapshot** (unfilled slots of entries 16 and 24 read 0, not `0xFFFFFFFF`). Entry 17, and the discount slots of entry 19, use `0xFFFFFFFF` deliberately.
*Timers.* A small family of helpers (`0x006FF430` "is set", `0x006FF4C0` "has elapsed", `0x006FF4E0` read the timer's value, `0x006FF440` start it with a value in milliseconds; the meanings are inferred from their call sites) is used by entries 16 and 19 to save and restore countdown timers; the snapshot stores the value the read helper returns.
*Alternate serializers.* Where an entry has one (2, 3, 16, 19, 23, 25), the save copies the same shapes from a "session state" buffer (the range `0x0290F27C`–`0x0290F544`) instead of the live objects; nothing about the layout changes. The alternate runs only when this machine is a *guest in someone else's hosted online session* (§11.7 gives the predicate and lists what each alternate copies; entry 19's alternate replaces only the 61-dword block, its bit sets and handle table still come from the live objects).

### 12.8 Radio

The radio manager is the object behind the pointer at `0x013C58CC` (stations at stride `0x690`, a song table at `0x013BBC18`, stride 20).

#### 12.8.1 Entry 17 — the "mix tape" playlist `0xB360`–`0xB75F`  **[CONFIRMED — disassembly + empirical]**

Save `0x00B96DB0` → `0x0055E250`; load `0x00B96DD0` → `0x0055F580` (→ `0x0055E380`). The buffer is first filled with `0xFFFFFFFF` (256 dwords = 1,024 bytes), then the manager's **`u16` list of song indices** (`+0x1A4`, count at `+0x5A4`) is copied to the front. **Format: `u16` song ids in play order, terminated by `0xFFFF`; everything after is `0xFF`** (16/16; capacity 512 entries; the loader accepts at most 512). On load the loader re-registers the order for each song and sets the "has mix tape" bit (bit 5 of the byte at `+0x689`) iff the list is non-empty. Both fields live in the **first station record** (record 0 of the `0x690`-byte station array — the record that the station-list code labels "Mix Tape"; HIGH CONFIDENCE for that label, inferred from the string sitting in the station-list builder `0x0055DB40`); entry 18 (below) covers records 1 and up. **Data**: empty in 13 samples; 19–20 song ids (398, 400, 399, 401, …, 414, 295, 297, 310, 654, 660, 662, 291) in the three level-49/50 saves with 65–78 % completion.

#### 12.8.2 Entry 16 — radio event queue and commercial-event flags `0xFBE0`–`0xFC5D`  **[structure CONFIRMED; meaning HIGH CONFIDENCE]**

Save `0x00B96D50` (`0x0055C280` + `0x0055C040`; alternate `0x00B99430`), load `0x00B96D80` (`0x0055C510` + `0x0055C010`; alternate `0x00B98830`).

- `0xFBE0 + 12·i`, 8 records: `+0` **event id hash**, `+4` **the event timer's value** (read by the timer helper, restored by its setter), `+8` **times-played byte** — the up-to-8 entries of the **posted radio events** ring (events from the radio-events data table are posted with a `Post_Time`-hours timer; the load re-posts them with the saved timer). Unused records hold the invalid-id constant (0). **All 8 × 12 bytes are 0 in 16/16** (no radio event was pending at any save).
- `0xFC40`, 30 bytes: **one 0/1 flag per commercial event** (30 events named in the commercial-events data table, slot = its `EventValue`); a commercial is enabled/disabled by events it names, so these are the flags behind the ads that play. Two bytes at `0xFC5E` are pad (0). **Data**: new game has flags **1, 2, 6 and 27** set; the level-49/65 %+ saves have up to 14 set.

#### 12.8.3 Entry 18 — flagged radio stations `0xB320`–`0xB35F`  **[structure CONFIRMED; flag meaning OPEN]**
