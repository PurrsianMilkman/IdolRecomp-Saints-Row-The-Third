## 4. `.gzn_pc` — the geometry payload

The paired GPU-side file (806 KB in this sample), with **its own distinct 4-byte magic, `0xE6EA70B7`**, unrelated to either `.czh_pc`'s or `.czn_pc`'s marker values — followed by 12 zero bytes, forming a 16-byte header. **[CONFIRMED — empirical, exact bytes.]** **[OPEN — desk review 2026-09-30: `spec-zone-data-format.md` §7.1 finds that the `.gzn_pc`'s leading `u32` also appears in its own `.czn_pc` in 1,002/1,002 pairs (control 6.5%), and §7.2 calls that value the check value that tags the block's `.gzn_pc` segment (Team B `team-b/HANDOFF.md` §9.55.2 reads one such value, `0xE0006BDD`, as a file's first 4 bytes); so `0xE6EA70B7` is most likely this sample's segment check value, not a format-wide magic — do not test for it as a constant; and the 16-byte header holds for the first segment only (`spec-zone-data-format.md` §10.4). To be settled against real data.]** This 16-byte-header shape (4-byte tag + 12 zero bytes) directly matches the pattern already confirmed for `.gcmesh_pc` and inferred for `.glmesh_pc` (`spec-geometry-format.md` §4, §4.1).

**Immediately after the header, a long run of small, smoothly-ascending 16-bit values** — the same shape already identified as a likely vertex-index buffer in both `.gcmesh_pc` and `.glmesh_pc`. **[HIGH CONFIDENCE — inferred, same value-range-shape evidence as those two formats; this is now a 3rd file family showing the identical "16-byte header, then an ascending-u16-run" shape, which strengthens confidence this is a genuine, deliberate engine convention rather than coincidence.]**

**Update from a follow-up Ghidra pass** (`spec-geometry-format.md` §4.1, prompted by exactly this three-way pattern match): the mechanism was fully traced and confirmed for `.gcmesh_pc` specifically — a real second magic (`0x424BD00D`), a version sub-header, and six independently-sized payload arrays, one of which (2-byte stride, size = a product of two header count fields) is a strong match for the index buffer already spotted here by inspection. **However, that same pass also found `.glmesh_pc` is loaded through demonstrably different code than `.gcmesh_pc`** (a different registered constructor), and **`.gzn_pc`/`.czn_pc` are registered with no dedicated constructor at all** — meaning terrain reaches whatever parses it through a separate, not-yet-traced path *(since traced in part: `spec-zone-data-format.md` §9.1 — a literal NULL constructor — and §9.5's walker, cited in §5 item 2 below)*. **So `.gzn_pc`'s matching black-box shape remains a real, useful clue, but the specific six-array mechanism confirmed for `.gcmesh_pc` should not be assumed to apply here without separately tracing `.czn_pc`/`.gzn_pc`'s own actual code path** — which, given §3's finding that terrain has its own real multi-region structure (`"Region<NNN>"` labels) that the generic mesh loader wouldn't need to know about, seems likely to be genuinely different rather than just an unconfirmed instance of the same thing.
