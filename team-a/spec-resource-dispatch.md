## 1. Overview and headline result

Every one of the ~45 **[exactly 43 registered, IDs 1–45 with 6 and 28 absent — §7 item 0, `spec-format-inventory.md` §1]** resource types in the registration table (`spec-geometry-format.md` §4.3, `FUN_00700780`) has its constructor/destructor function pointers stored into a shared, global, struct-of-arrays **[Corrected 2026-09-30, desk review: an array of structs — one 48-byte row per type, §2]** table (one row per type, indexed by type ID) by the registration consumer (`FUN_00daf4e0`). That table is read by a small, cohesive cluster of generic functions — none of them specific to any one resource type — that together: resolve a resource's on-disk filename(s) from its base name plus the type's registered extension(s), open/load the file(s), and invoke the registered constructor with the results. **This is the literal mechanism by which a `c`-side file's constructor receives its paired `g`-side file's data: the pairing is resolved generically, by simple filename+extension substitution, before the format-specific constructor ever runs — not via any content-based cross-reference read from within the `c`-file itself.** This directly and fully closes the scope boundary hit in `spec-geometry-format.md` §4.1.2 items 7–8.

## 3. Resolving the paired file by name — `FUN_00dd2a70`

This is the actual answer to "how does a `c`-file locate its paired `g`-file." Given a resource descriptor object (built elsewhere, containing at minimum: the resource's base name, its resolved type ID, and the flags byte from §2), and gated on that type's row `+0x10` flag bit `0x4` (the "has a pair" bit): **[⚠ CORRECTED 2026-09-20 — see §8.6 item 2: the "has a pair" test is the per-*entry* flags byte (`+0x15`) bit `0x4`; a set *row* `+0x10` bit `0x4` means "resolve nothing" (ID 39 only).]**

1. Build the **primary** filename by combining the resource's base name with the type's `+0x18` extension string (§2).
2. Resolve/open that file, store the result into the descriptor's own slot 1 (its `[1]`-th field, in 4-byte-element terms).
3. Build the **secondary** filename the same way, using the `+0x20` extension string.
4. Resolve/open that file too, store the result into the descriptor's slot 2 (`[2]`).

- **Convention and caller.** The entry is passed in `ECX` (a this-style call) plus one stack argument, removed by the callee (`RET 4`). The only caller is `FUN_00dd2f50` (`0x00dd30d3`), which always passes `0` for that argument.
- **Gate order (answers OPEN (a)).** First the *row* byte `+0x10` bit `0x04` of the entry's type (entry `+0x14`): if set, the routine returns at once and writes nothing — neither slot is touched. Otherwise the *entry* byte `+0x15` bit `0x04` decides: **clear (unpaired)** → the entry's name string (entry `+0x00`) is looked up **exactly as stored, with no extension appended**, the result goes to entry `+0x04`, and entry `+0x08` is set to `0`; **set (paired)** → steps 1–4 above run (primary into `+0x04`, then secondary into `+0x08`). So steps 1–2 are *not* run for unpaired entries — an unpaired entry's name is used whole.
- **Which extension (new).** The extension is not always `+0x18`/`+0x20`: the code reads entry `+0x18` as a word, sign-extends its low two bits into a small *variant index*, and takes the row field at `+0x18` + 4 × index (primary) and `+0x20` + 4 × index (secondary). The only writer of that 2-bit field seen here, `FUN_00dd22c0`, stores `0` or `1` — so index `0` gives the `+0x18`/`+0x20` pair and index `1` gives the `+0x1C`/`+0x24` pair (§2). (Values 2/3 would sign-extend to −2/−1 and reach `+0x10`/`+0x14`; no writer of those values was seen.) This 2-bit field is where the manifest's `variant_select` ends up (`spec-asm-format.md` §7.4's "low 2 bits at entry `+0x18`").
- **Name composition.** `FUN_00da8790(buffer, 64, base name, extension)` copies the base name into a 64-byte stack buffer, inserts a `.` only if the extension string does not already begin with one, and appends the extension; it reports failure (and leaves the buffer unwritten) if any pointer is null or the result would not fit. `FUN_00dd2a70` ignores that result.
- **What the slots receive (answers OPEN (b)).** Each slot gets the return value of `FUN_00da9670(name, 0, 0)`. That helper asks every registered search location (a global table walked by `FUN_00da8d90`) for the name; on the loose-file kind it queries the file system's attributes for the path and keeps the **file's byte size** (low 32 bits; the lookup counts as failed if the high half is nonzero); it returns that size, or **`0` when no location has the name**. So slots `[1]`/`[2]` = entry `+0x04`/`+0x08` receive **byte sizes**, consistent with §8.6 item 1 — not file objects, handles or buffers. For the other search-location kinds the returned value depends on callees not dumped (`FUN_00da8c80`, `FUN_00da8cf0`); on that path the visible code leaves the size field at its zero initial value — **OPEN** whether those kinds supply a size elsewhere.
- **Failure path (answers OPEN (c)).** No error is raised here: an absent file simply stores `0` into the corresponding size slot, and the caller returns success regardless.
- **Where this sits in the pipeline (new, corrects "resolve/open").** `FUN_00dd2f50` reads one manifest record (name, then four bytes, two `u32`s, one byte — §8.3) and, if it matches an existing entry, **either copies the record's two `u32` sizes into entry `+0x04`/`+0x08` (context byte `+0x10` clear) or, when that context byte is set, calls `FUN_00dd2a70` to take the sizes from the files found by name instead.** So this routine is a size-refresh path, not the step that opens or loads the pair: the buffers the constructor receives come from the backend's handle-resolution call in `FUN_00dd2e30` (§4), fed by handles that the container allocator assigns (`FUN_00db24e0`, which itself composes the primary file name from the base name and the variant-selected `+0x18` extension for paired entries before its allocation call, `0x00db27b5`–`0x00db27c8`). The filename-plus-extension pairing claim of this section stands; "resolve/open … store the result" in steps 2 and 4 is struck in substance by this note.

**This mechanism is completely generic** — it runs identically for any type whose registration row has the "has a pair" flag set, regardless of what the two extensions actually are. **[⚠ CORRECTED 2026-09-20 — see §8.6 item 2: the "has a pair" test is the per-*entry* flags byte (`+0x15`) bit `0x4`; a set *row* `+0x10` bit `0x4` means "resolve nothing" (ID 39 only).]** It does not special-case `.ccmesh_pc`/`.gcmesh_pc`, or read anything from either file's *content* to find the other — the pairing is pure filename convention (same base name, different extension), resolved before any format-specific parsing code runs.

### 8.3 What the code does with them **[CONFIRMED — disassembly]**

- So it is a **start-address alignment**, not a size granularity: sizes themselves are never rounded up; only the offset at which the next block begins is.
