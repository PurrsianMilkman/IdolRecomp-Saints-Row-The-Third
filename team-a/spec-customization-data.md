## 1. Overview: two separate systems, two separate archive families

"Customization data" is really two mostly-independent systems, each with its own definition-table location and its own per-item/per-vehicle asset archive:

- **Vehicle customization** (paint variants, spawnable component/wheel/color options): defined per-vehicle in the `<vehicle_name>.xtbl` file already noted in `spec-vehicle-data.md` §3, cross-referencing a handful of shared, central `vehicle_cust_*.xtbl` tables.
- **Character/item customization** (clothing, accessories, outfits worn by the player and NPCs): defined centrally in `customization_items.xtbl` and `customization_outfits.xtbl`, with per-item mesh/texture/morph assets in dedicated archives.

Both systems share the same reliability story already established for vehicle stats (`spec-vehicle-data.md` §2): **their central base-game definition tables live in `misc_tables.vpp_pc`, a mode-(a) compressed container, at non-first directory positions — `customization_items.xtbl` (index 99 of 1,342), `customization_outfits.xtbl` (102), `customization_slots.xtbl` (103), `customization_slot_defaults.xtbl` (104), and the `vehicle_cust_*` family already indexed in `spec-vehicle-data.md`.** ~~Per the container format's documented, closed-out known limitation, none of these are currently reliably extractable.~~ **RESOLVED 2026-09-24 (Team B; independently re-verified from scratch by SPEC TEAM) — the mode-(a) fix (`spec-vpp-container.md` §7/§8) makes all of these directly readable. See §6.**

**Same workaround as the vehicle-stats pass: the DLC archives (`dlc1/2/3.vpp_pc`) are fully raw/uncompressed, and each one ships its own `dlcN_customization_items.xtbl` and `dlcN_customization_outfits.xtbl`.** **[Location refined by §6: the `dlcN_` tables sit nested inside `str2_pc` bundles within `dlc1/2/3.vpp_pc`, not as top-level archive entries.]** These were used as the real, validated worked examples below. As with vehicle stats, the schema is presumably identical between DLC and base-game content (same table, same consuming engine code) — this resolves "what does the data look like," not "what are the values for every base-game item," which remains blocked **[no longer blocked — §6]**.

## 5. The `custmesh_<N>` bundle-name recipe — RESOLVED (agent AG, 2026-09-20)

**Added 2026-09-20 (agent AG, `gp_cust1`).** Resolves §2.3's and §4 item 3's "hash unidentified". Method: the two literal format strings `custmesh_%d` (VA `0x011776B8`) and `custmesh_%df` (VA `0x01177668`) each have **exactly one code reference**, both inside one function (`FUN_009FD8C0`, 4,854 bytes; references at `0x009FE11D` / `0x009FE65B`), whose only caller is the `Customization_Item` table loader `FUN_00829650` (one call site, `0x00829E6C`). The composer was decompiled in full and its hash/registration callees followed; the recipe was then reproduced against the real archives. Harnesses: `cust_enum.py`, `cust_hash.py`, `cust_reverse.py`, `cust_reverse2.py`, `cust_names.py`; Ghidra scripts `CustDecomp.java`, `CustDisasm.java`; raw dumps `cust_d1.txt`..`cust_d6.txt` (evidence dump, not in repo).

### 5.1 The recipe

`N` is a **32-bit composite key printed as a signed decimal**, built per *(wear option x variant)* of a `Customization_Item` (§2.1) from **two independent 16-bit halves plus an additive small integer**:

```
crc(s)   = table-driven CRC-32 (reflected polynomial 0xEDB88320, initial value 0, NO final XOR)
           over the LOWER-CASED bytes of s, no length limit
hi16     = crc(item.Name)                       & 0xFFFF      (the <Name> element, e.g. "cm_dlc_mask_panda")
lo16     = crc(male_mesh_filename_as_written)   & 0xFFFF      (the <Male_Mesh_Filename><Filename> text
                                                               INCLUDING its extension, e.g. "cm_dlc_mask_panda.cmeshx")
N        = int32( (hi16 << 16 | lo16) + VariantID )           (VariantID = <Mesh_Variant_Info><VariantID>; ordinary
                                                               32-bit add, wraps, then formatted with a signed %d)
male bundle    = "custmesh_" N        ".str2_pc"
female bundle  = "custmesh_" N "f"    ".str2_pc"     (only when the wear option has a <Female_Mesh_Filename>)
```

- **The hash is the engine's general-purpose name CRC-32, not a new function.** It is `FUN_00D9E8B0` (the routine documented as the ~835-call-site general name hash; lower-cases each byte, then the standard byte-wise reflected-CRC step with the seed passed by the caller — here 0 — and a caller-supplied length cap, here unlimited).
