# Saints Row: The Third — `.vpp_pc` / `.str2_pc` Container Format Specification

**Prepared by:** SPEC TEAM (cleanroom reverse-engineering process)
**Phase:** 1, Target #1 (from `spec-output.md` §4 (unpublished Team A working document, not in this repository))
**Scope:** A complete, implementation-ready description of the `.vpp_pc` archive container and its nested `.str2_pc` sub-package format: header, directory, filename table, compression, and alignment rules.
**Method across all passes:** (a) targeted static disassembly — first manual (Capstone/x86, no decompiler), later a real decompiler and cross-reference database (Ghidra, self-hosted locally specifically to get past a manual-disassembly dead end on the compression-mode question, §3.3) — of `SaintsRowTheThird.exe`, around the code that validates the archive's magic/version, walks its directory table, hashes filenames, and computes per-entry positions; and (b) black-box empirical verification — brute-force locating and successfully decompressing real zlib streams inside real shipped archive files, and cross-checking every proposed field/formula against ground truth (actual file sizes, actual entry counts, `patch_compressed.vpp_pc` vs `patch_uncompressed.vpp_pc`, naturally-occurring nested container headers found byte-for-byte inside larger archives, and a small non-deliverable verification parser built from the confirmed fields and run against 6 archives ranging from 2 to 110 directory entries, including a large sample specifically chosen to stress-test assumptions that looked solid on small samples but weren't). All research tooling — the verification parser and the Ghidra project/scripts alike — was kept in a `tools/` subfolder separate from this and the other spec documents, and none of it is itself a deliverable, in line with the cleanroom rule against producing implementation artifacts: everything below is the *description* of what that tooling showed, in our own words, never the tool output itself.
**Cleanroom compliance:** No disassembly listings, decompiled code, or original identifiers/comments/paths appear below. Struct field offsets, sizes, and the container magic number are exact literals (load-bearing format data) and are stated freely per the ground rules. Every field below is labeled with a confidence level and the evidence behind it; nothing is presented as certain that wasn't actually verified.

**Confidence key:**
- **[CONFIRMED — disassembly]**: directly observed in the code that reads/validates this field.
- **[CONFIRMED — empirical]**: directly and repeatedly verified against real file bytes (not just theorized).
- **[HIGH CONFIDENCE — inferred]**: consistent, unforced numeric match across multiple independent samples, but not traced in code.
- **[HYPOTHESIS — unconfirmed]**: a plausible reading that fit some samples but not others, or wasn't independently checked. Flagged explicitly; do not treat as fact.
- **[OPEN / UNKNOWN]**: not determined in this pass.

## 1. Fixed Header Layout (offsets `0x000`–`0x17F`)

All offsets below are relative to the start of the container (for a top-level `.vpp_pc` this is byte 0 of the file; for a nested `.str2_pc`, this is the start of that sub-package's own data — see §5). All multi-byte integers are **little-endian**, 32-bit unsigned unless noted.

| Offset | Size | Field | Confidence | Evidence |
|---|---|---|---|---|
| `0x000` | 4 | **Magic number**, exact value **`0x51890ACE`** (on-disk bytes `CE 0A 89 51`) | **CONFIRMED — disassembly + empirical.** *Exact literal required by the format.* | The loader compares the first 4 bytes of every opened container against this exact constant and rejects the file if it doesn't match. Verified present, identical, at this offset in all 37 sampled `.vpp_pc` files and in 15 naturally-occurring nested sub-containers found inside one of them (see §5). |
| `0x004` | 4 | **Format version.** Loader accepts the range **5–6 inclusive**; every file sampled in this install reads **6**. | **CONFIRMED — disassembly.** | The validation code rejects the file if this value is below 5 or above 6, immediately after the magic check. Only version 6 was observed on disk, so version-5 behavior (if it differs at all) is untested. |
| `0x008`–`0x14B` | 324 bytes | **Not meaningful on disk.** Always zero in every sampled file. | **CONFIRMED — disassembly + empirical.** | The loader bulk-copies the first 380 (`0x17C`) bytes of the on-disk header directly into its in-memory handle structure, then **immediately overwrites** the region corresponding to this byte range with a caller-supplied filesystem path string (not data that came from the file). This explains why the region is reliably zero on disk in every sample: it's reserved space in the in-memory structure for a runtime-only field, not a serialized on-disk value. Matches the actual number of filenames found in every sample (2, 16, 17, 110, 1342, etc. all matched exactly). |
| `0x158` | 4 | **Total container size in bytes** (size of the whole `.vpp_pc`/`.str2_pc` file/blob, header included). | **HIGH CONFIDENCE — inferred (empirical, exact match, 8/8 samples).** | Matched the real on-disk file size exactly in every one of 8 independently checked archives, from 8,212 bytes up to 5,343,916 bytes, with zero exceptions. | `0x15C` | 4 | **Directory table size in bytes** = entry_count × 24. | **CONFIRMED — disassembly (entry stride) + empirical (size match, 3/3 samples cross-checked, including one nested sub-container).** | See §2 for the entry stride confirmation. | `0x16C`–`0x17B` | up to 16 bytes | Zero-initialized by the loader at open time (not read from the file). | **CONFIRMED — disassembly.** | Explicitly zeroed by the same validation routine that checks the magic/version, immediately after loading. These are runtime bookkeeping fields (e.g., pointers/offsets resolved later once the directory and filename table are actually loaded into memory), not on-disk data. |

### 1.1 Fixed-size reserved regions — corrected and generalized this pass

Every region after the fixed `0x180`-byte header is **block-quantized to 2,048 (`0x800`) bytes, chained one after another**, where each region's reserved size is its own real content size rounded up to the next `0x800` boundary. **[CONFIRMED — empirical, exact match on every field/offset cross-checked across 6 archives, including a 110-entry one that exposed a bug in our own earlier assumption below.]**

```
dir_base      = container_base + 0x800
name_base     = dir_base + round_up(dir_size, 0x800)          [dir_size = header field @0x15C]
payload_start = name_base + round_up(name_table_size, 0x800)  [name_table_size = header field @0x160]
```

Concretely:
- Bytes `0x000`–`0x7FF` (2,048 bytes): the fixed header (only the first `0x180` bytes carry defined fields; the rest is unused padding).
- `dir_base` (`0x800`) onward: the **directory table** (§2), reserved for `round_up(entry_count × 24, 0x800)` bytes.
- `name_base` onward: the **filename table** (§2.1), reserved for `round_up(name_table_size, 0x800)` bytes.
- `payload_start` onward: entry payload data (§2, §3).

**Correction from an earlier draft of this document:** we previously stated the filename table always starts at a fixed offset `0x1000`. That is only true when the directory table is small enough to fit in one `0x800` block (≤ 85 entries) — it happens to hold for every small sample checked in the first pass, which is why it went unnoticed. It breaks on larger archives: a 110-entry sample (`dir_size = 0xA50`, i.e. 2,640 bytes, bigger than one 2,048-byte block) has its filename table starting at `0x1800`, not `0x1000`. **The general chained formula above is what an implementation should use; do not hard-code `0x1000`.** This was caught precisely because we tested against a large real archive rather than only the small ones from the first pass — a useful reminder to keep doing that.

The `payload_start` formula above is now **directly confirmed** (not just a guess) via the exact match against header field `0x168` (see the corrected row above) across 5 independent samples of varying size, including nested and doubly-nested containers.

## 2. Directory (Table-of-Contents) Entry Structure — fully resolved this pass

- **Location:** starts at `dir_base` (`container_base + 0x800`; see the corrected §1.1).
- **Stride: exactly 24 (`0x18`) bytes per entry.** **[CONFIRMED — disassembly + empirical, now cross-checked on 100+ real entries across 5 archives with zero exceptions.]**

### 2.1 Filename Table

- **Location:** starts at `name_base` (§1.1 — **not** a fixed offset; corrected this pass, see above).
- **Format:** back-to-back, individually **null-terminated ASCII strings**, one per directory entry, in no confirmed particular order relative to the directory table (each directory entry finds its name via the explicit offset field described above, not by position/index).
- **Size:** exactly `name_table_size` bytes (header offset `0x160`), which is the sum of every name's length-plus-terminator with no extra padding between strings. **[HIGH CONFIDENCE — inferred, see §1 evidence.]**
- Filenames observed in this table always carry their full sub-format extension (e.g. `decal_bullet_wood.str2_pc`, `achievements.xtbl`, `decal_containers.cpeg_pc`) — the table is effectively a manifest of "what this container logically holds," independent of how that data is physically packed/compressed.

### 2.2 Filename Hash (used for runtime lookup)

**Reuse found later (2026-09-10):** this exact algorithm, applied to the **lowercased** input, is also how `.rig_pc` stores a per-bone name hash — it reproduces **22,274 / 22,274** shipped bone-hash entries (and **0 / 22,274** for uppercased input). It is a **widely-reused string hash**, not a container-specific one. **Correction (2026-09-10, `.ctdg_pc` pass): the "a reimplementation needs exactly one" that this sentence used to end with was wrong.** **Breadth correction (2026-09-10, `spec-extensionless-types.md` §4): calling this hash "engine-wide" was backwards.** A call-site census gives ≈18 for this rotate-6/XOR routine, ≈174 for the multiply-33 bucket hash, and **≈835 for the table-driven CRC-32** — which this project first met as one format's registry key and which is in fact the engine's general-purpose name hash. This routine's documented uses (archive filenames, rig bone names, the foliage registry, conversation speaker ids) are close to its *complete* set of uses. Prefer naming the uses over the word "engine-wide". With that said, the engine has at least **three** string hashes (a third — multiply-33/XOR taken modulo a bucket count — was found in 2026-09-10's type-18 pass, `spec-texture-format.md` §8.2; unlike the two below it produces a bucket index rather than a name key): this rotate-6/XOR one, and a **table-driven CRC-32 over the lowercased string** (`FUN_00d9e8b0`) used for the mission-conversation registry key. `.ctdg_pc` uses *both* — CRC-32 for its registry key, rotate-6/XOR for the speaker ids inside the file — so a 32-bit name hash in an unfamiliar structure must not be assumed to be this one. See `spec-conversation-format.md` §6. See `spec-rig-format.md` §5. **Confirmed by disassembly (2026-09-10, foliage pass):** the routine at `FUN_00da7890` — which the `.cfmesh_pc` constructor calls to key its mesh registry — is exactly this loop, including the explicit `A–Z` → lowercase fold before the rotate/XOR. The pseudo-code below is now **[CONFIRMED — disassembly]**, no longer inferred from behaviour alone.

The engine does not do straightforward linear string comparison to find files by name at runtime; it computes a hash of the filename and uses that for lookup in an in-memory table. **[CONFIRMED — disassembly.]** The exact algorithm (reconstructed from the code's logic, expressed here in our own words/pseudocode, not copied from the binary):

```
hash = 0
for each character c in the filename (until the null terminator):
    if c is an uppercase ASCII letter ('A'-'Z'):
        c = lowercase(c)
    hash = rotate_left_32(hash, 6)
    hash = hash XOR c
return hash
```

This is a simple, case-insensitive, rotate-and-XOR string hash (not a standard named algorithm like CRC32 — it is small, custom, and cheap to compute). **Whether the on-disk directory entry also stores a precomputed copy of this hash (common in this class of format, to avoid needing the plaintext name table at all for fast lookups) was not confirmed** — the disassembly traced showed the hash being computed from the plaintext name at load time, not read directly from an entry field, but this doesn't rule out a stored hash existing elsewhere. Flagged as open (§6).

## 3. Payload Compression Scheme

**The codec is standard zlib (RFC 1950 zlib-wrapped DEFLATE). This is a publicly documented, public-domain-license algorithm — naming it is a fact, not proprietary expression.**

Evidence, at two independent levels:

1. **String-level:** the executable contains zlib's own public version-banner strings identifying it as **zlib 1.2.1** (the same banner text zlib itself prints/embeds in any build — these are the library's own public self-identification strings, not Volition code).
2. **Empirical, worked example:** in `sr3_city_missions.vpp_pc`, brute-force scanning for a valid two-byte zlib stream header followed by a successful decompression found a genuine zlib stream at file offset `0x8000`. Decompressing it with a stock zlib implementation (no special framing, no custom pre/post-processing needed) produced well-formed, human-readable data beginning with literal `<root>` / `<Table>` XML-style markup and text visibly matching one of the archive's known nested asset names (a `*_globals.xtbl` file referenced elsewhere in the same archive). The Adler-32 trailer checksum that RFC 1950 requires was implicitly validated as correct by the decompressor (a bad checksum would have raised an error). A second, much smaller worked example in `startup.vpp_pc` (a 20-byte compressed chunk decompressing cleanly to a 48-byte repeating pattern, consistent with a tiny placeholder texture) confirmed the same thing at much smaller scale, with a fully-consumed stream (no error) end to end.

### 3.1 Per-entry compression signal — resolved this pass

**The archive-level flags field (§1, offset `0x14C`) is not what signals compression — it's genuinely per-entry, and it's signaled by directory entry field `+0x10` (§2):**

- `+0x10 == 0xFFFFFFFF` → this entry's data is stored **raw**, and its byte length is field `+0x0C`.
- `+0x10 == <real value>` → this entry's data is **zlib-compressed**, decompressing to `+0x0C` bytes, and (for most entries — see 3.2) the compressed bytes on disk number `+0x10`.

This was confirmed by checking dozens of real entries across both fully-raw archives (every entry showed the `0xFFFFFFFF` sentinel, and reading raw bytes at the computed offset does show, e.g., a nested container's plain-text-visible magic number) and mixed/compressed archives (entries with a real `+0x10` value reliably decompress via zlib to exactly `+0x0C` bytes). This also explains, retroactively, why the archive-level flags field looked unreliable in the first pass: it isn't the real signal at all, and never was — the real signal was in the directory entry the whole time.

### 3.2 Compression grouping — genuinely mixed, and only partially resolved; flagged honestly

**RESOLVED 2026-09-20 (§7): non-first entries of a bit-`0x1` mode-(a) container are located by the physical-offset rule `payload_start + Σ round_up(size_j, 0x800)` over earlier entries (`size_j` = `+0x10`, or `+0x0C` if raw) — verified 3,263/3,263.** Everything below in §3.2–§3.8 about failed decodes, "silent corruption" and dictionary priming is explained by that single mistake (reading at `+0x08`); it is kept as history.

Two different arrangements were directly observed, and we could **not** fully unify them into one rule in this pass:

**(a) Independent per-entry streams.** In the simplest cases (a 2-entry archive, a 1-entry nested container, and the clear majority of entries in a large 110-entry archive), each compressed entry is its own **complete, independently-decodable zlib stream** starting exactly at `payload_start + data_off`: reading it with a stock zlib decompressor, using either the entry's own `+0x10` byte count or just letting the stream self-terminate, produces exactly `+0x0C` bytes of correct, sensible output (readable XML for `.xtbl` entries, plausible texture/palette bytes for others) every time. This is the model described in §2 above and it is solid.

**(b) One shared stream spanning multiple entries.** In one directly-confirmed case — a nested `.str2_pc` (found inside `sr3_city_missions.vpp_pc`, itself found inside a doubly-nested lookup) containing 2 entries — the **second** entry's data does *not* start with its own zlib header at its `payload_start + data_off` position. Instead, decompressing the **first** entry's stream *without* stopping at its own declared `+0x0C` length continues to produce more valid output, and the second entry's declared `data_off` (31,474) lands exactly on the boundary between the first entry's uncompressed length (31,474 bytes) and where the second entry's uncompressed content logically begins. In other words: for this container, `data_off` and `+0x0C` describe a byte range in a single shared **decompressed** buffer, not independent physical compressed streams — the whole container's payload was compressed once, as one stream, covering both entries. Strong corroborating evidence: the *sum* of both entries' `+0x10` values (4,228 + 1,797 = 6,025) exactly equals this container's own header-level `0x168` field (6,025) — consistent with `+0x10` being retained per-entry mainly as bookkeeping (so the sum reconstructs the container total) rather than as an independent stream boundary in this mode.

**What determines (a) vs. (b)? Now resolved — see §3.3 for the full derivation.** **Flags bit `0x2` (§1, offset `0x14C`) is the mode switch: clear = mode (a), set = mode (b).** This was found by decompiling the specific loader routine that computes per-entry positions at container-open time (via Ghidra, not manual disassembly — see §3.3) and is not a guess from correlation: the routine in question is *only executed at all* when bit `0x2` is clear, and its entire purpose is to walk the directory computing independent per-entry positions — which is exactly mode (a). When bit `0x2` is set, that routine is skipped outright, which is consistent with (and explains) mode (b): there's nothing for the loader to compute per-entry, because the entries don't have independent physical positions to compute. Checked against every flags value in this document with zero exceptions: `startup.vpp_pc` and `da_tables.vpp_pc` (`0x4801`, bit clear) are confirmed mode (a); the `Running Man.str2_pc` nested container (`0x4803`, bit **set**) is confirmed mode (b); `sr3_city_missions.vpp_pc`'s own top-level entries (`0x0`, bit clear, all raw) are consistent with mode (a) trivially (raw entries don't distinguish (a) from (b) either way, but the bit still predicts the loader's behavior correctly).

**Independent, black-box structural detector — confirmed 2/2, no counterexamples yet.** Separately from trying to find the *cause*, a second team working from this document independently tested real archive files (not code — just the game's own shipped data, which is a legitimate thing to test a from-spec implementation against) and found a reliable-so-far **symptom-level heuristic** for detecting mode (b) purely from the directory data itself, without needing to know why it happens: *when a container's second entry's `data_off` (§2, entry `+0x08`) exactly equals the first entry's uncompressed size (`+0x0C`), that container is using mode (b) (a single shared stream), and the same reasoning extends entry-by-entry (each entry's `data_off` equals the running sum of every prior entry's `+0x0C`).* This was independently confirmed on a second real example — `Horde Mode.str2_pc` (in the same `sr3_city_missions.vpp_pc` archive as the original `Running Man.str2_pc` case) — showing the identical signature: exact match, no adjustment needed. That makes it 2 real, independently-found examples with zero counterexamples so far. **This is a practical, implementable detection rule on its own, independent of whatever the underlying flag/field turns out to be** — an implementation can check this pattern directly on the directory table rather than waiting on the code-level answer. It does not explain *why* (so it may not generalize to every edge case, and a future counterexample would need to be folded back in), but it is real, tested, working, black-box evidence and is fair game to rely on provisionally.

**A separate, still-unresolved anomaly (do not paper over) — confirmed independent of the mode-(a)/(b) switch above, and CONFIRMED THIS PASS TO BE MUCH MORE SEVERE THAN FIRST CHARACTERIZED.** The original description below (kept for the record) understated the problem — see the correction immediately after it.

*Original characterization:* In the 110-entry archive used to validate mode (a), a real minority of entries (roughly a third of a ~30-entry sample manually checked) — despite having `data_off` values that are independently, arithmetically confirmed correct (their gaps from neighboring entries match `round_up(+0x0C, 0x800)` exactly) — either don't produce a valid-looking zlib header at their computed position at all, or produce one that fails partway through decompression with a stream-corruption error, even when given a very generous read window.

**Correction, from the `.xtbl`-format pass (`spec-xtbl-format.md` §1):** that original check only verified "did decompression throw an error" and "does the output byte count match" — it did not verify the *content* was actually correct. Testing against real files with actual content validation (well-formed-XML checking on real `.xtbl` samples) revealed that passing those two checks is **not sufficient**: **only a mode-(a) container's very first entry (index 0) was found to decode to genuinely correct content.** Every other entry either throws an exception, or — this is the important new finding — "succeeds" by both prior checks (no exception, correct byte count) while actually being **silently corrupted** (confirmed via real samples that were truncated mid-tag despite matching their declared length exactly). So the true affected fraction in a typical multi-entry mode-(a) container is not "a minority" — it's **every entry except the first**, unless proven otherwise for a given entry. Mode (b) containers do not have this problem (confirmed: decoded content from a non-first entry of a mode-(b) container was independently verified correct this pass).

**What was additionally ruled out this pass** (on top of what was already ruled out — see the original open-items list): concatenating each entry's own declared compressed-byte range, in order, into one virtual stream and decoding that continuously does **not** work either — it fails at the exact same byte position as decoding the second entry in isolation would. Combined with the earlier finding that simply reading further past an entry's own declared boundary also fails, this rules out both of the simplest "maybe it's actually one continuous thing" theories. **This strongly, but not conclusively, points at a missing preset compression dictionary or other decoder state that the container's own fields don't expose** — but this is a hypothesis about the likely *shape* of the missing mechanism, not a confirmed finding about what it actually is.

Now that entry `+0x04`'s exact meaning is also known (it's a loader-internal scratch value, not a flag — see the `+0x04` row in §2), it's confirmed to be zero for both failing and succeeding entries alike, so it isn't hiding a per-entry signal either. **We still do not have an explanation for the missing mechanism and are not going to guess further at what it is without more tracing.** This does not appear to invalidate the offset/size field identifications themselves (entry 0 decodes perfectly using exactly those fields, every time), but **an implementation relying on mode (a) as described should currently assume only a container's first entry is reliably extractable, not "most" entries** — this is a substantially stronger caveat than this document previously gave, and anything already built against the earlier, milder characterization should be re-checked.

**Exact compressed-length delimiting for mode (a):** with `+0x10` now confirmed as the field to use, this is otherwise resolved for the entries that do work — no more reliance on "let the decompressor find its own end."

### 3.3 How the mode-(a)-vs-(b) question was actually resolved

This pass used Ghidra (with its decompiler and a real cross-reference database, imported and auto-analyzed locally) rather than manual disassembly, specifically because a prior pass's manual/blind approach had hit diminishing returns on this exact question. The difference mattered: several leads below were only feasible to check *because* real decompiled pseudocode and reliable "find all references to X" queries were available.

**Architecture confirmation (third independent code path).** Before finding the switch itself, this pass traced the code path for **looking up a specific named entry** on demand (as opposed to the bulk directory-registration loop already described in §2): a linear, case-insensitive, name-string search across every mounted container's directory (walking `+0x154` entry count and `+0x16C` directory-table-base exactly as described in §1/§2 — a third independent confirmation of both fields, distinct from the magic/version validator and the bulk registration loop already documented). This search function itself turned out to be a plain existence check; the actual "give me this entry's data" caller sits one level up and, on success, copies the entry's `+0x0C` (uncompressed size) into its own result structure — a fourth independent confirmation of that field, via yet another code path.

**One lead actively ruled out, not just left unresolved:** this pass found a real, previously-undocumented 4-bit sub-field inside the archive-level flags word: `(flags >> 11) & 0xF`. Code exists that extracts exactly this sub-field and, when its value is `10` or `11`, triggers a least-recently-used cache-eviction routine (unloading the oldest currently-open container to make room) before proceeding with an open. This looked, at first, like a promising candidate for the mode switch — but every real archive flags value observed in this document produces either `9` or `0` for this sub-field, never `10` or `11`, and both a confirmed mode-(a) archive and the confirmed mode-(b) container produce the *same* value (`9`) here — so this sub-field cannot be what's distinguishing them. **Confirmed real** (it does gate an LRU-eviction code path) **but unrelated** — a resource-caching/streaming-budget mechanism, not the compression-mode switch. Recorded here so a future pass doesn't waste time re-deriving and re-testing the same dead end.

**The actual answer.** Container registration (§2's directory-registration loop) unconditionally calls one helper that resolves each entry's on-disk name-table offset into a real in-memory pointer (confirming the `+0x00`/name-offset field's exact behavior precisely, including that the on-disk sentinel `0xFFFFFFFF` means "no name" — folded into §2's field table above), then **conditionally** calls a second helper — only when flags bit `0x2` is clear. That second helper is the mode-(a)-vs-(b) switch itself: it walks every directory entry computing a running position (in units of 2,048-byte blocks, starting from the block count occupied by the header/directory/name-table regions) and writes that position into entry field `+0x04`, choosing `+0x0C` (uncompressed size) or `+0x10` (compressed size) to accumulate depending on flags bit `0x1`. **This is only meaningful, and only runs at all, for the independent-per-entry-stream case (mode (a)).** For mode (b) (flags bit `0x2` set), this computation is skipped entirely — consistent with, and explaining, why mode (b) has no independent per-entry physical positions to compute in the first place.

**An important nuance this also surfaced, folded into the `+0x04` row in §2:** the value this loader routine computes and writes to `+0x04` is a genuinely different computation from the real, authoritative `+0x08` field already documented — they can diverge (confirmed: they do diverge on `da_tables.vpp_pc`, where flags bit `0x1` is set, so the loader's `+0x04` accumulates using `+0x10`, while the real on-disk `+0x08` spacing — built by whatever tool packs these archives — always uses `+0x0C` regardless of that bit). No code was found anywhere in the binary reading `+0x04` back out for seeking purposes; it appears to be a write-only value used for something else (plausibly a memory/IO budget estimate). **This does not weaken the mode-(a)/(b) finding** — that rests on whether the routine runs at all, gated by bit `0x2`, not on the specific arithmetic it performs once running — but it's an important warning against assuming `+0x04` is a second, equally-valid way to compute an entry's position: it isn't, and ~~`+0x08` remains the only field an implementation should use for that.~~ **[Retracted 2026-09-20, §7: the `+0x04` accumulation IS the physical stream position in a bit-`0x1` container; `+0x08` is the logical offset.]**

This does **not** explain the separate decode-failure anomaly documented above (§3.2) — that remains genuinely open, and is confirmed to be a distinct problem from the mode switch (the affected archive is unambiguously mode (a) by the now-confirmed test).

### 3.5 Further tracing of the decode-failure anomaly (§3.2) — real progress, root cause still not pinned down

A dedicated further pass, prompted by the `.xtbl`-format work revealing the anomaly's true scope (only a container's first entry reliably decodes, not "most" entries — see `spec-xtbl-format.md` §1), traced this considerably further using Ghidra's RTTI/vtable resolution. This section records genuine, code-confirmed progress, and is explicit about exactly where the trail was lost.

**The engine's zlib wrapper class was located and its core method identified**, via the standard MSVC RTTI chain (the type-descriptor string for this wrapper class → its Complete Object Locator structure(s) → the vtable(s) that reference each locator → the function pointers stored in each vtable). One of that class's virtual methods is unambiguously a "feed compressed input, get decompressed output" operation: it takes an input pointer/length and an output buffer/length, and — critically — **calls the underlying decompression primitive with an explicit flush-mode value of `2`**. **[CONFIRMED — disassembly.]**

**Correction, found in a follow-up trace (§3.6): the single code location anywhere in the binary that constructs an object of this exact class was found and checked, and every one of its own callers (11 total) is unrelated to archive loading** — they're DXT texture-index compression tooling and one engine-startup self-test. This specific class is confirmed to be a real, general-purpose zlib wrapper used *somewhere* in the engine, and the `Z_SYNC_FLUSH` finding immediately below is still a real, valid fact about *this* class's behavior — but it is **not confirmed to be the class the archive loader uses**. Given how directly it exposes `Z_SYNC_FLUSH` (and how well that matched the sync-flush marker bytes found by inspection), it's plausible the archive loader uses either this same class through a code path not yet found, or a separate instance of essentially the same technique — but this pass could not confirm which. Treat the `Z_SYNC_FLUSH`/sync-flush-marker connection below as strong circumstantial evidence for the *mechanism* at play in the file format, not as proof this *specific* class is the one implementing it for archives.

That value is the well-known, public, standard value for `Z_SYNC_FLUSH` in zlib's own published API (this is a fact about the public zlib API, not proprietary information — naming it is no different from naming the codec itself in §3). This is a real, meaningful confirmation, not a coincidence: **`Z_SYNC_FLUSH` is exactly the mechanism that produces the specific 4-byte marker (`00 00 FF FF`, an empty "stored" deflate block used purely to reach a byte boundary) that this investigation found, by direct byte inspection, sitting at the exact end of a first entry's declared compressed-byte range** — described only as "sync-flush marker" in §3.2's prior write-up, before this pass tied it to a specific, confirmed engine code path. This confirms the entries genuinely are produced by one ongoing compression session with byte-aligned resume points between them, rather than fully independent per-entry streams — the packer keeps the compression window/history alive across entries deliberately, almost certainly for a better overall compression ratio across many small, structurally similar files (exactly the kind of content `.xtbl` tables are).

**Where this still falls short of a fix:** confirming *that* the mechanism is a shared, ongoing compression session doesn't by itself tell you how to correctly resume decoding at entry N without having decoded entries `0..N-1` first through the same, never-reset decompressor object. Several concrete reconstructions of "what a from-scratch decoder would need to do instead" were tried and **ruled out** this pass:
- Skipping a small fixed number of bytes (tested 0 through 16) at the start of the *next* entry's declared compressed range, while continuing the *same* decompressor object seeded with the first entry's output — produces a different low-level deflate error at nearly every skip amount tried, none of them valid.
- Priming a fresh decompressor for the second entry with the first entry's **decompressed** output as an explicit preset dictionary (the standard `deflateSetDictionary`/`inflateSetDictionary` technique, tested in both raw-deflate and zlib-wrapped framing) — fails identically to not using a dictionary at all.
- (From the prior pass) Simply concatenating each entry's own declared compressed-byte range into one virtual stream and decoding that continuously — fails at the exact same byte position as decoding the second entry in total isolation would.
- **(New, and this one changed the model in a real way even though the fix attempt still failed)** `+0x08` was confirmed, definitively, to be a **logical offset into the fully-decompressed output — not a physical file offset — for mode (a) too, exactly like mode (b)**: a real sample (`cutscene_tables.vpp_pc`) has a second entry whose `+0x08` value (1,443,840) is larger than the *entire container file* (791,049 bytes), which is only possible if that value was never meant to be added to a physical file position in the first place. It equals `round_up(the first entry's +0x0C, 0x800)` exactly — i.e. mode (a)'s logical layout is block-padded the same way physical layout is elsewhere in this format, whereas mode (b)'s logical layout (§3.2) has no such padding between entries. Given this, decoding the whole payload as one continuous stream from the true start with no per-entry input slicing at all, and cutting entries out of the *output* purely by their (now-understood-as-logical) `+0x08`/`+0x0C` values, was tested directly and precisely (byte-by-byte input feeding, to rule out chunking artifacts) — **it still fails at the identical point**: the first entry's own data decodes perfectly to its exact declared length, and the compressed bytes immediately following do not form a valid continuation, with or without small skip offsets (0–9 bytes tried). So the *positioning semantics* of `+0x08` are now solidly corrected (this is real, useful progress — see the field's description in §2, which should be read alongside this note), but this still doesn't hand over a working decode recipe: whatever determines where entry 2's compressed bits actually live is still not the physical byte immediately following entry 1's own compressed range, even though the two entries share one continuous decompression session.

**What was not found:** the actual call site that reads and decompresses a *specific, individually-requested, non-first* leaf entry. The confirmed decompress method is a virtual method reached through the class's vtable, and locating *its* callers requires finding indirect calls of the form "call through this vtable's slot for this method" rather than a direct, named call — a systematic scan for that exact call shape across the whole binary found only 14 occurrences, and every one of them belongs to an unrelated class using the same vtable slot index for a different purpose (a C runtime string-formatting internal, a couple of small Windows API utility functions, and an unrelated animation-curve-sampling routine) — none are archive-related. **This means the real caller either uses a call-instruction shape this scan didn't cover (e.g. a computed/indexed vtable offset rather than a fixed one), or the whole-container-at-once theory below is closer to correct than a per-entry-random-access model.**

**An alternative theory worth naming, and already partly (not fully) tested:** it's plausible that mode-(a) containers are never actually meant to support true random-access decoding of an arbitrary entry in isolation at all — that the engine simply decompresses a container's entries **in file order, in one pass, through one persistent decompressor, at the point the container is opened**, and that `+0x08`/`+0x0C`/`+0x10` exist to let the engine know where each entry's data ends up *after* that one sequential pass, not to support seeking into the compressed stream directly for a single arbitrary entry. **The two most obvious versions of this were already tried, in the prior pass and this one, and both failed identically**: decoding the whole payload region's raw file bytes continuously (padding gaps and all) fails at the same byte position as isolating the second entry does, and so does concatenating each entry's own declared compressed-byte range with the gaps removed (bullet three, above). So if a sequential/never-reset model is right, **the correct byte accounting for where one entry's compressed data ends and the next begins is neither "the file's raw layout" nor "the sum of the declared `+0x10` values"** — something else determines it, and that's still unknown. This keeps the theory's general shape plausible while being honest that the two cheapest ways of testing it are already exhausted. **[HYPOTHESIS — the general shape is plausible; two concrete instantiations of it are already ruled out; not tested end-to-end because the correct byte accounting isn't known.]**

### 3.6 One more pass: found the real per-resource "open for reading" function, confirmed mode (b)'s eager decode, still short of a full fix

A further, final pass for this investigation (before stepping back to other work, per team decision) took a genuinely different approach from the vtable-call-shape scan in §3.5: rather than searching blind for a call *shape*, it walked forward from code already fully understood (the directory-registration routine, and the container-open function that calls it) to see whether *they themselves* ever trigger decompression, and separately traced one specific, real lead that fell out of that walk.

**The registration routine and its two direct callees do not decompress anything.** The full bodies of the directory-registration loop and the two small helpers it calls (name-pointer resolution, and the mode-(a)-only position bookkeeping described in §3.3) were already fully known from earlier passes; re-reading them specifically for any decompression call confirms there is none — they're pure pointer arithmetic and bookkeeping. **[CONFIRMED — disassembly, re-verified.]** This rules out "decoding happens synchronously, inline, inside registration itself."

**Mode (b) *is* confirmed to be eagerly, wholly decoded right at container-open time — this is new, solid, code-level confirmation of something that was previously only an inference from mode (b) always working.** A function that runs immediately after a successful container-open (called from two places — a general "open by path" helper, and the per-resource-open function described next) contains a branch that fires **only when flags bit `0x2` (the mode-(b) bit, §3.3) is set**, and that branch performs what is unmistakably a bulk read-and-decompress step, ending in a call chain that ultimately reaches the exact same fields (`+0x164`/`+0x168`) already known to be runtime-only I/O bookkeeping. **[CONFIRMED — disassembly.]** The equivalent code path for mode (a) (flags bit `0x2` clear) does **not** exist — mode-(a) containers get no such eager, whole-container treatment anywhere in the container-open code already traced. This is a meaningful, positive result on its own: it confirms mode-(a) entries genuinely are meant to be read on demand, individually, rather than all at once — so the missing piece really is a distinct, still-unlocated "read and decompress this one specific entry" function, not a byte-accounting error in an already-found eager-decode path.

**A real, concrete per-resource "open for reading" function was found and traced as far as the decompiler could reliably follow.** Unlike everything traced so far, this one is called from ordinary game code (not from within the archive-loading subsystem itself), making it a strong candidate for the actual public entry point game systems use to request a named resource. It resolves/opens the underlying container, performs an initial small read using the same `+0x164` field used elsewhere, and then explicitly branches on the same "is this compressed" flag bit already established (§3.1): the uncompressed branch calls one function directly; the compressed branch first reads a small "streaming mode" value (the same `(flags>>11)&0xF` sub-field already identified and ruled out as the mode-(a)/(b) switch in §3.3 — confirmed here to have a real, different purpose: it's read again in this unrelated context, reinforcing that it's a general streaming-mode/priority tag, not specific to the compression-mode question) and then calls into a **generic, pluggable "pull N bytes from a backing store" abstraction** that tracks a read position against a total size in a small state structure, and dispatches to one of three interchangeable backend implementations depending on a type tag in that same structure — clearly a general I/O abstraction used well beyond just this one archive format, not something archive-specific. **[CONFIRMED — disassembly, through this point.]**

**Where the trail was lost, honestly:** the exact value passed as that abstraction's state-structure pointer, for this specific compressed-entry-read call, decompiled as a literal `0` (a null pointer) — which cannot be right for a function that immediately reads fields out of it with no null check, so this is either a real decompiler inaccuracy at this specific call (parameter/register mis-attribution across the several thin wrapper layers involved), or a sign that this particular call site isn't the one actually used for archive entries at runtime (e.g. a shared code path also used for a case that doesn't reach here in practice) and the real archive-entry route runs through the "backend type 0/1/2" abstraction some other way. Either possibility would need lower-level, instruction-by-instruction register tracing through several layers of thin wrapper functions to resolve — a substantially bigger effort than anything else attempted this pass, and the point at which the team decided to stop rather than continue.

**Overall assessment after three separate deep-tracing attempts across two passes:** the general *shape* of the mechanism is now well understood (one ongoing, `Z_SYNC_FLUSH`-using compression session per mode-(a) container; a generic pluggable backend abstraction for actually pulling bytes; mode (b) confirmed eager, mode (a) confirmed on-demand) — but the precise, implementable algorithm for correctly decoding a specific non-first mode-(a) entry was not recovered. This is being closed out as a documented known limitation rather than pursued further with the same static-analysis toolkit; the natural next step, if picked up again, is either instruction-level register tracing through the specific thin-wrapper chain identified above, or dynamic analysis (attaching a debugger to the running game and observing an actual non-first-entry read) rather than more static decompilation.

### 3.7 First dynamic-analysis pass: the traced I/O abstraction confirmed real, but ruled out for gameplay-table reads

Per team decision, the mode-(a) decode-failure investigation was picked back up with a genuinely different method — a debugger attached to the actual running game (VS2012's native debugger, driven via COM automation; a dedicated Lua-bindings-format investigation had already established there's no simpler static win available for this specific question). This is the first dynamic-analysis pass in this project's history, motivated directly by §3.6's own conclusion that static tracing had hit its limit.

**Breakpoints armed at the two most concrete addresses from §3.6**: the per-resource "open for reading" function's entry, and the generic I/O backend-dispatch function's entry (one level past the null-pointer parameter that §3.6 couldn't resolve statically). **Both fired repeatedly and reliably during real gameplay — confirming they are genuinely live, frequently-executed code, not dead or unreachable paths.** **[CONFIRMED — dynamic/live.]**

**The null-pointer ambiguity from §3.6 is resolved: it was a decompiler artifact, not a wrong call path.** Live inspection at the backend-dispatch function's entry shows its state-structure parameter is **never actually null** — it's a real, live pointer into what looks like a pool of fixed-stride (~364-byte) state structs, and every field the earlier decompile attributed to it (`+0x148` a small backend-type tag, `+0x158` an EOF/error flag, `+0x15c` a read position, `+0x160` a total size, `+0x168` a flags word) reads back real, sensible, internally-consistent values on every single hit. **[CONFIRMED — dynamic/live, hundreds of hits inspected.]** This confirms the general *shape* of §3.6's static model was correct — the decompiler just lost track of the parameter across the thin-wrapper chain, exactly the more benign of the two possibilities §3.6 flagged.

**However — and this is the actual finding worth recording — extensive, broad, real gameplay coverage through these two breakpoints never once produced a hit that looks like a small gameplay/config-table read.** Every single hit observed (many hundreds, across backend-type values `0`, `1`, and `2` — all three observed live) carried a `total` (state `+0x160`) size in the tens-of-KB-to-multiple-MB range, consistent with texture, mesh, and geometry streaming — never a size matching any independently-known `.xtbl`/table entry size from this project's other specs (checked directly against `vehicle_defaults.xtbl`'s known 11,531-byte compressed size and several sibling vehicle/table entries from `spec-vehicle-data.md`, none matched). The gameplay coverage swept was genuinely broad, not a single narrow probe: game boot, main menu, open-world movement, crib access, the garage menu, the full vehicle roster, vehicle selection, and vehicle retrieval/spawn (which needs the vehicle's physics/handling data to actually simulate) — **all of it**, with zero small-table-range hits anywhere in that entire sweep. **[CONFIRMED — dynamic/live, negative result across a broad, deliberate action sweep, not absence-of-evidence from a narrow or accidental test.]**

**Conclusion: these two functions are confirmed NOT to be the code path used for gameplay/config-table reads (`vehicle_defaults.xtbl` and, by extension, `misc_tables.vpp_pc` content generally)**, despite being real, live, frequently-exercised I/O infrastructure for *other* content (textures, meshes, geometry). This is a genuine, positive, dynamically-confirmed negative result — it rules out a specific hypothesis with much stronger evidence (live behavioral coverage across a real, broad play session) than any static reasoning could have provided, and reframes the open question: the missing piece isn't a byte-accounting bug in *this* mechanism, it's that gameplay-table data almost certainly loads through a **separate, specialized loader that never routes through this generic streaming backend at all.**

**Natural next angle, not yet attempted:** trace backward from the confirmed Lua/UI hook call sites that are known to need this exact class of data — `garage_populate`/`garage_performance_stats` (`spec-lua-bindings.md` §4) are directly on-topic and were found via unrelated static work, giving a concrete, targeted starting point for locating the real loader, rather than searching blind.

### 3.8 Following up §3.7's lead: garage hooks read pre-populated objects, not files — and the trail leads into unrelated generic infrastructure

A follow-up static pass traced backward from both garage hook call sites named in §3.7.

**Both hooks read already-in-memory game objects, not files.** `garage_populate`'s registration function walks a linked list of vehicle "info" objects (each entry advancing via a fixed pointer-list-node field) and reads plain, already-set fields directly off each one (a name/localization ID, a couple of flag bytes) to build the roster UI — no file access of any kind in this function or its immediate callback. `garage_performance_stats` is even more directly on-point: it builds the UI's 4 performance-rating slots (torque/speed/etc., named via a literal string table including `SLOT_TORQUE`) by reading single bytes out of an array **already pointed to by a field on the vehicle object** — again, no file access, just reading a value that must have been populated at some earlier point. **[CONFIRMED — disassembly, both functions fully decompiled.]** This directly explains §3.7's dynamic negative result: by the time a player is anywhere near the garage UI, the relevant data is already resident in memory — the actual load happened earlier, at a point the live-play sweep never specifically isolated (most likely bulk object construction at world/save load or boot, not anything garage-specific).

**Traced one step further — where that per-vehicle array pointer gets set — and the trail leads into unrelated, generic infrastructure, not a vehicle- or table-specific loader.** A whole-`.text` scan for every instruction referencing the exact struct offset the stats array pointer lives at found two writers: one is an ordinary bulk field-initializer (zeroing/defaulting hundreds of fields on object construction, including this one, to an empty-sentinel state — not a real data load). The other looked much more promising at first — a function that takes a `[start, end)` byte-range pointer pair, records bookkeeping about it, and `memcpy`s a leading slice of it directly into the object — a very plausible "embed a small header parsed from a larger loaded blob directly onto the object" pattern. **Tracing its two callers, however, shows unmistakable position-independent-data relocation-fixup logic** (walking a linked block structure with 16-bit tagged entries and a type-field bitmask matching the standard `IMAGE_REL_BASED_HIGHLOW`-style relocation-type encoding, adjusting embedded pointer values by a base-delta) — **this is generic engine infrastructure for loading any complex, self-referential data blob, not something specific to vehicles or to `misc_tables.vpp_pc` content.** **[CONFIRMED — disassembly, the relocation-style pattern is unambiguous; HIGH CONFIDENCE that this specific mechanism is generic/shared rather than vehicle-specific, based on the pattern's shape, not directly proven by finding a second, unrelated consumer.]**

**Where this pass stopped, honestly:** fully unraveling this relocation-fixup framework to find where *it* gets fed a `vehicle_defaults.xtbl`-shaped blob specifically would mean reverse-engineering a general-purpose deserialization system — a substantially bigger undertaking than the original question, and exactly the kind of scope expansion this project tries to catch before committing to it rather than after. **Not pursued further this pass.** The concrete, narrower finding — that the garage UI's data comes from pre-populated objects rather than a file read at interaction time, and that populating those objects touches generic relocation-fixup code rather than anything archive-specific — is recorded here as real progress, with the bigger "reverse-engineer the generic deserialization framework" question left explicitly open rather than started informally.

## 4. Uncompressed Payload Mode

`patch_uncompressed.vpp_pc` (flags `0x00000000` at offset `0x14C`) and other archives that showed no locatable zlib stream (`effects.vpp_pc`, `decals.vpp_pc`) store their payload data **as raw, unmodified bytes** — no compression, no additional framing observed. This was confirmed directly for `decals.vpp_pc`: its top-level `.str2_pc` entries are stored as complete, byte-for-byte intact nested containers, each with its own fully readable magic number and header sitting in the file exactly where expected (see §5) — something only possible if the bytes weren't compressed. Given the archive-level flags field's demonstrated unreliability as a strict global switch (§1), the safest implementation approach is: **attempt to read the first two bytes of a candidate payload region as a zlib header (valid `CMF`/`FLG` byte pair, i.e. `CMF & 0x0F == 8` and `(CMF*256+FLG) % 31 == 0`); if it doesn't look like a valid zlib stream, treat the data as raw/uncompressed.** This is exactly the detection method used to find every zlib stream described in this document, and it worked reliably as a black-box test in every sample tried. **[Superseded: the flags field is fully explained (§1, §3.3), and the per-entry `+0x10` raw sentinel is the compression signal (§3.1); read the sentinel first (§5.9). zlib-header sniffing is only a fallback heuristic.]**

## 5. Relationship Between `.vpp_pc` and `.str2_pc`

**`.str2_pc` uses the exact same header and directory structure as `.vpp_pc` — they are the same container format, just used at two different nesting levels, not a distinct or simplified variant.** **[CONFIRMED — empirical, strong.]**

Direct evidence: `decals.vpp_pc` stores its 14 `.str2_pc` directory entries **uncompressed** (§4). Scanning the raw file bytes for the container magic number (`0x51890ACE`) found it not just once (at file offset 0, the outer container's own header) but **14 additional times**, at file offsets `0x28000, 0x2A000, 0x2C000, ... 0x42000` — evenly spaced exactly **8,192 (`0x2000`) bytes apart**, one per `.str2_pc` entry, in the same order as the directory listing. Every one of these 14 nested headers read the identical magic number and the identical version value (6) as the outer container. One nested header was decoded in full and its own internal fields (entry count, directory-table size, filename-table size) were all internally consistent with the same rules described in §1–§2 (e.g. its directory-size field again equaled `entry_count × 24` exactly).

**Practical implication:** a single recursive parser implementing §1–§4 of this document handles both `.vpp_pc` and `.str2_pc` — there is no need for separate format logic. A `.str2_pc` is simply "a container of this same format, found as the payload of a directory entry in a parent container of this same format."

**Nesting depth — updated this pass:** the first draft of this document could only confirm one level of nesting. This pass directly confirmed **two levels**: `sr3_city_missions.vpp_pc` → its `Running Man.str2_pc` entry (stored raw at the top level, so directly parseable without decompression) → which is itself a valid container of this same format, whose own entries are ordinary leaf content files (an `.xtbl` and a `.cefct_pc`, not further containers, in the one case fully inspected). Whether deeper nesting than two levels ever occurs was not tested, but nothing about the format itself suggests a hard limit — a correct implementation should treat nesting as unbounded/recursive rather than assuming a fixed depth.

### 5.1 Top-level entry alignment — corrected and fully resolved this pass

The earlier draft of this document read the `0x2000` (8,192-byte) spacing between consecutive nested containers in `decals.vpp_pc` as evidence of a *fixed* 8 KB slot per entry. **That was a coincidence of that particular sample, not the real rule, and is superseded by §2's confirmed finding:** every entry (whether it's a container, a texture, an effect file, whatever) is simply padded to `round_up(+0x0C, 0x800)` bytes (physical layout for raw entries / bit-`0x1`-clear containers; for bit-`0x1` containers see §7.1, which uses `+0x10`) — i.e., its **uncompressed** size rounded up to the next 2 KB boundary — and the next entry starts immediately after. The `0x2000` spacing in that one archive was simply what `round_up(size, 0x800)` happens to produce for entries in the 6.0–6.4 KB range (which is what those particular nested `.str2_pc` packages were); a large, varied 17-entry sample from the same archive (sizes from ~1 KB to ~154 KB) confirms the general `round_up(size, 0x800)` rule exactly, with no fixed constant involved. The last entry in a container is not padded out to a full block at the very end — its data simply ends at `total_size` with no trailing padding, confirmed on multiple samples where the last entry's computed end lands exactly on `total_size`.

### 5.9 Refinement: the per-entry raw sentinel takes precedence over the container's shared-stream flag

Found while extracting `.anim_pc` files (`spec-anim-format.md` §7). `preload_anim.vpp_pc` **sets the shared-stream flag (`0x2`) but stores all 4,209 of its entries uncompressed**, each carrying the per-entry raw sentinel `0xFFFFFFFF`. An implementation that branches on the container-level flag *first* and inflates the whole payload as one zlib stream fails outright on this archive (`incorrect header check`); checking the per-entry sentinel first extracts all 4,209 cleanly. **[CONFIRMED — empirical.]**

The two signals are genuinely independent, confirmed by survey: `characters.vpp_pc`, `customize_item.vpp_pc`, `sr3_city_0.vpp_pc` → flag `0x0`, all entries raw; `preload_anim.vpp_pc` → flag `0x2`, all entries raw; `misc_tables.vpp_pc` → flag `0x4801`, no raw entries (the mode-(a) archive behind this document's long-standing parked limitation). **Read the sentinel first; treat the container flag as a layout hint, not a compression declaration.**

## 7. Mode-(a) non-first entries — RESOLVED: the physical-offset rule (2026-09-20)

**Added 2026-09-20.** The long-standing "only entry 0 of a mode-(a) container decodes" limitation (§3.2, §3.5–§3.8, §6 item 1, `HANDOFF.md` §27.3) is **resolved**. It was never a compression puzzle: every earlier pass read non-first entries at the directory's `+0x08`, which is a *logical* offset, not the physical position of the stream.

### 7.1 The rule

For a container whose directory flags have **bit `0x1` set and bit `0x2` clear** (flags `0x4801` on every shipped mode-(a) archive), the physical byte offset of entry *i*'s stream is

`payload_start + Σ_{j<i} round_up(size_j, 0x800)`, with `size_j` = the entry's `+0x10` (compressed size), or `+0x0C` when `+0x10` is the raw sentinel `0xFFFFFFFF`.

This is exactly the loader accumulation already documented in §2 (`+0x04` row) and §3.3 (block index += `round_up(+0x10, 0x800)/0x800` when bit `0x1` is set) — the spec recorded the computation but discarded it as "write-only scratch" because no *reader* of `+0x04` was found. Entry 0 always worked because its physical and logical offsets coincide (both `payload_start`). Each entry's stream is an independent zlib stream: inflate exactly `+0x10` bytes and the output is exactly `+0x0C` bytes; the stream need not end with a final block or checksum, so do not require a stream end.

### 7.2 Provenance and verification

**Found by Team B** (2026-09-20; their reader; they report 1,693/1,693 compressed `.fxo*` entries of `shaders.vpp_pc` and 1,908/1,908 sampled over the nine `0x4801` archives). **A read-only Fable consultation** (advisory; the user had suggested one) found that the rule is already in this document's own §2/§3.3 and predicted every recorded symptom. **Independently verified by SPEC TEAM** with `tools/harnesses/modea_offset_check.py` (no game code run; top-level entries of four archives only):

| Archive | entries | arithmetic identity `pos_last + size_last == total_size` (= file size) | inflate length == `+0x0C` at rule offsets | old `+0x08` rule (control) | shuffled positions (control) |
|---|---:|:-:|---:|---:|---:|
| `shaders.vpp_pc` | 1,693 | yes | **1,693 / 1,693** | 2 | 0 |
| `cutscene_tables.vpp_pc` | 118 | yes | **118 / 118** | 1 | 1 |
| `misc_tables.vpp_pc` | 1,342 | yes | **1,342 / 1,342** | 1 | 0 |
| `da_tables.vpp_pc` | 110 | yes | **110 / 110** | 1 | 0 |

**Total 3,263 / 3,263.** Other controls (offset accumulation with `round_up` to `0x10`/`0x100`/`0x400`/`0x1000`, or unrounded) score 1–5 per archive, i.e. chance. Content checks at the rule offsets: `.fxo_pc`/`.fxo_pc_dx11` magic 1,691/1,691 (two `.fxo` DXBC blobs have no check); `.xtbl` entries begin `<root>` and parse as XML in all but 4 (`07_out.cte_xtbl`, `07_out-lightset.xtbl`, `template.xtbl`, `xbox360_text.xtbl` — length matched, strict parser rejected, not investigated further); `da_tables` 110/110. Base-game `weapons.xtbl` (526,229 bytes, entry 344 of `misc_tables.vpp_pc`) now reads as real XML (`<Weapon><Name>Avatar_sword</Name><Weapon_Class>flamethrower</Weapon_Class>…`).

### 7.3 What this explains

Reading at `+0x08` (= Σ `round_up(+0x0C)` ≥ Σ `round_up(+0x10)`) lands inside a later entry's stream or past EOF: the sporadic false zlib headers (2/1,693 ≈ chance); "silent corruption" (when `+0x08` coincidentally equals another entry's true start you inflate a *different* table and cut it at this entry's `+0x0C`); `cutscene_tables` entry 1's `+0x08` exceeding the file size (§2, §3.5 — the file is compressed-size-sized); continuous whole-payload decoding dying right after entry 0; preset-dictionary priming being useless; and `startup.vpp_pc`'s two entries both decoding (its 20-byte entry 0 rounds identically either way). §3.5's "one ongoing session" reading is withdrawn: a sync-flush marker does not imply a shared window.

### 7.4 Subtleties (from the consultation; not all tested)

- Condition on flag **bit `0x1`**, not on the literal `0x4801`; with the bit clear the accumulation uses `+0x0C`. **Mode (b)** shared-stream containers (bit `0x2`) are unchanged (packed, no padding).
- A raw-sentinel entry inside a bit-`0x1` container: `round_up(0xFFFFFFFF, 0x800)` would overflow to 0 in 32-bit; this reader uses `+0x0C` for such entries (none occurred in the four archives checked: 0 raw-sentinel entries) — **untested** where they do occur.
- Nested `.str2_pc` containers: recurse with the child's own flags (not exercised here).
- Tooling: `tools/harnesses/vpp_modea.py` (`modea_positions`, `get_entry_bytes_modea`) is the opt-in reader; `scan_meshes.py` is **deliberately unchanged** (its `idx != 0` refusal keeps every earlier population count — PEG 70,524, asm 805, etc. — reproducible; those counts EXCLUDED the mode-(a) non-first entries and may now be re-run including them).

The earlier `DAT_02a3c170` backend-vtable trace (`spec-resource-dispatch.md` §7 item 1) is now moot and was **not** pursued; `.czn_pc`'s object-placement/property-stream interior is a separate question and remains untouched. ## 8. Independent confirmation by Team B's container reader (2026-09-20)

Team B fixed and re-verified their `vpp::Container` (their `HANDOFF.md` §9.78) after SPEC TEAM's own verification in §7. Their oracle was independent of any offset rule: a zlib stream must inflate to EXACTLY `+0x0C` and stop (output not capped), consuming its input within `[+0x10, +0x10 + 8]`. **Mode (a)** (flags bit `0x2` clear): **4,272/4,272 compressed entries over all ten shipped mode-(a) containers** (all flags `0x4801`); the old `+0x08` rule scores 14/4,272. **Mode (b)** (bit `0x2` set): **6,239/6,239 containers** satisfy both invariants — `+0x08` equals the packed running sum of earlier `+0x0C`, and the decoded stream length equals Σ the entries' `+0x0C` — including the 68 that also hold raw entries (over all 6,431 containers examined). Through their fixed reader: 4,272/4,272 mode-(a) and 385,168/385,168 mode-(b) entries decode Ok with zero errors. Independent content oracles: `.fxo_pc` wrapper magic 844/844 (was 0/844), PEG header words 69,761/69,761, XML well-formedness 2,079/2,080 (1,817 in the `<root><Table>` shape). **[CONFIRMED — empirical, two independent implementations; the mode-(b) invariants restate what §3.2(b) already documented.]**

**Two implementation notes from Team B:** (1) zlib's `inflate()` may report an error in the same call that produces the last payload byte (real entries end with a short sync-flush-style tail followed by padding), so "produced == `+0x0C`" must count as success even if zlib complains afterwards; (2) a decoder that caps its output at `+0x0C` and reads at the wrong offset returns a right-length PREFIX OF A NEIGHBOURING ENTRY — that, not a corrupt stream, is what made non-first entries look "silently corrupt" (§3.2, §3.5).

**Populations re-run by Team B through the fixed reader (their measurements):** PEG — the 76 mode-(a) index>0 c-files (cvbm 45 + cpeg 31) parse 76/76 (were 0/76), so the c-file total is 70,524 + 76 = **70,600**; `.cefct_pc` — all 1,812 entries Ok (previously Ok 240, RecoveredSharedStream 3, LongChain 1,569) and the enumeration is IDENTICAL (`root+0x40` 346/135 entries/files, `0x70` 595/168, `0x90` 478/119), i.e. the old backward-walk heuristic had recovered the right bytes and exact slicing reproduces them; `.fxo_pc` 844/844 exact consumption (was 2/108), `.fxo_pc_dx11` 847/847 decoded (was 0).

**The four XML rejections in §7.2, explained (SPEC TEAM re-derived):** they are authoring quirks in the shipped tables, not container failures — `misc_tables.vpp_pc :: template.xtbl` (232 bytes, complete at its declared size) contains `<RampExposure>False</Exposure>` (a mismatched close tag; Team B: the only genuinely malformed file of 2,080); `07_out.cte_xtbl` and `07_out-lightset.xtbl` contain an illegal control character `0x1F` inside `<Name>09_PLayer\x1f_Neg</Name>`; `xbox360_text.xtbl` has an element name containing a space (`<Xbox 360_Identifier>`). An `.xtbl` reader must therefore be tolerant the way the engine evidently is (mismatched close tags, control characters in text, spaces in element names).
