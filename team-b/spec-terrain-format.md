# Saints Row: The Third — `.czh_pc`/`.czn_pc`/`.gzn_pc` Terrain Format Specification

**Prepared by:** SPEC TEAM (cleanroom reverse-engineering process)
**Phase:** 1, black-box follow-on to the world-streaming survey (`spec-world-streaming.md` §5)
**Scope:** The terrain/zone geometry format found once per tile (and per named landmark) throughout the open-world streaming system.
**Method:** Black-box byte inspection of one real, fully-reliable sample set (`sr3_city~s1018.czh_pc`, 1,280 bytes; `sr3_city~s1018.czn_pc`, 489,516 bytes; `sr3_city~s1018.gzn_pc`, 806,468 bytes — all extracted from a mode-(b) shared-stream tile bundle, so fully reliable). No disassembly this pass, per the same scoping as the geometry/effects passes: real structure documented where found, deeper binary layout explicitly left open where it would need Ghidra rather than more guessing.

**Confidence key** (as in prior specs): **CONFIRMED — empirical**, **HIGH CONFIDENCE — inferred**, **HYPOTHESIS — unconfirmed**, **OPEN / UNKNOWN**.

---

## 1. Overview

Every terrain-bearing bundle in the open-world streaming system (each coordinate tile, and each named landmark that has its own ground/floor — `spec-world-streaming.md` §3–4) carries a matching trio of files sharing one base name: **`.czh_pc`** (small, CPU-side — a "header" in the literal sense, holding almost entirely material/texture references), **`.czn_pc`** (CPU-side, larger — region/chunk metadata), and **`.gzn_pc`** (GPU-side — the actual geometry payload). This is the same general `c`/`g` paired-file convention used throughout this project, just split across two CPU-side files instead of one.

## 2. `.czh_pc` — material/prop reference list

Opens with the **same shared material-reference block** already confirmed in `.matlib_pc`, `.ccmesh_pc`, `.cefct_pc`, and `.clmesh_pc` (`spec-geometry-format.md` §3.1, §4.1) — magic `0x00043854`, a name-table-length field, and a reference count (56 in this sample). **[CONFIRMED — empirical, exact field match — a 6th confirmed use of this shared block.]**

**The name list itself is not flat — it's split into two labeled sub-groups by embedded `cc:N` marker strings** (`cc:0`, then 44 real names, then `cc:78`, then 12 more): the first group is **ground/splat textures** — real names like `dirt_tile_01_d_dt.tga`, `tarmac_02_n.tga`, `asphalt_lot_02_r.tga`, `sidewalk_01_d_co.tga`, `gravel_01_sp.tga` — following the same `_d`(diffuse)/`_n`(normal)/`_r`(roughness)/`_s`,`_sp`(specular) suffix convention already established elsewhere in this project; the second group is **foliage/clutter mesh source references**, with the extension **`.fmeshx`** (matching the "compiled-from-an-editable-source" naming convention already seen for `.effectx`, `spec-effects-format.md` §1) — real names like `fol_fern_a01.fmeshx`, `litter_cansjunk_a01.fmeshx`, `litter_pizza_a01.fmeshx`. **[CONFIRMED — empirical, full name list enumerated, the `cc:N`-delimited grouping directly visible.]** The `N` in `cc:N` (`0`, then `78`) does not obviously match a simple entry-count or byte-offset checked against this one sample — **[OPEN / UNKNOWN what `N` actually encodes.]** **Pointer (2026-09-10, third):** the zone module resolves a zone's dependencies by **authoring** extension — it references `.effectx`, `.cmeshx`, `.rigx`, `.todx`, `.ctdgx`, `.lmeshx`, `.smeshx` and `.fmeshx` in one function — which is why `.fmeshx` names appear inside `.czh_pc` rather than shipped names. The complete authoring list for this engine is in `spec-zone-data-format.md` §4. **[CONFIRMED — disassembly.]**

**Pointer (2026-09-10, second):** everything in `.czh_pc` *after* the material block described in this section is the **`SR3Z` zone-header block**, now fully resolved — magic, version range 27–29, fixed `0x40` header, then `count × 14` bytes, reproducing the exact file size of all 2,971 shipped files. See `spec-ctorless-types.md` §5. That section also answers this document's standing note that terrain/zones have no registration-table constructor: a null constructor is a supported mode, and the zone module builds its own filenames. The authoring extension for zones is **`.zonex`**.

**Pointer (2026-09-10):** the shipped counterpart of `.fmeshx` is **`.cfmesh_pc`** (registration type 37, "Foliage Mesh") — the 19 shipped files carry exactly these base names (`fol_fern_a01`, `litter_cansjunk_a01`, `litter_pizza_a01`, …), the same authoring-name/shipped-name split as `.animx` → `.anim_pc`. See `spec-foliage-format.md`.

A short trailer follows the name list (72 bytes in this sample, mostly zero) containing a second fixed 4-byte marker, **`0x5A335253`** (on-disk bytes read as the literal ASCII `SR3Z`), then a `u32` reading `29`, then mostly zero bytes with one non-zero small value near the end. **[CONFIRMED — empirical, exact bytes; HYPOTHESIS for the marker's/fields' purpose.]** **[Resolved: this trailer is the `SR3Z` zone-header block — see the pointer above and `spec-ctorless-types.md` §5.]** Not decoded further — the file is nearly all name-list, so there isn't much trailer left to characterize.

## 3. `.czn_pc` — multi-region chunk metadata

⚠ **Reconciled 2026-09-12 against `spec-zone-data-format.md` §6–§8** (written later, over the full 2,971-file population), after Team B's independent reader flagged the two documents as apparently describing `.czn_pc` differently and never cross-checked. **They are the same structure** — the corrected reading follows; the original single-sample framing is kept below it, since it is what actually found the region-label string that follows.

**What the "magic" actually is:** `0x80002233`'s upper 16 bits are `0x8000` and its lower 16 bits are `0x2233`; `0x80002237`'s are `0x8000`/`0x2237`. That is exactly the shape `spec-zone-data-format.md` ~~§6~~ §1 confirms population-wide for the top-level structure: a chain of `{u32 id (high bit set, upper half `0x8000`), u32 length}` records, 8-aligned, with **790 distinct ids observed across the shipped corpus**. **This sample's two "magic values" are simply its first two top-level records** (`0x2233`, then `0x2237`, two of the 790 ids), not a file-specific magic — a reasonable reading from one sample, since most other formats in this project do open with a genuine fixed magic, but not the actual shape here now that the population-wide pass has characterised it. **[CORRECTED — empirical, byte arithmetic on this sample's own already-published values; see `spec-zone-data-format.md` ~~§6~~ §1 for the population-wide model this reconciles against.]**

**What survives, and is new information `spec-zone-data-format.md` did not have:** the literal, readable string `"Region<003>"` sitting immediately after the second top-level record's id/length pair, followed by a second `"Region"` string — i.e. **a human-readable label living inside a specific top-level record's own interior body.** `spec-zone-data-format.md`'s population-wide pass never looked for readable strings at this specific position (its own work focused on the Mesh sub-block's binary signature and on the top-level chain's *structure*, not on decoding what a record's interior *contains*), so this is a genuinely new lead recorded here and cross-referenced there (~~§6.4~~ §9.4) — useful precisely because record-interior content is still the project's one parked question (`HANDOFF.md` §27.3). **Recording the observation is in scope; decoding what it means is not, and this note does not attempt to.** **[CONFIRMED — empirical, exact bytes, a real readable string — unchanged from the original finding below.]**

---

**Original framing, kept visible as the record of what one sample showed before the population-wide pass existed to check it against:**

A much larger file (489 KB in this sample) with its **own distinct magic, `0x80002233`** — not the shared material-reference block. **[CONFIRMED — empirical.]** The file is organized as **repeating tagged sub-blocks**: a second occurrence of a near-identical magic value (`0x80002237` — differing from the first only in its low byte, by exactly `4`) appears a short distance into the file, immediately followed by a **literal, readable region label string, `"Region<003>"`**, and a second `"Region"` string starts immediately after that. **[CONFIRMED — empirical, exact bytes, a real readable string.]** This is strong evidence the file holds **multiple named/numbered terrain regions or chunks**, each introduced by its own small, incrementing magic-like tag — consistent with a tile's terrain being subdivided into several sub-patches (matching the same general "a tile is actually composed of several pieces" pattern already seen at the tile-naming level, `spec-world-streaming.md` §3). ~~**[HIGH CONFIDENCE — inferred: the repeating-tagged-region shape is real and directly observed; the exact per-region record layout, how many regions a typical tile has, and what "003" numbers (a region index? a sequential ID?) was not determined from one sample.]**~~ **→ the "repeating-tagged-region shape" is the already-confirmed top-level `{id, length}` chain (see the corrected reading above); the "003" question remains genuinely open.**

## 4. `.gzn_pc` — the geometry payload

The paired GPU-side file (806 KB in this sample), with **its own distinct 4-byte magic, `0xE6EA70B7`**, unrelated to either `.czh_pc`'s or `.czn_pc`'s marker values — followed by 12 zero bytes, forming a 16-byte header. **[CONFIRMED — empirical, exact bytes.]** This 16-byte-header shape (4-byte tag + 12 zero bytes) directly matches the pattern already confirmed for `.gcmesh_pc` and inferred for `.glmesh_pc` (`spec-geometry-format.md` §4, §4.1).

**Immediately after the header, a long run of small, smoothly-ascending 16-bit values** — the same shape already identified as a likely vertex-index buffer in both `.gcmesh_pc` and `.glmesh_pc`. **[HIGH CONFIDENCE — inferred, same value-range-shape evidence as those two formats; this is now a 3rd file family showing the identical "16-byte header, then an ascending-u16-run" shape, which strengthens confidence this is a genuine, deliberate engine convention rather than coincidence.]**

**Update from a follow-up Ghidra pass** (`spec-geometry-format.md` §4.1, prompted by exactly this three-way pattern match): the mechanism was fully traced and confirmed for `.gcmesh_pc` specifically — a real second magic (`0x424BD00D`), a version sub-header, and six independently-sized payload arrays, one of which (2-byte stride, size = a product of two header count fields) is a strong match for the index buffer already spotted here by inspection. **However, that same pass also found `.glmesh_pc` is loaded through demonstrably different code than `.gcmesh_pc`** (a different registered constructor), and **`.gzn_pc`/`.czn_pc` are registered with no dedicated constructor at all** — meaning terrain reaches whatever parses it through a separate, not-yet-traced path. **So `.gzn_pc`'s matching black-box shape remains a real, useful clue, but the specific six-array mechanism confirmed for `.gcmesh_pc` should not be assumed to apply here without separately tracing `.czn_pc`/`.gzn_pc`'s own actual code path** — which, given §3's finding that terrain has its own real multi-region structure (`"Region<NNN>"` labels) that the generic mesh loader wouldn't need to know about, seems likely to be genuinely different rather than just an unconfirmed instance of the same thing.

3. **`.gzn_pc`'s vertex-attribute layout** — `.gcmesh_pc`'s matching black-box shape has since been traced and resolved (`spec-geometry-format.md` §4.1), but that same pass found terrain is registered with no dedicated constructor, so its actual loader path is still separate and untraced. Tracing it would need starting from wherever `.czn_pc`'s multi-region parsing (§3) hands off to the geometry data, not from the `.gcmesh_pc` constructor this pass already opened up.

   **Update, 2026-09-30 — a real negative on zone-tile *texturing* specifically, reported by Team B from their own file-side work (two independently-built tools agreeing exactly, one calling their own `sr3zone::ZoneGeometry::locate()` directly):** the vehicle-style per-draw-range material/texture-binding mechanism (the `0x424BD00D` "GeometryBlock" sub-header keyed by a draw range's own material id — `spec-geometry-format.md` §4.1/§4.1.3) **does not extend to zone geometry at all.** `0x424BD00D` never occurs anywhere in real `.czn_pc` data (0/2,915 and 0/2,971 in their two independent full-population scans — the exact file-count denominator isn't reconciled between the two scans, but both agree on zero), and every real layout-code-24 Mesh-block channel has `texcoordCount == 0` (535/535, both scans) — **consistent with, and now population-wide confirmation of, this document's own single-sample observation** (`spec-vertex-format.md` §12.3's population table already recorded "texcoord idx observed: 0" for code 24, from this project's own 448-channel full sweep — the two findings agree independently, from two different sides of the clean-room boundary). carry the vehicle-style per-range GeometryBlock texturing mechanism — a real absence, not a reader bug — and if zone texturing works some other way, it isn't visible from the file side alone.** **[CONFIRMED — empirical, peer-reported and independently re-verified on this side directly against real bytes** (`spec-vertex-format.md` §12.13 item 4: 448/448 real code-24 channels measure exactly 20 bytes/vertex with zero texcoord bytes appended, matching the peer's `texcoordCount == 0` finding exactly) **— agreement across both sides of the clean-room boundary, from two structurally different **Role update, 2026-09-30 — the shadow/occlusion/collision-proxy reading is RETIRED, real render evidence (Team B, their own HANDOFF §9.130, i.e. `team-b/HANDOFF.md`):** a composite render of code 24 together with its companion channels (sem 0/2/4), at two camera angles, shows the companion window/facade detail cards sitting inside code 24's own wall faces and hugging its silhouette edges — the two are coplanar, and the combined image reads unambiguously as buildings with windows on their walls. **Code 24 is CONFIRMED to be the visible building shell itself, not a proxy of any kind.** This reframes the open question entirely: the shell is genuinely UV-less (§12.13 item 4's own texcoord-count-zero finding stands unchanged), so it must get its surface appearance some other way — a world-space or triplanar projection computed from position/normal, vertex-color-driven shading, or a flat/parameter-only material.

**Answered, 2026-09-30 (`spec-vertex-format.md` §12.13 item 5, full detail there): code 24's own vertex shape is exactly what this engine's shared "role 4/5" G-buffer normals/lighting-parameter fill pass requires — a routine, non-special-cased shape used by 100+ real shaders across the whole corpus, most of them either genuinely flat/parameter-only (zero texture samples) or reflection-mapped (a spherical env-map projection, not triplanar — no literal triplanar pattern was found anywhere in this family).** This reads as: code 24 feeds the deferred normals/lighting-parameter pass, not a diffuse/color pass at all — the shell's real diffuse appearance most plausibly comes through the sibling, texcoord-bearing channel (sem 0/2/4) via a separate pass, consistent with everything else measured.

**Upgraded, same day, from structural to disassembly-grounded (`spec-vehicle-geometry.md` §11.9.3, `spec-zone-data-format.md` §9.5): a real zone-side draw-call chain was traced, and it creates and registers its render materials through the IDENTICAL allocator/registry functions vehicle-body materials use** (`FUN_00e5e240` for the `rl_static_material` instance — literal vtable match, `spec-render-pipeline.md` §22.3's own RTTI-decoded address — and `FUN_00e3fcb0` for the global material registry, §22.2), reached from two genuine `.czn_pc` top-level record handlers (`FUN_00864c60` for id `0x2237`/"Region", `FUN_007512f0` for id `0x2251`). Since `rl_static_material`'s own vtable `+0x10` technique-select forwarder is completely format-agnostic (`FUN_00e5e530`, §22.4/§23.2 — no vehicle/tree/zone-specific branch anywhere in it), any zone material created this way is drawn through the exact same role-selection logic already confirmed (via the car-paint shader's own real T8 pass table, §20.12) to resolve to role 4/5 for vehicles. **This is no longer just "code 24's shape happens to fit what role 4/5 needs" — the zone material-dispatch code path IS the same code already confirmed to reach role 4/5.** **[HIGH CONFIDENCE, upgraded from the shape-match alone — the creation/registration side is disassembly-CONFIRMED identical to the vehicle path; still short of fully end-to-end CONFIRMED because (a) no live/dynamic trace caught an actual running frame with the role-selecting flags held during a zone draw, and (b) the final hand-off object submitted to the generic per-item draw loop (`FUN_00e74880`/§23.6.1) was not resolved — a further `FUN_00e72070`-allocated "reference record" object is built and handed a vtable `+0x7c` call, but its own RTTI class was not decoded this pass; the material-id-to-filename binding for zones remains separately unresolved (above).]**

**Update, 2026-09-30 — direct answer to "how does a zone draw range select its material," the specific next wall Team B flagged:** zone Mesh sub-blocks DO carry a real, per-draw-range material id, using the identical 16:16-packed convention `spec-vertex-format.md` §8.2 already confirms for characters/vehicles (dense from 0, real variation observed up to at least masked id 16 across the population) — decoded directly from 448 real zone meshes' own group/range records, which live inside the universal Mesh sub-block and do NOT depend on the missing GeometryBlock wrapper at all. **So the material *id* concept is confirmed present and working for zones; the wall is specifically the next step — turning that id into an actual texture/material.** For every other carrier in this project, that step is the `0x424BD00D` sub-header's own material-count field plus a per-material 12-byte texture-binding-record region living immediately after the Mesh sub-block (`spec-vertex-format.md` §8.3/§8.4) — and that entire mechanism is structurally absent for zones, not merely unconfirmed, since it requires the GeometryBlock header Team B already showed never occurs in `.czn_pc`. **One direct hypothesis was tested and REFUTED:** a zone tile's max material id + 1 does not equal its sibling `.czh_pc`'s own shared-material-block reference count (0/279 real tiles match) — so material id is not a simple direct index into that tile's `.czh_pc` name list. The real lookup — whatever links a zone draw range's material id to an actual `.czh_pc`/`.matlib_pc` texture reference — remains genuinely OPEN; this narrows the search (a real, varying id exists to key from) without resolving it.
4. **Only one tile's terrain trio was sampled.** No cross-tile validation was done (e.g. whether every tile has exactly one `.czh_pc`/`.czn_pc`/`.gzn_pc` set, whether the `s`/`f`-prefix distinction noted for `angels_crib` in `spec-world-streaming.md` §5 applies to plain coordinate tiles too) — flagged rather than generalized from one example.

None of these gaps prevent locating and extracting a tile's terrain-related files, or enumerating the ground textures and foliage props it references — only the actual terrain mesh geometry and the multi-region chunk structure remain to be decoded.
