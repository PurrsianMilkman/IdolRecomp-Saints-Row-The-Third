### 3.1 Schema, quoted from the file's own embedded `TableDescription`

**[CONFIRMED — empirical, the schema definition is embedded literally in the `.xtbl` file itself, the standard convention this project has already documented for every other `.xtbl` container.]**

```
Group_AI_Overrides            (Type: Grid; Description, paraphrased: per-group AI
                                behaviour overrides, needed for riot-shield NPCs)
  Group_AI_Override           (Type: Element)
    Group_Name                (Type: String, Unique; Description, paraphrased: the
                                name of the overridden group)
    Overrides                 (Type: Element)
      Personality              (Type: Reference, Required: false)
        -> File: AI\ai_personalities.xtbl, Type: Personality.Name
      Behavior                 (Type: Reference, Required: false)
        -> File: AI\ai_behavior.xtbl, Type: Behavior.Name
```

**This is a real, designer-facing mechanism, and the file states its own purpose**: a per-area table lets a mission/encounter override a *named enemy spawn group*'s AI behavior and/or personality profile by string reference into two master tables. The document's own comment — that the grid is needed for riot-shield NPCs — is a genuine piece of design intent, not an inference. *(Description strings paraphrased, desk review 2026-09-30.)*

**Runtime consumer (added 2026-10-02, re-derived from the executable). [CONFIRMED — disassembly, fresh read-only dumps of `FUN_006F3D60`, `FUN_004F27F0`, `FUN_00507E60`, `FUN_006E7280`, `FUN_004F36A0`; string uses from bus job `20261001T021649-team-a-qsme` `hn1_str1.txt`.]** The only code that names `Group_AI_Overrides`/`Group_AI_Override`/`Overrides` is the per-area modal-table loader **`FUN_006F3D60`** (the same routine that reads `Wave_Difficulty_Presets`, `Enemy_Groups_Presets`, `Powerups`, `Kill_Triggers` from these area files). The consumer works in two steps:

1. **Parse (around `0x006F4541`–`0x006F46E5`).** Each `Group_AI_Override` element that has an `Overrides` child adds one entry to three parallel scratch lists (room for 540 each): the `Group_Name` text (bounded to 31 bytes), a personality number and a behaviour number. An element with no `Overrides` child is skipped. The personality number starts at 20 (the byte at `0x011177E5`) and, if `Personality` is present, is replaced by the result of `FUN_00507E60`, which hashes the name and searches the loaded personality list for that hash, returning 20 when not found. The behaviour number starts at 44 and, if `Behavior` is present, is replaced by the result of **`FUN_004F27F0`**, a case-insensitive comparison (first 30 characters) of the name against every loaded `ai_behavior.xtbl` record name (`spec-tables-traffic-ai.md` §10), returning the record index or 44 (the table's capacity, used as "none") when no record matches. So 20 and 44 both mean "no override". The loader does look for an earlier entry with the same `Group_Name`, but it does not use what it finds: every element is appended as a new entry.
2. **Apply (around `0x006F5025`–`0x006F50D5`).** After the group lists have been built (by `FUN_006F02F0`, in `0x7C0`-byte preset blocks — read here as the wave presets, from the neighbouring element names), each group entry (60-byte entries; name at `+0x00`) first gets the defaults (behaviour 44 at `+0x34`, personality 20 at `+0x30`). Then the group's name is compared, case-insensitively, against **every** override entry in file order. On each match the entry's behaviour and personality numbers are copied in and a per-override "used" byte is set, so when two overrides name the same group, the later one wins.

**At spawn time**, `FUN_006E7280` (reached only through a pointer table at `0x0113D2E8`) sets up each character spawned for the area. If the character's group entry has a personality other than 20, that personality is applied. If its behaviour number is not 44, **`FUN_004F36A0`** is called with that number. This routine stores the behaviour index in the character's AI sub-object (`+0xE4`) and a pointer to the `0x200`-byte behaviour record at character `+0x31C`. It then accepts the assignment only if a yes/no property of the character (`FUN_009BA300`, a wrapper over `FUN_00941F60`, not traced) equals the record's `Riotshield_Only` bit. Otherwise, and also for an index outside the loaded count, it falls back to `FUN_004F3600`. **HYPOTHESIS:** that property is "carries a riot shield". This fits the schema's own riot-shield comment, but the routine was not read. The `+0x31C` pointer is the one the goal/action selector reads (§3.3). The literal `"Brute Melee"` is therefore turned into decision behaviour by a name lookup once at area load, then copied into each spawned character as a record pointer.

**Who reads the goal bytes (added 2026-10-02, re-derived from the executable). [CONFIRMED — disassembly. Sources: exe_index dumps of `FUN_004F2650`/`FUN_004F29B0`/`FUN_004F2B50` and the xrefs of `0x0135BFC8`/`0x013617C8`; fresh read-only dumps of `FUN_004F3750`, `FUN_004F36A0`, `FUN_004F4EE0`, `FUN_004F27F0`.]** An xref search on the record array finds only the loader, the name lookup `FUN_004F27F0`, the assigner `FUN_004F36A0` and `FUN_004F4EE0`. Consumers do not address the array directly; they go through the per-character record pointer at `+0x31C`, which `FUN_004F36A0` sets. `FUN_004F4EE0` either re-applies a character's stored index or, for characters whose type lacks a particular flag, points `+0x31C` straight at the record named `Saint Rifle`. Following the static tables that the loaders fill leads to the reader: **`FUN_004F3750`** (called from `FUN_004F5210`) is the per-character goal/action chooser. It reads the `ai_goals.xtbl` action lists at `0x012E22F8` and the `combat_actions.xtbl` precondition bytes at `0x012E1C75`. In own words:

- It walks the **17 goal ids in fixed order 0…16**. A goal is considered only if its goal-enabled byte in the character's behaviour record (`record +0x1C6 + goal`) is non-zero, **and** the goal's own test routine says yes. That routine comes from a function-pointer slot in the static goal table at `0x012E22F0` (32-byte entries: name pointer at `+0x00`, routine at `+0x04`, then the 24 ordered action ids that `FUN_004F29B0` fills from `order_of_actions`, padded with `0x47` = none).
- For a goal that passes, it tries that goal's actions in list order. Each action must be enabled in the behaviour record's ability table (`record +0x22 + 6·action + 4`) and not already tried in this pass. Its `pre_flags` precondition (from `combat_actions.xtbl`) must match the character's current state (`FUN_004F25C0`), and a per-action timer on the character (`+0x320 + 4·action`) must allow it. Then the action's own routine is called, through the function pointer at `+0x08` of its 24-byte entry in the static action table at `0x012E1C60`. **The first action whose routine returns success is the result.** The first goal in id order that yields an action wins, so goal id order works as a fixed priority.
- Special cases: an action already in progress is kept when the character's state flags mark it so and its timer check (`+0x440`) passes. When a second flag is set, it is first re-checked through its own routine, and if that fails the state is reset and a 250 ms timer is started; the timer's exact meaning (for example no-interrupt) is not established. A character flag (`+0x2BC` bit 1) forces action 14 (`hold position` per `spec-tables-traffic-ai.md` §10). If nothing is chosen, the result is action 14 or action 48, depending on `FUN_0051DB40`, not traced.

**Consequence for the "hardcoded" question above.** Both readings are partly right. *What* a named behaviour may do is data: which goals are on, which actions are on, their repeat timings, and the cover/suppress/seen-in-last parameters (`spec-tables-traffic-ai.md` §10). The *order of actions within a goal* is also data (`ai_goals.xtbl` `order_of_actions`). Hardcoded engine code supplies three things: the *goal priority* (fixed id order), the *test of whether a goal applies*, and the *execution of each action*. These are one routine per goal and one per action, reached through function pointers in two static tables. They are not named in any file. So "a thin naming layer over hardcoded logic" ~~is very likely~~ is CORRECTED to: a named data record that gates and parameterises a fixed set of hardcoded goal tests (up to 17; a goal whose slot is empty is skipped) and hardcoded action routines (up to 70). **OPEN:** what each goal-test routine and each action routine does. Each needs its own disassembly pass.
