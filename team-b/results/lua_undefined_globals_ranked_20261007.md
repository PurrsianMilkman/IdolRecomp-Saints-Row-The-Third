# Undefined-global ranking for the next natives pass (2026-10-07)

**REPORT-ONLY.** No native implemented, no `sr3luahost` source touched. This is a static
cross-reference built independently of (and run *after*) the native-implementation batch that
landed in `7cd9275`/`0acb5aa` this same session (16 natives, `specConfirmedStubNames()` now at
246) — it is meant to feed whichever pass comes *after* that one, and deliberately does not
re-propose anything that batch already closed.

## Method, in order

1. **Ran `luacheck`** (MIT, lunarmodules/luacheck v1.2.0) over every shipped Lua script this
   project's own mission-drive harness discovers, configured to report only warning **W113**
   ("accessing an undefined global variable").
2. **Cross-referenced** the resulting per-name static counts against the runtime stub-hit table
   (`results/verdict_stub_hits_with_missions.tsv`) and the current "already implemented" roster.
3. Produced the ranked table below, with a CONFIRMED-spec-coverage check against `spec-*.md` for
   every entry in the top 20.

## Step 1 — luacheck: installable, but not via luarocks

`luarocks`/`lua`/`luacheck` were not present on this machine and no package manager (`choco`,
`scoop`) was available either (`winget` is). Network egress worked, so rather than stand up a full
Lua+LuaRocks toolchain for one task, I pulled the **official standalone Windows binary** luacheck
itself publishes on GitHub Releases (`lunarmodules/luacheck` v1.2.0, `luacheck.exe`, MIT) —
same project, same license, no third-party mirror. Verified it runs
(`Luacheck: 1.2.0 / Lua: PUC-Rio Lua 5.4 / Argparse 0.7.1 / ...`). This is a local tool-install
convenience only; nothing about it is checked into the repo.

**Getting the scripts onto disk.** The mission-drive harness (`tools/lua_host_run.cpp`) and the
data census (`tools/lua_mission_ui_census.cpp`) both find scripts by walking the real archive
cache in memory — neither writes raw script text back out to individual files, which is what an
external linter needs. Rather than patch either existing tool (out of scope — "do not modify any
`sr3luahost` source file", and I extended that caution to not touching these two tools' own logic
either), I wrote a small new standalone diagnostic, following this project's own
`tools/validation/` convention (deliberately **not** wired into `CMakeLists.txt` — see that
directory's own `README.md`):

- **`tools/validation/lua_source_dump.cpp`** — duplicates the same recursive archive walk
  `lua_host_run.cpp`/`lua_mission_ui_census.cpp` each already duplicate locally (this codebase's
  own stated convention: a small `walk()` per tool, not shared), leaf test `.lua` (case-insensitive),
  and for every script found writes its raw bytes unchanged to `<out_dir>/scripts/NNNNN.lua` plus
  a `manifest.tsv` (`index, archive, path_chain, entry_name, byte_length`) that is the only place
  mapping a dumped file back to its real shipped identity.
- Built directly from source with the Developer Command Prompt (no `cmake`, no stale
  `build_verify\*.obj` needed — this worktree had none): `cl.exe` against
  `src/{byte_view,format,hash,payload_locator,container,content_validation}.cpp` and the vendored
  zlib `.c` files. One wrinkle: `third_party/zlib/zconf.h` is normally generated by CMake's
  `configure_file(... @ONLY)` from `zconf.h.cmakein`, which is NOT a plain copy — it contains two
  `#cmakedefine` lines (`Z_PREFIX`, `Z_HAVE_UNISTD_H`) that MSVC's preprocessor rejects outright
  (`C1021: invalid preprocessor command 'cmakedefine'`). Resolved by hand-rendering those two lines
  to their Windows/MSVC-false form (`/* #undef ... */`), matching exactly what CMake's own
  `check_include_file(unistd.h ...)` result would produce on this platform — not guessed, derived
  from what the one real substitution variable (`Z_HAVE_UNISTD_H`, never true on Windows) and the
  never-set `Z_PREFIX` actually resolve to.
- **Smoke-tested implicitly by its own summary line**, since the real population size is already
  independently known: run against the real archive cache
  (`D:\Project Crreish\Saints Row 3 CRREISH\packfiles\pc\cache`, same path
  `results/mission_drive_20261002_next_blockers.md` already cites) it reported
  `archives_found=38 archives_opened=38 ... lua_scripts_found=804 lua_scripts_written=804` —
  exactly the 804-script population `lua_host_run.cpp`'s own top comment documents, a real,
  checked cross-check rather than an assumed match.

## Step 1 result: the raw static signal

`luacheck --no-color --codes -j4` (`std = "lua51"`, `only = {"113"}`) over the 804 dumped scripts:

- **118,422** total W113 warnings, **7,165** distinct flagged names.

This raw count is dominated by one real limitation luacheck has no way around: it analyzes **one
file at a time**, with zero visibility into what a *different* shipped script defines. This
project's own data census (`tools/lua_mission_ui_census.cpp`) explicitly designed around exactly
this gap with a real two-pass whole-population Lua parse (SCRIPT-DEFINED vs ENGINE-PROVIDED).
Spot-checking the first few raw hits confirmed the expected shape immediately: `game_lib.lua`
(the shared mission-scripting include every mission script relies on) defines
`MINIMAP_ICON_LOCATION`, `SYNC_ALL`, `cutscene_play`, `marker_remove_trigger`, etc. directly
(`function cutscene_play(...)`, `SYNC_ALL = 3`) — luacheck correctly flags these as "undefined"
in every *other* file that merely calls them, which is a true statement about that one file in
isolation but not about the shipped population as a whole, and would have been pure noise against
this report's actual question ("which names does **no** shipped script define, anywhere").

**Filter applied (judgment call, not a full parse):** a regex-based census over all 804 raw
dumped files — `^function NAME(`, `^NAME = function(`, `^NAME[, NAME2...] = <value>` (excluding
`local`/comment lines) — found **16,887** distinct script-defined names across the whole shipped
population, and every name in that set was excluded from the candidate list. This is a
best-effort heuristic, not `sr3lua`'s real AST parse: a multi-line table constructor whose field
happens to start a line (`key = value,`) is indistinguishable from a true top-level global
assignment under a plain per-line regex, so this filter almost certainly **over-excludes** rather
than under-excludes — the safer direction of error for a candidate list (risk is a few genuine
natives missing from the tail, not false natives polluting the head). Not independently verified
name-by-name; flagged here rather than silently assumed exact.

After that filter: **1,262** distinct names remain — genuinely undefined anywhere across the
whole 804-script shipped population, by this static method. This is the real "call to a host
native this project hasn't defined as a known global" signal Step 1 asked for.

## Step 2 — cross-referencing against "already implemented," the hard way

The obvious join is against `specConfirmedStubNames()` (`src/lua_spec_confirmed_stubs.cpp`,
re-counted directly from the source array rather than trusting the commit message's stated
figure: **246**, matches exactly). Doing *only* that join produced a visibly wrong #1 result:
`thread_yield` — **315,449,910** real runtime calls (`verdict_stub_hits_with_missions.tsv`) —
ranked as the single highest-priority "unimplemented" native. It is not unimplemented. It has a
real, dedicated, hand-written `ThreadScheduler` backing it (`src/lua_thread_scheduler.cpp`,
wired into `Host`'s constructor in `src/lua_host.cpp`); it simply never went through the
*generic-stub-promoted-to-confirmed* pipeline `specConfirmedStubNames()` tracks, because it was
never a generic stub to begin with. Caught this and widened the "already implemented" set by
reading every `register*(lua_State* ...)` registration site in `src/` (exactly four exist:
`lua_spec_confirmed_stubs.cpp`, `lua_thread_scheduler.cpp`, `lua_bare_globals.cpp`, and the
generic fallback `lua_stub_registry.cpp`, which is not a "real" implementation by construction).
`src/lua_bare_globals.cpp` turned out to carry a second correction: `tools/LUA_ROSTER_NOTES.md`
(2026-09-30) documents the 24 "bare globals" (`floor`, `debug_print`, `rand_int`, `thread_new`,
`thread_yield`, `thread_kill`, `thread_check_done`, `abs`, `acos`, `cos`, `sin`, `ceil`,
`assert_msg`, `get_frame_time`, `include`, `max`, `min`, `rand_float`, `round`, `sizeof_table`,
`sqrt`, `strstr`, `closest_point_on_line_segment`, `which_side_of_2d_line`) as **"PENDING" —
deliberately registered as none of them** pending an exact roster from Team A. That note is now
stale: all 24 have real bodies in `lua_bare_globals.cpp` and are wired into both Lua states via
`registerBareGlobals(...)` in `lua_host.cpp`. Worth flagging to whoever owns that note next, as a
side finding, not the main point of this report.

**Final "already implemented" set: 271** (246 `specConfirmedStubNames()` ∪ 24 bare globals ∪
`thread_close`, the one `ThreadScheduler` name outside the bare-globals list). Excluding all 271
from the 1,262 static candidates leaves **997** names that are genuinely, currently unimplemented
by this project, by both signals.

**Runtime-count caveat (real, not cosmetic):** `verdict_stub_hits_with_missions.tsv` only logs a
"hit" for a call that reaches a *registered* stub/function. A call to a name with **zero**
registration raises an immediate Lua `attempt to call a nil value (global 'X')` error instead —
which usually kills that mission's thread right there rather than logging anything in that TSV.
That is exactly why every genuinely-unimplemented name below shows `runtime_call_count = 0` in the
default-mode TSV: the column structurally cannot see them. Where a deeper investigation already
measured this properly today, I cite it directly rather than re-running it myself (see
`character_is_in_vehicle` below) — `results/verify_probe_20261007/`, the raw output behind
`results/probe_blockers_ranked_20261007.md`, no longer exists in this worktree to re-derive from,
so I did not re-run `--probe-unresolved-names` myself this pass (budget; the top-level TSV already
regenerated fresh this session is the one this report's own join uses).

## What's genuinely unresolved / judgment calls (stated, not papered over)

- **The script-defined filter is a regex heuristic, not a parse.** 16,887 excluded names is too
  many to hand-verify; I verified the *mechanism* (checked `game_lib.lua` really does define
  several sampled names the way the filter assumes) but not every exclusion. Direction of risk:
  under-counting the tail of the ranked list, not over-ranking anything at the head — the top 20
  above were all independently confirmed present in `spec-*.md` by a second, different method
  (direct text search), which is a real check this report's own numbers are not resting on the
  regex filter alone for.
- **Call-site vs. bare-value reference is not distinguished.** luacheck's W113 fires identically
  for `foo(...)` and for a bare constant read; I did not re-derive which from source context for
  all 997, only spot-checked the top 20 against `spec-lua-api-behaviour.md`'s own "Arguments:"/
  "Body:" sections existing for each (which would not be written for a plain constant) — all 20
  check out as real function entries, not constants.
- **`results/verify_probe_20261007/`** (the raw per-mission probe data behind
  `results/probe_blockers_ranked_20261007.md`, generated earlier the same session) no longer
  exists in this worktree. I cited that document's own already-published number for
  `character_is_in_vehicle` rather than re-running the expensive `--probe-unresolved-names` pass
  myself; I did not attempt to recover or re-derive numbers for any other name that pass might
  also have surfaced.
- **This is one ranking, not the only defensible one.** Sorting by `files` (breadth across
  missions) instead of raw static call count would reorder this list somewhat (e.g.
  `game_is_active_input_gamepad` at 147 files/238 calls vs `trigger_enable` at 59 files/563 calls)
  — both are real, measured columns in the full data; I chose raw call-site count as primary
  since it is the literal column this task asked for, and kept `files` alongside for whoever wants
  to re-sort.
