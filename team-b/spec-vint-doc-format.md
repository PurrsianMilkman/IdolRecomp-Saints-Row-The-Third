### 1.2 Two formats exist in the executable; only one ever ships

The executable contains a real, complete, generic **text/XML-style document reader** (a TinyXML-shaped node-tree API) capable of expressing a `.vint_doc`/`.vint_xdoc` as authored markup, dispatched by a version/type-tag check (looking for a `vint_doc_type` node equal to the literal `vint_document`, or `vint_project` for the `.vint_xdoc` sibling, plus a `vint_doc_version` node equal to `1` or `2`). This is the **editor/authoring-format branch** — real and decompiled, but never observed in any of the 159 shipped files, exactly analogous to this project's own precedent elsewhere for a format variant the code supports but no shipped file actually uses. **Every real `.vint_doc` file is the separate, undocumented BINARY format** this whole document describes; the text/XML branch is noted here for completeness and is not otherwise covered.

**Review status (2026-09-30): DESK-PASS — desk review (not re-derived from the executable).**

Every real file begins with the identical leading 4-byte little-endian value. ## 2. File header

**[CONFIRMED — disassembly, cross-checked field-by-field against 159/159 real files via an independently-written parser.]** All fields are little-endian; offsets are from the start of the file. Two tiny, dedicated stream-reader primitives (a bounds-checked little-endian 32-bit read that advances an internal cursor by 4 bytes) do every field read described in this section and in §3/§4 below — there is no separate "header struct" read as one block; the reader is a simple sequential cursor over the whole file. **[2026-10-03, CONFIRMED — disassembly: the two 4-byte primitives are `0x007b2390` and `0x007b2420` (identical bodies; the second is the one used for float-typed fields); 1- and 2-byte fields are read inline by the same rule. The stream is three words {buffer start, buffer size, cursor}. Every read succeeds only when cursor + width is STRICTLY LESS than buffer start + size; a read that fails leaves the destination unchanged and does not move the cursor. So no primitive can consume a file's final byte. Shipped files never reach that limit, because the last section, the string table (§3.1), is read through a separate cursor and its character bytes are never read through a primitive. The reader is not one cursor over the whole file: the string table gets a second cursor that starts at header `0x16` (below).]**

Versions `1` and `2` are both real, live formats found in this one archive (155 v2 files vs. 4 v1 files) — not a deprecated/current split. The loader's own binary-reader function handles both through one code path, with a version-dependent extra byte read per critical-resource entry (§3).

**Whole-file section order (CONFIRMED — disassembly of `0x00e20500` + Team A loader-faithful walk 159/159, 2026-10-03):** fixed header (`0x00`–`0x1D`) → critical-resource entries (header `0x12` of them, §3.2) → metadata entries (header `0x0E` of them, §3.2) → top-level element records (header `0x1A`, §4) → top-level animation records (header `0x1C`, §4) → **at header `0x16`:** the string table (§3.1), running to end-of-file. Note that the critical resources are read BEFORE the metadata, although their count sits later in the header.

A given string-pool index is resolved as `base + offsetArray[index]`, where `base` is that recorded post-array cursor position — **not** the header's own `0x16` "secondary offset" field (an earlier validation attempt using the header field as the base produced systematically truncated strings, e.g. `ument_depth` instead of `document_depth` — the exact symptom of a wrong base; switching to the cursor-position base produced clean, correct strings throughout, e.g. `vdo_bitmap_viewer`, `RADIO STATION`, `640x480`, full sentence-length text, and literal file-name tails like `ards.vint_doc`).

**Not yet fully closed:** after correcting the base-pointer formula, roughly half the sample (85/159 files) still resolves under 90% of its own string-table entries to clean printable text; many of the remaining "bad" resolutions are short fragments (e.g. `grp`, `t_bar`, `_grp`, `sub_grp`, `menu_sub_grp` all appearing together in one file) that look like a **suffix-sharing string pool** — distinct table entries deliberately pointing partway into a longer stored string, so a string that is a literal suffix of another one isn't duplicated. This is a plausible, known space-saving technique and several such suffix chains line up cleanly, but it was **not** confirmed against the reader's own code this pass (doing so would require tracing exactly how an entry's own end is delimited, since there is no per-entry length field alongside the offset — presumably each string is still read as NUL-terminated at the moment it's needed). **[OPEN — exact string-pool boundary semantics / whether suffix-sharing is real, or whether some index↔offset pairings are still off for a subset of entries.]** This uncertainty does **not** affect the header, element-tree, or property-tag findings in §4/§5 below, all of which were validated independently of exact string content (by count, offset-boundedness, and tag-byte structure, not string text). **[OPEN — desk review 2026-09-30: no full-file (exact end-of-file) walk of the §4/§5 tree is recorded anywhere in this spec, and Team B's throwaway probes found none on `building_purchase.vint_doc` (see §4), so "validated independently of string content" covers the header and counts, not the whole tree; the pool's extent (from `base` up to where?) and its termination semantics are also unstated — to be settled against the executable (the string-array read and the string-by-index accessor; no addresses recorded yet) / real data (offset monotonicity, `offs[0] == 0`, gap between the furthest string end and header `0x16`).]**

**Correction, 2026-10-03 — CONFIRMED by disassembly of `0x00e20500` and the string-table reader `0x00e1fbe0`, with Team A's loader-faithful walk over 159/159 distinct documents.** The string table is NOT after the header. It is read through a second cursor placed at the absolute file offset held in header `0x16` (§2), and it is the last section of the file:

| Field | Size | Content |
|---|---|---|
| string count *N* | u32 | must be non-zero: with *N* = 0 the reader returns failure and the whole document load fails |
| pool byte length *L* | u32 | the size of the character data. The reader checks *L* + 4*N* ≤ the bytes remaining after this field and fails otherwise. This field was missing from the earlier text. |
| offsets | *N* × u32 | read one at a time with the 4-byte primitive into a buffer from the document's allocator |
| characters | *L* bytes | the pool base is the cursor position just after the offset array; string *i* is `base + offsets[i]` |

The string-by-index accessor is `0x00e1ed90`. It returns the address `base + offsets[i]` when *i* < *N* and a null pointer otherwise; it does no length check, so each string ends at its NUL terminator. The earlier base formula (the cursor just after the offsets) was right; the earlier position (`0x1E`) was wrong. With this layout, Team A's population check (`tools/harnesses/vintdoc_pool_check.py`) gives, over 159/159 distinct documents: `offsets[0] = 0`; offsets strictly increasing; the pool ends exactly at end-of-file; its last byte is a NUL; and every one of the 8,893 entries points at the START of its own NUL-terminated string (one stored string per entry; no entry points into the middle of another string; no repeated offsets). 8,888 of 8,893 are printable ASCII. So the "suffix-sharing" fragments described above, and Team B's contradiction findings, were artifacts of reading the table at `0x1E`. The words there are critical-resource entries (§3.2): Team B's "`0x1E` ∈ {0, 1}" is the first entry's selector byte, and `0x1F`–`0x22` is its u32 string index. **[Empirical figures are Team A's own run, not yet Team B's; to be cross-checked by `vintdoc_validate`.]**

**Review status (2026-09-30): NEEDS-EXE: string-pool extent/termination and the string-lookup function are unaddressed; base formula `0x1E + 4 + 4N = 0x22 + 4N` checks out (e.g. `0x426` for *N* = 257) — desk review (not re-derived from the executable).** **Review status (2026-10-03): position, layout, extent and termination CONFIRMED by disassembly (`0x00e1fbe0`, `0x00e1ed90`). The `0x22 + 4N` formula is withdrawn: the base is header[`0x16`] + 8 + 4*N*. Team A walk 159/159; awaiting Team B data.**

### 3.2 Critical resources and metadata — CONFIRMED structurally (disassembly), selector byte OPEN

Critical-resource entry: u8 selector, then u32 string index, then (version 2 only) a u8 flag. **Walk question (b) — what are the baseline/override byte-offsets measured from, and where does the main cursor resume? (answer for Team B, desk review 2026-09-30; ~~NOT CONFIRMED~~ CONFIRMED 2026-10-03, see the first bullet)**
- **Resolved 2026-10-03 — CONFIRMED (disassembly of `0x00e29860`, read in full; Team A loader-faithful walk 159/159).** Both offsets are **file-absolute**.   1. Read u32 *baseline*; if *baseline* ≥ file size, return.
