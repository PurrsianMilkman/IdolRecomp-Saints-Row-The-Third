## 3. What this means structurally

The registration table's five load-time shapes are now fully enumerated:

1. **Parse in the constructor** — most binary asset types.
2. **Stash-only** — morph 11/12, csc 24, ctdg 42, VINT doc 26, vehicle-customization camera 43 *(desk review 2026-09-30: `spec-format-inventory.md` §2 also lists types 9, 10, 13, 14 and 23 as stash-only, so this roster is incomplete; ctdg 42's constructor registers into a 330-slot CRC-32-keyed table, which §1 would call "register")*. The constructor records the buffer somewhere and a later subsystem parses it.
3. **Flag-variant thin constructor** — the PEG family, types 3/17/18 (`spec-texture-format.md` §7–§8).
4. **No constructor at all** — types 29/30/39/44/45 (`spec-ctorless-types.md`): the dispatcher skips the call and reports success.
5. **No extension at all** — the six here: never filename-resolved, constructed programmatically. **[OPEN — desk review 2026-09-30: contradicted by `spec-asm-format.md` §9.3, which shows all six ship real files with real extensions, picked by the manifest's `type_id`; see §1. What is established is only "no extension in the registration table".]**

Shapes 4 and 5 are independent: a type can have one, the other, or both (39 `Buffer` has both, and ships nothing at all). *(Desk review 2026-09-30: no file, but `spec-asm-format.md` §9.4 counts 2,447 type-39 manifest entries, each naming no file.)*

## 4. Correction: which hash is actually the engine-wide one

A call-site census of the three string hashes gives:

| Hash | Call sites | Where this project had seen it |
|---|---|---|
| Table-driven **CRC-32**, lowercased (`FUN_00d9e8b0`) | ~~**≈835**~~ **835** exact, from 398 functions plus 202 calls in code outside any defined function (corrected 2026-10-02, see below) | documented as the `.ctdg_pc` conversation-registry key |
| **Multiply-33 / XOR**, lowercased, `% buckets` (`FUN_00dab330`) | ~~**≈174**~~ **174** exact, from 143 functions plus 2 calls outside any defined function (corrected 2026-10-02, see below) | documented as the always-loaded texture registry's bucket function |

### 4.1 Not a fourth hash

Light Curve's 512-bucket index comes from `FUN_00dab2b0`, which looked like another string hash and is not one: it takes an **integer**, not a string, and applies a shift/XOR/multiply avalanche (`~(x<<15)+x`, `(x>>10 ^ x)*9`, `x ^ x>>6`, `x + ~(x<<11)`, `x>>16 ^ x`) before the modulo. It is a well-known **integer mixer** applied to an already-computed CRC-32, not a name hash. Checked precisely because its address sits `0x80` from the multiply-33 function and the assumption would have been cheap to make. **[CONFIRMED — disassembly.]** *(Desk review 2026-09-30: the five steps match the published 32-bit integer mixer of Thomas Wang step for step.)* **[OPEN — desk review 2026-09-30: not stated from the disassembly are 32-bit wrap, logical vs arithmetic `>>`, and an unsigned `% 512` (vs a signed modulo or `& 511`); these change the result when bit 31 is set. **[Re-derived 2026-10-02 from the executable (`FUN_00dab2b0`; its call at `0x008e631d` in the Light Curve constructor `0x008e6300`; the lookup `FUN_008e4db0`; the same read-only `calls` query as §4). The five-step structure is CONFIRMED, and every step is plain 32-bit register arithmetic, so each wraps at 32 bits. The open points, settled: (a) **Shifts.** All three right shifts (by 10, by 6 and by 16) are **arithmetic**: they copy bit 31 into the vacated high bits, so the value is treated as a signed 32-bit integer. The two left shifts are ordinary. The published mixer is normally written with logical (zero-filling) right shifts, so the desk review's "step for step" match is CORRECTED: the steps match in shape but not in this detail, and the detail matters. Over 200,000 random 32-bit keys, a version with logical right shifts put 50.1% of them in a different one of the 512 buckets. A reimplementation must shift right arithmetically to reproduce the engine's buckets. (b) **Modulo.** It is a **signed** division: the mixed value is sign-extended and divided by the second argument with the signed divide instruction, and the remainder is returned. There is no mask. (c) **Why the sign never shows.** The last step XORs the value with its own arithmetic shift right by 16; both operands carry the same bit 31, so the result always has bit 31 clear. The dividend is therefore never negative, and for a positive bucket count the remainder always lies between 0 and count − 1. For 512 the result is identical to an unsigned modulo 512, or to keeping the low 9 bits, of that same value. The modulo form is thus harmless; the shifts are what a reimplementation must get right. The 200,000-key check found no mixed value with bit 31 set. (d) **Light Curve's call** passes the CRC-32 key and a count of `0x200`, and the returned index is used unmasked to pick the bucket head (`FUN_008e4db0` reads the table's dword at +8 + 4 × index), which is safe only because the index cannot be negative.
