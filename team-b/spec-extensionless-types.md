# Saints Row: The Third — The Six Extension-less Registered Types

**Prepared by:** SPEC TEAM (cleanroom reverse-engineering process)
**Phase:** 1, the last block of registered-type work. These six were never on `spec-format-inventory.md` §6's target list *because* they declare no file extension — which is precisely the question this pass answers.
**Scope:** Types **25 `Lightset`**, **26 `VINT doc`**, **33 `Mission override table`**, **34 `Activity table file`**, **38 `Light Curve`**, **43 `Vehicle customization camera`** — how they receive data, what each does with it, and two corrections to previously-published claims that fell out of the work.
**Method:** All six constructors decompiled; a **recursive** census of every archive entry in the game (405,694, including inside `.str2_pc` bundles) to test whether extension-less files exist at all; and a call-site census of the engine's hash functions. Evidence: `tools/extless.txt`, `hash_sibling.txt`; harness `scratchpad/extless_files.py`.
**Cleanroom compliance:** No decompiled code or original identifiers. Quoted strings are shipped data; offsets and bucket counts are load-bearing.

**Confidence key**: **CONFIRMED — empirical**, **CONFIRMED — disassembly**, **HIGH CONFIDENCE — inferred**, **HYPOTHESIS — unconfirmed**, **OPEN / UNKNOWN**.

**Review status summary (2026-09-30)** — adversarial desk review (`review/adv_extensionless-types.md`), 12 units (§1; the six §2 rows; the §2 closing paragraph; §3; §4; §4.1; §5): **DESK-PASS 1** (§5); **DESK-PASS, text fixes applied 6** (§1, rows 26, 33 and 43, the §2 closing paragraph, §3); **NEEDS-EXE 5** (rows 25, 34 and 38, §4, §4.1); **NEEDS-DATA 0**; **VALIDATED-BY-DATA 0** (Team B has no reader for these six types and no full-population figure that covers them). A desk pass alone does not clear a unit: it means the text is internally consistent and agrees with the other specs, not that it was re-derived from the executable or data; only VALIDATED-BY-DATA units are already backed by Team B's full-population run, and this spec has none. **Cross-spec conflict:** `spec-asm-format.md` §9.3 (CONFIRMED — empirical, 805 manifests, 390,134 entries) shows all six types ship real files, picked by the manifest entry's `type_id`: 25, 33, 34 and 43 as `.xtbl`, 26 as `.vint_doc`, 38 as `.lightmult_pc`/`.lightrot_pc`/`.lightpos_pc`. This spec's "never filename-resolved / constructed programmatically" reading is therefore marked OPEN where it appears (§1, the §2 closing paragraph, §3 shape 5), and its CONFIRMED label in §1 is downgraded. **Awaiting the executable:** row 25 (`FUN_00599120`: consumer, argument test), row 34 (`LAB_006d13c0`/`FUN_006d08b0`: table, entry layout, cap), row 38 (`LAB_008e6300`/`FUN_008e5940`: table, collisions, parse routine), §4 (raw call counts of the three hashes, plus `FUN_00db09d0`), §4.1 (`FUN_00dab2b0` shift signedness and modulo); also the OPEN notes in §1 and rows 26, 33 and 43. **Awaiting real data:** the shipped type-25/26/33/34/38/43 manifest entries and files (names, counts, sizes), via the bridge.

## 1. Headline results

- **No extension-less file exists anywhere in the game.** A recursive scan of **405,694 entries** across all 38 archives *and* inside every `.str2_pc` bundle finds **zero** entries whose name has no extension. **[CONFIRMED — empirical, exhaustive.]** *(Desk review 2026-09-30: consistent with `spec-asm-format.md` §9.3, where these types' files all carry extensions; the absence of extension-less names does not by itself show that the types are never file-backed. The evidence files named in the front matter are not in this repository, so the census cannot be re-run from here.)*
- **So these six types are never resolved by filename.** They still take the normal `(name, buffer, size, …)` constructor signature and really do receive buffers — so they are **constructed programmatically**, by whatever subsystem already holds the data, rather than by the resource system resolving a path. The registration entry exists to give that data a type, a name and a lifetime, not to find it on disk. ~~**[CONFIRMED — disassembly + the exhaustive negative.]**~~ **[Label downgraded to OPEN, desk review 2026-09-30: `spec-asm-format.md` §9.3 (CONFIRMED — empirical) shows all six types ship real files with real extensions, picked by the manifest entry's `type_id` (25/33/34/43 `.xtbl`, 26 `.vint_doc`, 38 `.lightmult_pc`/`.lightrot_pc`/`.lightpos_pc`). "Never resolved by filename … constructed programmatically" is therefore contradicted as the load path for shipped data; the empty registered extension is simply not what finds them. Still CONFIRMED — disassembly: the constructors take the normal `(name, buffer, size, …)` signature. How a manifest file name reaches the dispatcher for a type with no registered extension is OPEN — to be settled against the executable / real data.]**
- **`FUN_00754410`, listed in the inventory as the destructor for nine types **[count corrected 2026-09-30: eleven — `spec-format-inventory.md` §2 lists it for IDs 2 and 8–14 by address and as "(no-op stub)" for 25, 33 and 43; see its §3]**, is a no-op** — its entire body is a return. It is also *called* as a labelled hook (e.g. with the literal `"Lightset"` and a size), so it is a **stripped instrumentation stub**, not a destructor. Those nine **[eleven]** types have no teardown at all. **[CONFIRMED — disassembly.]** **[Qualified, desk review 2026-09-30: what is confirmed is that the registered destructor is a no-op; whether teardown happens elsewhere is OPEN, as §5 item 5 of this spec asks.]**
- **All four load-time patterns this project has catalogued reappear here**, which is a good sign the catalogue is complete: parse-in-constructor (25, 33, 38), stash-only (26, 43), and register-into-a-hash-table (34, 38). *(Desk review 2026-09-30: this bullet names three patterns, §3 below lists five shapes with no separate "register" shape, and `spec-ctorless-types.md` §6 calls no-constructor the fourth. The numbering is not unified; read §3 as the list.)*
- **A breadth correction on the engine's hashes** (§4): the rotate-6/XOR hash this project has repeatedly called "the engine-wide string hash" has **18 call sites**. The table-driven CRC-32 has **835**. Calling the former engine-wide, relative to the latter, was backwards. *(Desk review 2026-09-30: the call-site counts are disputed; see §4.)*

**Review status (2026-09-30): DESK-PASS, text fixes applied (mechanism claim downgraded to OPEN per `spec-asm-format.md` §9.3; teardown claim qualified; count wording annotated) — desk review (not re-derived from the executable).**

## 3. What this means structurally

The registration table's five load-time shapes are now fully enumerated:

1. **Parse in the constructor** — most binary asset types.
2. **Stash-only** — morph 11/12, csc 24, ctdg 42, VINT doc 26, vehicle-customization camera 43 *(desk review 2026-09-30: `spec-format-inventory.md` §2 also lists types 9, 10, 13, 14 and 23 as stash-only, so this roster is incomplete; ctdg 42's constructor registers into a 330-slot CRC-32-keyed table, which §1 would call "register")*. The constructor records the buffer somewhere and a later subsystem parses it.
3. **Flag-variant thin constructor** — the PEG family, types 3/17/18 (`spec-texture-format.md` §7–§8).
4. **No constructor at all** — types 29/30/39/44/45 (`spec-ctorless-types.md`): the dispatcher skips the call and reports success.
5. **No extension at all** — the six here: never filename-resolved, constructed programmatically. **[OPEN — desk review 2026-09-30: contradicted by `spec-asm-format.md` §9.3, which shows all six ship real files with real extensions, picked by the manifest's `type_id`; see §1. What is established is only "no extension in the registration table".]**

Shapes 4 and 5 are independent: a type can have one, the other, or both (39 `Buffer` has both, and ships nothing at all). *(Desk review 2026-09-30: no file, but `spec-asm-format.md` §9.4 counts 2,447 type-39 manifest entries, each naming no file.)*

**Review status (2026-09-30): DESK-PASS, text fixes applied (roster completed by annotation; shape 5 marked OPEN) — desk review (not re-derived from the executable).**

## 4. Correction: which hash is actually the engine-wide one

A call-site census of the three string hashes gives:

| Hash | Call sites | Where this project had seen it |
|---|---|---|
| Table-driven **CRC-32**, lowercased (`FUN_00d9e8b0`) | **≈835** | documented as the `.ctdg_pc` conversation-registry key |
| **Multiply-33 / XOR**, lowercased, `% buckets` (`FUN_00dab330`) | **≈174** | documented as the always-loaded texture registry's bucket function |
| **Rotate-6 / XOR**, lowercased (`FUN_00da7890`) | **≈18** | documented as *"the engine-wide string hash"* |

The rotate-6/XOR hash is the **narrowest of the three**, not the broadest. Its documented uses — archive filenames, `.rig_pc` bone names, the foliage registry, `.ctdg_pc` speaker ids — are apparently close to its complete set of uses, which is consistent with an 18-call-site count. Meanwhile the CRC-32, which this project first met as one format's registry key, is the engine's general-purpose name hash by a wide margin. **[CONFIRMED — empirical call-site census.]**

This is the **third** revision of this claim (`spec-vpp-container.md` §2.2 has gone "exactly one" → "two" → "at least three"), and it is a different *kind* of revision from the first two: those added hashes, this one corrects the **relative breadth** of the ones already known. The phrase "engine-wide" should be dropped in favour of naming the actual uses.

*(Caveat on the numbers: these are Ghidra reference counts and include some call sites Ghidra could not attribute to a named function. The counts are reliable as orders of magnitude — 18 vs 174 vs 835 — not as exact totals.)*

**[OPEN — desk review 2026-09-30: hash-count conflict. `spec-rig-format.md` §13.1 reports a raw `CALL`/`JMP` flow scan of the whole `.text` that finds **12 callers** of `FUN_00da7890` (all listed), against **≈18** here (Ghidra reference counts, caveat above). Separately, `spec-texture-format.md` §10.6 attributes a rotate-left-6/XOR hash to a different address, `FUN_00db09d0`; if that is a second copy, this census undercounts the algorithm. The ordering (12 or 18) ≪ 174 ≪ 835 survives either way. To be settled against the executable: raw call and reference scans of `0x00da7890`, `0x00db09d0`, `0x00dab330` and `0x00d9e8b0`, plus a search for inlined copies.]** *(The CRC-32's initial value 0 and lack of a final XOR are given in `spec-save-format.md` §9.8.)*

### 4.1 Not a fourth hash

Light Curve's 512-bucket index comes from `FUN_00dab2b0`, which looked like another string hash and is not one: it takes an **integer**, not a string, and applies a shift/XOR/multiply avalanche (`~(x<<15)+x`, `(x>>10 ^ x)*9`, `x ^ x>>6`, `x + ~(x<<11)`, `x>>16 ^ x`) before the modulo. It is a well-known **integer mixer** applied to an already-computed CRC-32, not a name hash. Checked precisely because its address sits `0x80` from the multiply-33 function and the assumption would have been cheap to make. **[CONFIRMED — disassembly.]** *(Desk review 2026-09-30: the five steps match the published 32-bit integer mixer of Thomas Wang step for step.)* **[OPEN — desk review 2026-09-30: not stated from the disassembly are 32-bit wrap, logical vs arithmetic `>>`, and an unsigned `% 512` (vs a signed modulo or `& 511`); these change the result when bit 31 is set. To be settled against the executable (`FUN_00dab2b0` shift and divide opcodes, and its call in the Light Curve constructor).]**

**Review status (2026-09-30): NEEDS-EXE: shift signedness and modulo form — desk review (not re-derived from the executable).**
