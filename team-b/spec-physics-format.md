# Saints Row: The Third — Physics: Middleware Identification and the Collision-Geometry Container

**Prepared by:** SPEC TEAM (cleanroom reverse-engineering process)
**Phase:** 1, scoping pass (per `HANDOFF.md` §28.4/§28.5 item 4 — turning "AI/physics: statement of shape, not a finding" into a bounded result), immediately followed by as much depth as the evidence cleanly supported without crossing into third-party code.
**Scope:** Determine whether the game's physics simulation is Volition's own code or licensed third-party middleware (the same question the audio scoping pass resolved for sound with Wwise), and — since a genuinely Volition-owned, file-backed physics/collision artifact already existed as a named open item (`spec-geometry-format.md` §4.2's ~8 untraced `.clmesh_pc` sub-parsers) — characterize that artifact as far as it cleanly goes.
**Method:** (1) A raw-binary ASCII-string scan of `SaintsRowTheThird.exe` for physics-engine-suggestive literals, cross-checked against the PE import table (the same method the audio pass used to identify Wwise's `AK::` cluster). (2) Ghidra decompilation of the 8 named `.clmesh_pc` sub-parser addresses already on record, plus one adjacent function found in the process.
**Cleanroom compliance:** No decompiled code is reproduced verbatim below; all logic is restated in this document's own words. No original Volition (or Havok) identifiers are used as identifiers — Ghidra `FUN_xxxxxxxx` addresses are cited only as evidence. Class names and file paths quoted below (e.g. `hkpWorld`, `Havok version: %s`) are literal ASCII data recovered from the shipped executable, the same convention this project already applies to Lua hook names and `.xtbl` field names — they are third-party public API names, not anything invented or reproduced from Volition's own source.

**Confidence key** (as in prior specs): **CONFIRMED — empirical**, **CONFIRMED — disassembly**, **HIGH CONFIDENCE — inferred**, **HYPOTHESIS — unconfirmed**, **OPEN / UNKNOWN**.

## 1. Headline result: the physics simulation is Havok, third-party, out of cleanroom scope

**`SaintsRowTheThird.exe` statically links Havok Physics.** This is `CONFIRMED — empirical`, on the same evidentiary basis the audio pass used for Wwise (magic/class-name strings plus the import table), and is corroborated further by disassembly (§3).

**What was counted, and against what population:** a full-binary ASCII-run extraction (142,536 printable runs of length ≥ 4 out of a 16,257,024-byte executable) was searched for a fixed list of physics- and AI-middleware-suggestive literal substrings, and separately for two regex-shaped token families (`hk[A-Z]...`, `[NP]x[A-Z]...`) applied to every extracted run. A failing case for the Havok reading would have been: zero `hk`-prefixed class-name tokens, no exact Havok version string, no Havok source-tree paths, and a `havok*.dll`/`hkbase.dll`-style entry in the PE import table (the shape a *dynamically*-linked middleware would leave, as this project has not yet seen). None of that is what was found:

- **168 distinct bare `hk`-prefixed tokens** (Havok Common/Base — `hkBase`, `hkArray`, `hkReferencedObject`, `hkVector4`, `hkQuaternion`, `hkMatrix3`, `hkRotation`, …).
- **286 distinct `hkp`-prefixed tokens** (Havok **Physics** proper — the largest single bucket, e.g. `hkpWorld`, `hkpRigidBody`, `hkpAction`, `hkpAabbPhantom`, `hkpVehicleRayCastBatchingManager`, `hkpVehicleRayCastWheelCollide`, `hkpThinBox`, `hkpContactPoint`, `hkpRagdoll*`).
- **12 distinct `hkgp`-prefixed tokens** (Havok Geometry Processing — convex-hull tooling, e.g. `hkgpConvexHull`, `hkgpMesh`).
- An **exact version string**: `hk_2010.2.0-r1`, alongside the literal print-format string `"Havok version: %s\n"`.
- A **complete Havok SDK source path** baked into an assert/diagnostic string inside Havok's own compiled code: `D:\projects\sr3\pc_rc\sr3\src\game\havok\hk2010_2_0_r1\Source\Physics\Dynamics\World\hkpWorld.cpp` — which independently confirms the version string (`hk2010_2_0_r1`) and additionally shows *where* in Volition's own build tree the Havok SDK source lived (`sr3\src\game\havok\...`): vendored directly into the game's own source tree, the normal way a Havok source-code license is delivered and built.
- 471 distinct `hk*`-prefixed tokens overall, none of them coincidental English words (spot-checked; e.g. `hkClassNameRegistry`, `hkCpuJobThreadPool`).

**The PE import table (16 entries total) contains no physics-middleware DLL** — `WS2_32.dll`, `SHLWAPI.dll`, `binkw32.dll`, `steam_api.dll`, `IPHLPAPI.DLL`, `KERNEL32.dll`, `USER32.dll`, `GDI32.dll`, `ADVAPI32.dll`, `SHELL32.dll`, `ole32.dll`, `WSOCK32.dll`, `d3d9.dll`, `XINPUT1_3.dll`, `DINPUT8.dll`, `OLEAUT32.dll`. **This is the same shape as the audio finding**: Havok, like Wwise, is statically linked into the executable rather than loaded as a separate DLL, so its presence is provable only from string/RTTI-table evidence, never from the import table. **[CONFIRMED — empirical, exhaustive: this is the complete 16-entry import table, not a sample.]**

**Per this project's own standing rule** (`HANDOFF.md` §28.1, §28.4, and the task framing that motivated this pass): a licensed, publicly-documented middleware is **out of cleanroom scope beyond identification**, the same category this project already applies to Wwise, Bink (`binkw32.dll`), and the Inno Setup installer. **Havok's own internals are not investigated further in this document**, consistent with that boundary.

## 3. The Volition/Havok boundary, located concretely

Two real addresses illustrate exactly where "Volition's own code" stops and "Havok's own compiled library" begins — the same distinction the audio pass drew between the Volition-authored `IAkLowLevelIOHook` implementation and Wwise's own decoder internals.

- **`FUN_00bf81a0`** is **Volition's own code** — `CONFIRMED — disassembly`. It prints the literal diagnostic line `"Havok version: %s\n"`, then walks a per-frame timer array (an object at a fixed `+0x48`/`+0x4c` count/array-pointer pair) accumulating per-timer float samples into a running average, and conditionally prints two labelled ASCII-art report sections gated by two independent flag bits: `"Total Times"` (all timers summed) and `"Per Frame Time"` (a per-timer horizontal bar built by hand from `#`/space characters, scaled against the running average and clamped to a fixed 0x27-character width). This is unmistakably **a Volition-authored performance-profiling report over Havok's own per-frame timer data** — the kind of thin, engine-side instrumentation wrapper this project's audio pass found in the equivalent place for Wwise.
- **`FUN_00c1c4f0`** sits at the other side of the boundary: it is the function Ghidra's cross-reference search resolves as the sole referrer of the embedded assert-string `hkpWorld.cpp` path above. Given that string is Havok's *own* SDK source path (not a Volition string), this function is very likely **inside Havok's own compiled `hkpWorld` code** — `HIGH CONFIDENCE — inferred`, not traced further, consistent with the standing rule that Havok's own internals are out of scope.

**This pair is the concrete evidence for where the cleanroom boundary actually falls in this binary**: Volition-authored wrapper/instrumentation code around Havok (in scope, and `FUN_00bf81a0` is a legitimate future target if Havok integration specifics ever matter) versus Havok's own statically-linked library code (out of scope, and not pursued past this identification).

## 4. The in-scope Volition artifact: `.clmesh_pc`'s ~8 sub-parsers, characterized

`spec-geometry-format.md` §4.2/§6 item 6 already established that `.clmesh_pc`/`.glmesh_pc` ("Level Mesh"/"Level Mesh Collision", registered types 31/40) is a **Volition-owned container format**, structurally parallel to but not identical with `.ccmesh_pc`, with its own magic (`0x4fe66afa`), exact version requirement (`20`), and fixed `0x140`-byte header — and left the ~8 sequential sub-parser functions it calls (`FUN_007499d0`, `FUN_00749b40`, `FUN_00749ba0`/`FUN_00748c70`, `FUN_00749c40`, `FUN_00749cf0`, `FUN_00749d40`, `FUN_00749e80`) as identified-by-address but untraced. This is the one collision-adjacent gap in the project with a real file behind it, and it is now traced. **[CONFIRMED — disassembly, all 8 functions decompiled in full.]**

### 4.1 The shared idiom

Every one of the 8 functions follows the same shape already established for `.ccmesh_pc`'s six-array structure (`spec-geometry-format.md` §4.1): given a **hidden cursor argument threaded by register** (dropped by the decompiler at every call boundary, exactly the pattern already documented for `.ccmesh_pc`'s two-cursor threading) and the fixed-header object's own base address, each function:

1. ~~16-byte-aligns the cursor~~ **16-byte-aligns the cursor, but only when the array about to be walked is non-empty — an unconditional align is wrong, §4.4.2(a)** (the same `cursor & 0x8000000f` signed-modulo idiom used throughout this project's other array-walking code),
2. reads a **count** already stored in the fixed `0x140`-byte header (at a fixed offset specific to that function, all offsets falling within `0x40`–`0x10c`, i.e. inside the header itself),
3. records the cursor position (plus the file's base offset) as a resolved **pointer**, writing it back into another fixed header slot,
4. advances the cursor by `count × stride`.

This is the header-populate-in-place pattern: the fixed `0x140`-byte header is not fully-populated data on disk — most of its trailing fields are **count fields that gate variable-length arrays following the header**, and the "sub-parsers" are what turns raw counts into usable in-memory pointers, exactly mirroring `.ccmesh_pc`'s six outer arrays but with a richer, more deeply nested set of shapes.

⚠ **Correction (2026-09-13, §4.4): this is NOT one shared idiom threaded through a single continuous cursor.** The chain is genuinely three parts — a HEAD, ~~an opaque MIDDLE whose size nothing in this document establishes, and a TAIL that must be found by search~~ **a MIDDLE, and a TAIL** — and a spec-literal single-cursor walk lands correctly on 0 of the full 100,384-entry shipped population, confirmed complete 2026-09-13 (§4.4.3). Steps 1–4 above remain correct *within* a part; step 4 does not carry a cursor value across the MIDDLE. See §4.4 for the exact boundaries, population validation, and five further refinements. ⚠ **Updated 2026-09-13 (§4.4.6): the MIDDLE is sized and the TAIL is no longer searched for — the three parts are now walked by one continuous computed cursor, 100,384/100,384 exactly on EOF. The "three parts" division is still the right mental model (each part is a different kind of structure), but there is no longer any discontinuity in the cursor.**

##### (a) The first thing to correct: `thunk_FUN_00e3e590` is not a reference resolver

§4.2's `FUN_007499d0` row and §4.4.1 both frame `+0xb8` as "one more single reference" resolved by a thunk, by analogy with array 1's `FUN_00e718b0`. **That framing is what made the gap look unclosable, and it is wrong.** The stub is `thunk_FUN_00e3e590` at `0x00e3e770` (an unconditional jump to `FUN_00e3e590` at `0x00e3e590`); it has **exactly one call site in the whole binary**, `0x00749b1f` inside `FUN_007499d0`, versus `FUN_00e718b0`'s eight. It is **not** a member of the generic 8-caller resolve-and-hand-to-a-singleton family at all, and it does not resolve anything: it is a **parser one layer above that family**, in the same `0x00e3xxxx` module as `FUN_00e3c4e0`/`FUN_00e3c6e0`/`FUN_00e401d0`/`FUN_00e40210`, and it *calls into* `FUN_00e718b0`/`FUN_00e71910` two levels down. What it returns is simply **the address of a `0x50`-byte record it just claimed at the 16-aligned cursor inside the file** — which is why `+0xb8` reads zero on disk: the slot is an output for a pointer *into the file's own bytes*, and the entire payload is laid down inline immediately after the record.

So the answer to "does the generic resolution mechanism carry or compute a size" is: **the question does not apply.** No size is carried, hidden, or looked up anywhere. The MIDDLE's length is produced the same way every other length in this format is — by the cursor advance of a sub-parser walk — and the only reason §4.4.1 could not size it is that this particular walk had never been traced. **[CONFIRMED — disassembly, exhaustive xref check on both functions.]**

##### (b) The formula

All functions below are decompiled in full. `align_n(x)` rounds `x` up to a multiple of `n`; `u32(p)` reads a little-endian `u32` at file offset `p`. `cur` enters at `headEnd` (§4.4.1, corrected formula).

```
MIDDLE(cur):                                    # thunk_FUN_00e3e590 -> FUN_00e3e590
  cur = align16(cur)
  R = cur ;  cur += 0x50                        # the record whose address lands in +0xb8
  if u32(R) == -1: return cur                   # abort path; never taken, 0/100,384
  cur, H = MATSET(cur)                          # FUN_00e40210
  cur = align8(cur) + u32(H) * 8                # R[+0x08] array: one 8-byte entry per material
  cur = GROUPS(cur, R)                          # FUN_00e3c6e0
  return cur

MATSET(cur):                                    # FUN_00e40210, the material-set block
  cur = align8(cur) ;  H = cur                  # 0x20-byte header
  cur = align16(H + 0x20) + 1                   # name table: 16-aligned, then ONE extra byte
  if u32(H+0x10) != 0: cur += u32(H+0x10)       # +0x10 = name-table length in bytes
  cur = align8(cur) + u32(H) * 8                # +0x00 = material record count; one slot each
  repeat u32(H) times:  cur += u32(cur)         # FUN_00e71090: each record's OWN declared size
  return cur, H

GROUPS(cur, R):                                 # FUN_00e3c6e0
  cur = GROUP(cur)                              # FUN_00e3c4e0, always
  if u32(R+0x18) != -1: cur = GROUP(cur)        # second group; taken 100,384/100,384
  cur = align8(cur) ;  A = cur ;  cur += u32(R+0x20) * 0x10
  for i in 0 .. u32(R+0x20)-1:
      cur = align8(cur) + u32(A + i*0x10 + 8) * 0x20      # count at +0x08, ptr slot at +0x00
  cur = align8(cur) ;  B = cur ;  cur += u32(R+0x30) * 0x10
  for i in 0 .. u32(R+0x30)-1:
      cur = align8(cur) + u32(B + i*0x10 + 0) * 4         # count at +0x00, ptr slot at +0x08
  if u32(R+0x48) != 0: cur = align16(cur) + u32(R+0x48) * 0x34
  return cur

GROUP(cur):                                     # FUN_00e3c4e0, one render-mesh group
  cur = align16(cur) + 0x60                     # 0x60-byte group header
  cur, n = IDXLIST(cur)                         # FUN_00e401d0
  cur = MESH(cur)                               # FUN_00e71410, c-side
  cur = align8(cur) + n*2 + n                   # a u16 array then a u8 array, no align between
  return cur

IDXLIST(cur):                                   # FUN_00e401d0, generic index list
  cur = align8(cur) ;  L = cur ;  n = u32(L+8)
  return cur + 0x10 + n*4, n

MESH(cur):                                      # FUN_00e71410 c-side, self-validating
  require u16(cur) == 9                         # the shared 'Mesh' sub-block version word
  q = align4(cur+2) ;  chk = u32(q) ;  cLen = i32(q+4)
  require u32(cur+cLen-4) == chk                # bookend copy of the check value
  return cur + cLen                             # EXACTLY cLen, no rounding on either side
```

Note the two asymmetries, both real and both load-bearing: `GROUPS`' first nested array holds its per-entry count at `+0x08` with the pointer slot at `+0x00`, and its second holds the count at `+0x00` with the pointer slot at `+0x08`; and `MATSET`'s name table starts at `align16(H+0x20) **+ 1**`, the leading-NUL convention `spec-tree-format.md` §6 item 2 already documents for this same shared block. **The only quantity in the whole formula that is not either a disassembly constant or a field read out of the file is the format's own already-known `0x140` header size.** **[CONFIRMED — disassembly, all seven functions decompiled in full.]**

`MESH`'s `cur + cLen` is the same fact `§4.4.4` established empirically for consecutive array-1 blocks ("+0, no rounding either side"), now read directly out of `FUN_00e71410`'s own closing self-check (`(cursor - startCursor) == cLen`, alongside the bookend compare) — so it is a property of the block, not of `.clmesh_pc`'s use of it, and it holds at the two further sites inside `FUN_00e3c4e0` as well.

##### (c) What `+0xb8` actually points at, and why its two consumers look the way they do

The task of sizing this region turned out to be the same task as identifying it, and the two documented downstream readers name it exactly:

- `R[+0x00]` receives **the material-set block's header `H`**, and `H[+0x00]` is the **material record count**. `FUN_00749e80`'s "non-null and non-empty" gate (§4.2) is literally `R != 0 && R[0] != 0`, i.e. *the material set resolved and has records*.
- `FUN_0074a110`'s "lookup-table bound" is, in disassembly, `*(*(header+0xb8))` — `H[+0x00]`, the material count — and the table it indexes is `(header+0xb8)[2]`, i.e. `R[+0x08]`'s `count × 8` array, with `FUN_00e3fcb0` resolving each 8-byte element to a runtime material handle. Both quantities are terms in the formula above. **The consumption pattern really was the clue: the bounds-checked lookup table is the material set, and the bound is the material count.** **[CONFIRMED — disassembly, `FUN_0074a110` read directly.]**
- The same bound appears a second time at load: `FUN_00e3c4e0`'s own remap loop rejects `idx >= materialCount` and then indexes the remap array — the identical relationship, one layer down.
- `FUN_00e3fcb0` and `FUN_00e3ffd0` themselves carry no bound and no size: the first is a name/hash → handle cache (hash via `FUN_00e7a520`, `% 0x5000`, bucket table `DAT_02b2a958`, miss path `FUN_00e3faa0`), the second a free-list pop off `DAT_0132d7f8`. They were the wrong place to look for the table's shape; `FUN_0074a110`'s own bound expression was the right one.

- **`+0x30` (byte, bit `0x04`): an "active at this LOD tier" flag.** Found in `glmesh_ctor_FUN_0074c530`, gated by its own separate threshold global (distinct from item 2's):
  ```
  gate: DAT_012f7784 > 0  &&  DAT_012f7784 <= FUN_00748d10()

  ```
  `FUN_0074c2b0` is a genuine **introsort** — own recursive structure, element stride `0x34` (matching the trailer exactly), a `0x20`-element insertion-sort cutoff, a recursion-depth budget halved-plus-quartered per level, and a heapsort fallback once that budget is exhausted: the standard MSVC STL introsort shape, decompiled in full this pass (`tools/phys4_sort_clean.txt`). **Three causes fully explain the ~1,417-failure gap; none of them is a format or data bug in the common case.**

1. **A real g-file mispairing bug in the initial reproduction's own lookup — minor effect.** The lookup keyed `.glmesh_pc` candidates on `(archive, bare filename)` with plain dict assignment; the same stem recurs at many `str2_pc` bundle locations within one archive (8,545 `(archive, stem)` collisions on the c-side alone, e.g. `terminal_sign_c~l1.clmesh_pc` at 8+ bundle paths in `sr3_city_0.vpp_pc`), so many c-files were checked against the wrong same-named g-file copy. 2. **The dominant cause: `mesh_scan.py`'s `validate()` only tries 16-byte-aligned g-file offsets, but a chain's second-and-later Mesh sub-blocks almost never start on one.** Hand-traced byte-for-byte with zero slack on four independent files spanning three asset families and chain lengths 2/2/4/14 — `bank_floor4_destroy.clmesh_pc` (`sr3_city_0`, `n48=14`), `hotel_complex.clmesh_pc` (`sr3_city_1`, `n48=2`, one of Team B's own two named Class-3 files), `terminal_sign_c~l1.clmesh_pc` (`sr3_city_0`, `n48=4`), `diner_wall_2_a01.clmesh_pc` (`dlc3`, `n48=2`): block 0's g-segment starts at g-offset 0 (16-aligned, found correctly by the existing search); every later block's segment starts **exactly** where the previous block's own channel-walk replay ended — zero padding, not even 4-byte alignment. On all four files, every block's predicted continuation offset (checkval match + `replay_g()` length exactly equal to the declared `g_len` + matching bookend) landed with **zero slack**, at chain lengths up to 14. Because a chain's continuation offset is essentially never itself a multiple of 16, `validate()`'s `i % 16 == 0` gate throws away the one correct candidate before ever testing it — a search-harness bug, not a cursor-formula bug: the c-side stepping (`phys_mid.py`'s `mesh_block()`, already disassembly-confirmed, §4.4.4) needed no correction at all, and it is the g-side abutment that mirrors it exactly (the same "zero padding between consecutive blocks" fact §4.4.4 already established on the c-side, now confirmed on the g-side too — the internal per-channel `align16` calls inside a block's own replay are computed against the *absolute* g-file offset, not an offset relative to the block's own start, which is what makes a non-16-aligned block start reproduce byte-exact regardless). This explains every failure in both the original draft and the bundle-path-fixed rerun: 100% of them were at chain index ≥ 1, never index 0 — exactly the population this bug drops. `mesh_scan.py` itself was left unmodified (it is shared by five other carrier-format pairs whose published results are out of scope here); `tools/harnesses/clmesh_refcheck.py` instead does its own chain-aware g-side walk scoped to `.clmesh_pc`/`.glmesh_pc`.

All 11 c-file copies chain-validate perfectly, with zero slack, against that single shared g-file. This is consistent with this project's own already-documented generic name-based resource dispatch (`spec-resource-dispatch.md`) rather than a per-bundle-scoped file read, and was confirmed identically for `ceilingventa~l1`. `clmesh_refcheck.py` resolves this correctly via a same-archive, same-stem fallback (tried only after the same-bundle path fails; never across archives).

**Full decompile** (`tools/749da0_dump.txt`, `tools/gp_phys6`), restated below in plain English per this project's cleanroom convention rather than reproduced verbatim. The function returns a 4-byte value and takes five parameters, `param_1`–`param_5` (mapped to their roles in the table below):

If the selected group's own inner count — read via the resolved pointer array at `param_1`'s header offset `+0x100`, indexed by `param_2` — is zero, the function skips the whole loop below and goes straight to computing its return value. Otherwise, starting a running index at `0`, it repeats the following for each of that count's entries:

1. Reads the entry's own `u32` key from the resolved pointer array at `param_1`'s header offset `+0x108` (again indexed by `param_2`).
2. If `param_4` (the `+0xd8` array's own element count) is zero, the entry's corresponding 16-byte output record — in the output array based at `param_5 + 4` — is zeroed outright and the function moves on to the next entry.
3. Otherwise it linearly scans all `param_4` records of the `+0xd8` array (each record shaped `{u32 id, u16 fieldA, u16 fieldB}`, 8 bytes, reached via `param_3`), comparing each record's own leading `u32 id` field against the key. **The scan does not stop at the first match** — it continues to the end of the array, so the LAST matching record wins if more than one matches.
4. On any match, both of the matching record's `u16` fields are passed through `FUN_007549c0` (which resolves each to a runtime pointer), and the two resolved pointers are written into the entry's own 16-byte output record as `{resolved-from-fieldA, 0, resolved-from-fieldB, 0}`. If no record matched, the whole 16-byte output record is zeroed instead.
5. The running index advances by one and the output-record cursor advances by 16 bytes; the loop repeats until the running index reaches the group's own inner count (re-read from `+0x100` at each iteration).

The return value packs the final running-index count into its upper three bytes and a constant `1` into its low byte — so the low byte, the only part any caller checks, is always `1`.

## 7. Methodology note for `HANDOFF.md` §5

**Combine a raw-binary string scan with a Ghidra-defined-data string search — they catch different things.** The raw Python byte-scan found `havok` as a substring 37 times and the exact version token `hk_2010.2.0-r1`, but a second, separate query for the literal substring `\src\game\havok\havok.cpp` (guessed from the raw scan's truncated context window) came up empty — the real string was several times longer (`D:\projects\sr3\pc_rc\sr3\src\game\havok\hk2010_2_0_r1\Source\Physics\Dynamics\World\hkpWorld.cpp`) and was only found by asking Ghidra's own defined-data iterator for a *shorter, more distinctive* substring (`hkpWorld`) and reading whatever full string it was embedded in, rather than by guessing the full string from a byte-window context snippet. **When a raw scan's context window truncates a promising string, don't guess the rest of it and re-search for the guess — pick the shortest confident substring instead and let the real string come back whole.**

**A document's own framing of an open gap can be the thing keeping it open (2026-09-13, §4.4.6).** This file described `+0xb8` as "one more single reference resolved via `thunk_FUN_00e3e590`", by analogy with the array-1 slot next to it, and then asked what that resolver returns. Three of that sentence's four load-bearing words were wrong: `thunk_FUN_00e3e590` has one call site engine-wide (not eight), belongs to a different module, resolves nothing, and is a *parser* sitting one layer **above** the resolver family it was grouped with. As long as the question was "what size does the resolution mechanism carry", it had no answer — because no resolution was happening. **The unlock was reading the thunk from scratch instead of reasoning forward from the document's own characterisation of it.** Generalisable form: when a gap has survived several passes, re-derive the *one sentence that defines it* before spending effort inside it — an inherited analogy ("this is like the one next to it") is exactly the kind of claim that gets written once and then never re-checked. Same family as §5's "an offset without an explicit base is not a location", one level up: **a mechanism named by analogy is not a mechanism identified.**

**A control that a downstream alignment absorbs is not a control (2026-09-13, §4.4.6(e)).** §4.4.5 recorded the `+0x78` gated-pair byte cost as "not measurable from shipped data", having found that 0/4/8/12/16/20 bytes all land identically. The measurement was not wrong, but its conclusion was an artifact of the instrument: a 16-byte align downstream swallows any 0–15-byte shift, and a *searched* tail start swallows the rest. Once the tail stopped being searched, substituting `0` dropped the population landing from 100,384/100,384 to 89,192/100,384 and the same quantity became trivially measurable — it is a size field in the block. The first `±4`-byte tail-shift control in this pass had the identical defect and reported the baseline's own score until it was widened to `±16`. **Before citing a null result from a perturbation, check what absorbs the perturbation; size the perturbation to exceed every slack term between it and the observable.**

**Verifying a Ghidra write: `getBookmarks(Address, String)` takes a bookmark TYPE (`"Note"`), not a category.** Querying it with a category name returns 0 on bookmarks that were written correctly — a clean false negative, hit once while writing this pass's own verification script, and caught only because the plate comments at the same nine addresses reported 9/9. Iterate `getBookmarksIterator("Note")` and filter on `getCategory()`. Same family as §5's standing "a verification that reports failure can itself be the bug".
