HONEST RESULT (the central finding of this scene, stated plainly, not hidden
behind a prettier framing): the final composited image is a real, correctly-
projected, correctly-textured-at-the-G-buffer-stage, but visually FLAT BLACK
silhouette of the drawable geometry (the tower's metal support shaft + the
hangar door) against the CHOSEN dark clear colour. This is a MEASURED,
deterministic consequence of applying this tool's OWN already-established
real-confirmed-zero-when-unauthored convention faithfully to every named CTAB
constant this session found no real per-material source for (Diffuse_Color,
Object_instance_params, Specular_Color, Specular_Map_Amount,
Self_Illumination at the material stage; Normal_Map_TilingU/V at the
G-buffer stage) - per this task's own explicit instruction NOT to invent a
new fallback rule beyond the one pre-existing Tint_color exception. This
tool's own NEW printTargetStats() diagnostic readback (run every time,
printed in baseline_stdout.txt) proves the pipeline is still genuinely
exercised end-to-end even though the final colour is black: the G-buffer's
own lighting-parameter target really does carry the real Specular_Power 0.1
floor (measured R channel 0..1/255, matching max(0.1/512,1/256)'s real
encode exactly), and the light-accumulation buffer really does carry the
real noon/Overcast weather-row colour run through the real shader math
(measured uniform (21,46,65,91) - uniform because the G-buffer normal
feeding it is itself uniform, for the Normal_Map_TilingU/V=0 reason above,
not because the light math itself is fake). sr3clmesh::LevelMesh::
MaterialRecord's own `constantNameCount`/`vec4ConstantCount` fields
structurally resemble vehicles' already-proven per-material array-B/C
constant mechanism and are a concrete, testable lead for recovering real
Diffuse_Color/Specular_Color/etc. values in a follow-up session, but
decoding a new part of this binary format is a separate investigation this
task's own "don't invent a new fallback rule" instruction rules out
attempting here - left OPEN, not chased, not silently patched over.

Why NOT the render-everything-at-any-cost alternative: forcing a non-zero
value into Diffuse_Color/Specular_Color/etc. without a real source would be
exactly the "invented fix" this project's own operating discipline (and this
task's own item 5) explicitly rules out - a nicer-looking PNG built on a
fabricated number is worse than an honestly dark one built on real data only.
