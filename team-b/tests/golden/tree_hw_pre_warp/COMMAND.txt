WHAT CHANGED AND WHY (the actual task: HANDOFF Sec9.120's own Addendum flagged
that st_pine_tall has 4 materials present but the frozen render showed only
material 0's trunk/branch geometry, because tree_baseline_render.cpp hardcoded
drawing only "draw group 0" of the LOWEST-INDEX PRESENT LOD SLOT)
============================================================================

THE ADDENDUM'S OWN GUESS WAS MEASURED, NOT ASSUMED, AND TURNED OUT TO BE SUBTLY
WRONG IN WHERE THE OTHER MATERIALS LIVE - stated plainly because getting this right
mattered more than confirming the guess: the Addendum's own wording ("leaves/needles
almost certainly live in one of the other 3 present materials' own draw range(s)")
reads as if all 4 materials' ranges sit inside ONE Mesh sub-block's own draw-group
array (the same shape sr3_viewer's `vehicle` command already handles - many ranges,
several materials, one group). A real diagnostic dump of st_pine_tall's raw
structure (every LOD slot's every draw group's every range - a throwaway scratch
tool built for exactly this check, not guessed from the spec) shows a DIFFERENT real
shape:

  Tree-level LOD slot 0 (present, layout code 11, 1710 elements, 3 internal draw
    groups): EVERY range of EVERY group has materialId=0. Textures: Bark_01_D/N/S -
    this is the TRUNK (the "trunk/branch" label Sec9.120's Addendum used for
    material 0 is half right - it is trunk ONLY; see slot 1 below for branch).
  Tree-level LOD slot 1 (present, layout code 12, 153 elements, 1 draw group, 1
    range): materialId=1. Textures: Branch_01_D/N. This is the BRANCH geometry -
    a SEPARATE Mesh sub-block from the trunk, not an extra range inside slot 0's
    own group array.
  Tree-level LOD slot 2 (present, layout code 11, 2728 elements, 3 internal draw
    groups): EVERY range of EVERY group has materialId=2. Textures: pineneedles_D/
    N/S. This is the NEEDLE geometry this task exists to surface.
  Tree-level LOD slot 3: NOT PRESENT in this tree's shipped data at all (checked
    directly: `tree.lodSlots()[3].present == false`). Material 3 (textures
    common_bb_D/N - the "common billboard" impostor) therefore has NO decoded
    geometry anywhere in st_pine_tall to draw - a real, evidenced DATA ABSENCE, not
    a decode failure or a bug in this render tool. This is consistent with (not a
    new finding beyond) spec-tree-format.md Sec7's own already-flagged HYPOTHESIS-
    tier, no-known-reader impostor/billboard atlas structure - still not built on
    here, still not guessed at.

So the real, structural rule this task found (measured on st_pine_tall specifically -
not claimed as a general population statistic across all 11 shipped trees, which
would need its own separate census) is: EACH PRESENT TREE-LEVEL LOD SLOT IS A
SEPARATE MESH SUB-BLOCK BOUND TO EXACTLY ONE MATERIAL, not "one mesh whose group
array partitions several materials". "Draw all the real materials this tree's data
has" therefore means: draw group 0 of EVERY PRESENT LOD SLOT, not search harder
inside one LOD slot's own group array. That is the actual code change.

WHY THIS IS NOT THE "DIFFERENT, UNDECODED LAYOUT CODE" DEAD END THE TASK BRIEF
WARNED ABOUT: checked directly before writing a single line of drawing code, not
assumed - LOD slot 0 is layout code 11 (known=true, decoded since Sec9.120), LOD
slot 1 is layout code 12 (known=true, decoded since Sec9.120), LOD slot 2 is layout
code 11 again (known=true). All three present slots decode successfully
(decodeChannel(0) returns real, in-bounds vertex data for all three - independently
exercised with a scratch diagnostic tool before this baseline was captured). No
`known=false` layout code was ever on the path to drawing the leaves/needles here,
so the task's own "stop, do not guess" branch was never triggered.

CODE CHANGE (tools/tree_baseline_render.cpp only - no sr3mesh/sr3tree reader
touched): the tool's default (no `--lod` override) now collects EVERY PRESENT LOD
slot (ascending) instead of just the lowest-index one, builds ONE
sr3render::MeshRenderer PER SLOT (each slot is a distinct Mesh sub-block - own
vertex/index buffers, in general a different layout code/element count - so one
upload() call cannot span more than one slot), uploads each with the SAME
drawGroup=0 convention the tool always used, and draws all of them into ONE shared
render target + depth buffer (only the FIRST slot's renderer owns the depth buffer;
every later slot's draw() call relies on that same view, bound externally by the
caller) - the identical compositing pattern tools/sr3_viewer.cpp's
MultiChannelMultiSetRender already uses for the analogous multi-channel character-
mesh problem (HANDOFF Sec9.105), adapted here to multiple LOD-slot Mesh sub-blocks
instead of multiple channels of one Mesh sub-block. The camera now frames the
COMBINED bounding box across every rendered slot (not just the first), so the whole
tree - not just whichever part happened to be uploaded first - fits in frame.
`--lod N` still works exactly as before (draws exactly that one slot, isolated) -
unchanged single-slot behaviour, useful for inspecting one part alone; the golden
scene itself does not use it (matches the prior baseline's own command line).

ALPHA-BLENDING / DOUBLE-SIDED HONEST LIMITATION (task brief's own anticipated
caveat, confirmed real, not hypothetical): pine needle geometry is real triangle
mesh here (not billboards - the needle "cards" are actual 3D wedge shapes, 550 real
triangles), but this renderer draws every material with the SAME opaque, single-
sided pipeline state every other MeshDrawMode already uses (see
sr3render::MeshRenderer's own header comment - milestone-3 scope, no per-material
blend/cull state). Sec9.120's own Checker-mode render already shows this is enough
to see real geometry clearly; a production-fidelity render of thin, possibly-
double-sided foliage cards would additionally need alpha-blend and/or two-sided
rasterizer state THIS RENDERER DOES NOT HAVE - not attempted here, per the task's
own explicit instruction to report this as an honest limitation rather than build a
new rendering feature. The needle geometry in baseline_render.png is real, undistorted
positions - what is NOT attempted is production alpha/double-sided shading of it.
