THIS BASELINE'S CORE FIELD (POSITION) IS HIGH CONFIDENCE, NOT CONFIRMED - stated
plainly here, not smoothed over (spec-vertex-format.md Sec12.12):
  Position (FLOAT16x3 at channel offset +0) is empirical, full-population (code 11
  specifically: 28,423/28,457 vertices in-bounds against each tree's own real bbox,
  22/22 channels individually >=90%), independently reproduced twice, non-denormal,
  correctly scaled against this exact tree's own real bounding box (see the sanity
  check above) - the strongest evidence this project currently has for it. But it
  stops short of CONFIRMED for two honest, UNRESOLVED reasons this baseline inherits
  rather than hides:
    1. No CPU/GPU consumer of this exact byte range has been found anywhere in the
       disassembly (spec Sec12.9.1's existing finding - neither Mesh-block walker
       dereferences an individual vertex field's content for these codes - extends to
       this byte range too). This is empirical/statistical confidence, not
       disassembly-confirmed against a real reader.
    2. Offset +0 and offset +16 are ~70% byte-identical cross-channel duplicates
       (spec Sec12.9.7), with an existing, STILL-OPEN hedge that this pair could be
       runtime-populated/stale content rather than authored per-vertex data. This
       FLOAT16 finding is NEW EVIDENCE TOWARD "real, authored data" (a coherent,
       correctly-scaled, recognisable tree silhouette falls directly out of it - see
       baseline_render.png itself) - it does NOT resolve that tension or disprove the
       "stale" explanation.
  Normal (+8, UBYTE4N xyz) and Tangent (+12, UBYTE4N xyz + handedness sign in the 4th
  byte) ARE CONFIRMED (spec Sec12.9.5/Sec12.10.2 - the same confirmed offsets already
  established earlier the same session, per HANDOFF's own resume note) - only Position
  carries the lower tier on this baseline. This is a visibly DIFFERENT, LOWER
  confidence tier than the zone_tile golden scene's own Position field (layout code
  24, spec Sec12.3, full-population CONFIRMED, 581,647/581,647) - do not read this
  baseline as being on the same footing as that one. zone_tile's own COMMAND.txt
  caveats its unread +16 slot; this baseline goes one step further, because here the
  caveat sits on the scene's own CORE geometry field, not a side slot.

What this reader deliberately never touches (skip/reserved, not decoded into any
Vertex field - see src/mesh_block.cpp's layoutInfoFor() case 11/12/13 and
decodeChannel()'s own cursor-arithmetic comments for exactly how the cursor steps over
these bytes without reading them): the 2-byte gap between Position and Normal
(channel offset +6..+8, UNKNOWN, not investigated by this task's own scope); the
near-duplicate FLOAT16x3 repeat at +16..+22 (the SAME byte range caveat 2 above is
about - read once, at +0, deliberately never a second time into a second Vertex
field); and 10 further UNKNOWN bytes at +22..+32. These gap sizes (2 + 6 + 10 = 18
bytes total, expressed as two separate LayoutInfo fields:
reservedBytesAfterPosition=2 before Normal, reservedBytes=16 after Tangent) were
independently re-derived from the real 36-byte stride and the real +8/+12
Normal/Tangent offsets, not assumed from any brief's own sketch of the layout - they
check out exactly: 6 (position) + 2 (gap) + 4 (normal) + 4 (tangent) + 6 (dup) + 10
(gap) + 4 (this channel's one texcoord set) = 36.
