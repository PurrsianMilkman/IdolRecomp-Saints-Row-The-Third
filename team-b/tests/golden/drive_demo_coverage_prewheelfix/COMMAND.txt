Golden scene: drive_demo_coverage, multi-channel vehicle mesh coverage/bbox
regression (NOT byte-exact-only - see tools/golden_scene_check.cpp's own
checkDriveDemoCoverageScene() doc comment for the full design rationale)
================================================================================

WHY THIS SCENE EXISTS: the drive_demo v2 mesh-shatter fix (merged to main,
commit range ending ec1694d) masked the vehicle's single upload()/draw() call
down to draw-group-0's genuinely-channel-0 ranges (16/20) to stop an index-
buffer corruption bug, but that ALSO silently dropped the OTHER 4 ranges'
real geometry (submeshIndex 1/2 - the car's middle body, doors/cabin walls) -
nothing automated caught it; a human had to notice a missing car body from a
screenshot (HANDOFF.md). This scene exists so that class of regression fails
a build, not a glance. The actual fix (this task, 2026-10-08): one
MeshRenderer PER CHANNEL present in draw group 0 (not just channel 0), each
fed its own decodeChannel(c) and its own rangeMask restricted to that
channel's own ranges - this file's own already-established multi-channel
pattern (MultiChannelMultiSetRender, tools/sr3_viewer.cpp).

Real command (run with cwd = tests/golden/ so the "captured:" line in the
frozen stdout, if ever frozen, would record the exact relative path this
file records - same convention every other scene's own COMMAND.txt uses):

    <sr3_viewer.exe> drive_demo ^
        "D:\Project Crreish\Saints Row 3 CRREISH\packfiles\pc\cache\dlc1.vpp_pc" ^
        car_4dr_genki_0.ccar_pc ^
        --no-city --frames 1 --capture _work/drive_demo_coverage.png --capture-frames 0

<sr3_viewer.exe> = the real CMake target build output (e.g.
build_preset_vs2022/Release/sr3_viewer.exe), same binary golden_scene_check's
own --bin-dir resolves to real a `cmake --build`.

NOTE on --capture-frames (not --capture-frame): drive_demo's own
--capture-frame alone only sets the FALLBACK frame used when --capture-frames
resolves EMPTY. Its own default --capture-frames is the non-empty 3-phase
list {89, 179, 239} (one frame per scripted phase) - that default still wins
over a bare --capture-frame 0, so --frames 1 --capture-frame 0 alone captures
NOTHING. --capture-frames 0 explicitly overrides the list to {0}, which
DOES get hit on the single frame --frames 1 presents. Confirmed directly by
testing both forms. The written file is "<capture-path>_frame0.png" (the
same "_frameN.png" suffixing every non-empty --capture-frames run uses),
NOT the bare --capture path - see runDriveDemo()'s own per-frame capture
block.

Real data: dlc1.vpp_pc (the whole shipped DLC1 archive), car_4dr_genki_0.ccar_pc
+ .gcar_pc + .cpeg_pc/.gpeg_pc nested inside car_4dr_genki_0.str2_pc within
dlc1.vpp_pc - the SAME real vehicle tests/golden/vehicle_genki's own golden
uses (see checkDriveDemoCoverageScene()'s own doc comment for why that
matters: this scene cross-checks its own coverage/bbox fraction against
vehicle_genki's as a secondary, deliberately loose sanity signal). --no-city:
no sr3_city_0.vpp_pc dependency at all - this scene renders the car alone,
per the task brief's own "render the car alone" instruction.

Why frame 0 of the straight phase: deterministic (fixed VehicleTuning test
fixture + fixed start pose - see BuildDriveDemoVehicleTuning()/runDriveDemo()'s
own doc comment - no RNG, no wall-clock input), and the earliest frame
available, so this is the fastest possible single-frame capture of this
scene. The trailing chase camera at frame 0 (pos (-960,-700), heading 0 deg)
still frames the vehicle from behind-and-above per runDriveDemo()'s own fixed
kCamDistance/kCamHeightAbovePivot/kPivotHeight constants - an angled, non-
straight-on view (the task brief's "fixed 3/4 view").

Determinism: confirmed directly this session by running this exact command
twice in a row into two different --capture paths and MD5-comparing the
