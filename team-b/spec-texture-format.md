## 1. Overview

A texture (or a batch of related textures, packaged together as one "container") is split across two files:

- **`.cpeg_pc`** — a small "CPU-side" file holding a header, one fixed-size metadata record per texture (dimensions, pixel format, byte offset into the paired file), and a table of the original source filenames (e.g. `.tga` names) — everything needed to know *what* textures exist and *where* their pixel data lives, without needing any of the actual pixel bytes.
- **`.gpeg_pc`** — the "GPU-side" file: **just the raw, back-to-back ~~compressed~~ pixel data (block-compressed *or* uncompressed, per the code table in §11) for every texture described in the paired `.cpeg_pc`, with no header of its own.** Each texture's data starts at exactly the byte offset its `.cpeg_pc` record declares, confirmed directly (byte 0 of the `.gpeg_pc` is the first texture's data with no preamble, and the second texture's declared offset lands exactly where the first texture's full mip chain would end **[desk review 2026-09-30: *rounded up to 16 bytes* — §5 shows an 8-byte pad, 43,688 → 43,696; the rule is §10.5's `align16`]**). **[CONFIRMED — empirical, both samples.]**

Both files are otherwise unremarkable entries in the container format already documented (`spec-vpp-container.md`) — always found in a `.vpp_pc`/`.str2_pc` as a matched name pair (`<basename>.cpeg_pc` + `<basename>.gpeg_pc`).

### 3.1 Filename Table — confirmed this pass, was previously undocumented

Immediately following the last per-texture record (i.e. at `0x18 + texture_count × 72`), the file continues with **one null-terminated filename per texture, back-to-back, no padding, in the same order as the record array** *(refined 2026-09-20, §10.4: strictly one name per record **group** — the group size is the record's `+0x14`, `1` on every shipped record, so names and records are 1:1 on all 70,524 files)* — the original `.tga` source names already mentioned informally in §1, now pinned down structurally. **[CONFIRMED — empirical, cross-checked on two independent samples: the 12-texture `decals.vpp_pc` set (12 names found immediately after the 12th record, filling the file out to its declared `0x08` total size exactly) and a newly-sampled single-texture case (§7) where the trailing name plus the fixed header and one record account for the file's declared size to the byte.]** An implementation can locate this table directly (no length field needed beyond what's already derivable): it starts right after the record array and its total length is simply `own_size (0x08) − (0x18 + texture_count × 72)`.

## 4. Pixel Format and Mip Chains

**Corrected 2026-09-11 by the clean team; the original rule stated here was wrong in a way that hid itself — see the correction note below.** A texture's data in `.gpeg_pc` is a mip chain stored as standard block-compressed (DXT/BC-family) pixel data, under two rules that this document previously got wrong:

> **The chain terminates at 4×4, not at 1×1.** The 2×2 and 1×1 levels are never stored.
>
> **Not every texture has a chain at all.** Some declare exactly their base level and nothing more (`ds_skidmark01.tga` is a confirmed example). ~~There is no single chain-length rule — **the declared size field (`+0x24`) is authoritative for how many levels are present**, and an implementation should consume levels until that byte budget is exhausted rather than computing a level count.~~ **Corrected 2026-09-20 (§10.5):** the level count is the **explicit byte at record `+0x23`** and the code consumes exactly that many levels (dimensions halve only while `(dim >> 1) ≥ 4` for DXT-family codes and `≥ 1` for the others — the mechanism behind "terminates at 4×4"); `+0x24` is the total those levels add up to, and the two agree exactly on 76,650/76,650 paired records. Either method reproduces the same chain on shipped data; the code's method is the count byte. **[Desk review 2026-09-30: "terminates at 4×4" is a clamp applied to width and height *separately* (§10.5) — on a non-square DXT texture the shorter edge stops at 4 while the longer keeps halving; this per-dimension clamp is **code-derived only** (§12.5 C7: no shipped record exercises it).]**

With both rules applied, computing the mip-chain byte total and comparing it against the declared size matches **exactly, with zero residual, on 13 real textures** — not "closely enough". **[CONFIRMED — empirical, clean team, 13/13 exact.]**

**Why the original rule survived as long as it did, and why that matters:** assuming the chain ran down to 1×1 overshoots by exactly the two missing levels — 16 bytes for a BC1-class texture and 32 for a BC3-class one, *every time*. That is a small, perfectly consistent excess, and this document absorbed it into a hedge about "the small rounding expected from block-compression's fixed minimum block size." **That hedge was not describing rounding; it was describing an error.** The lesson is the same one recorded in `HANDOFF.md` §5 about the geometry format's length-prefixed blob: *a plausible-sounding tolerance is where a wrong rule hides — when a size formula does not land exactly, the residual is evidence, not noise.* (The related lesson also holds: when a structure resists a formula, check whether the format already declares the answer. Here it does, at `+0x24`.)

*(Note: an earlier version of this section cited `+0x22` as the declared-size field. That is stale — §3 corrected the size field to `+0x24`, with `+0x22` being a separate, still-unidentified field. Corrected here.)* **[Resolved: `+0x22` is now identified as a one-byte animation rate and `+0x23` as the level count, §10.3.]**

The bytes-per-pixel ratios that distinguish the format codes:

- **Format code `400`** — 0.5 bytes/pixel. **Confirmed BC1** (DXT1; 8 bytes per 4×4 block).
- **Format code `402`** — 1.0 bytes/pixel. **Confirmed BC3** (DXT5; 16 bytes per 4×4 block).
- **Format code `403`** — 2.0 bytes/pixel. ~~**Deliberately still OPEN**: several 16-bit-per-pixel layouts fit that ratio and the size math alone cannot separate them. Left unresolved rather than guessed.~~ **RESOLVED 2026-09-20 (§11.2): `D3DFMT_R5G6B5`** — named by the format switch in the upload code and confirmed by decoding a real `403` texture (the other 16-bit layouts render as channel noise).

**[CONFIRMED — empirical, by decoding and rendering, clean team, 2026-09-11.]** Codes `400` and `402` were settled by actually decoding the pixel bytes and looking at the result, which is the only way this could have been settled: **a wrong block layout does not degrade gracefully.** It produces structured 4×4 noise, not a slightly-wrong image — so a recognisable decode is itself strong evidence, and size arithmetic alone could never have distinguished BC1 from any other 4-bits-per-pixel scheme. ~~Code `403` remains open for exactly the complementary reason: its 2.0 bytes/pixel is consistent with several 16-bit layouts, and no decode has yet disambiguated them.~~ **Closed 2026-09-20 (§11.2): the code names R5G6B5 and a decode of one real `403` texture confirms it.**

**A separate empirical finding worth recording:** `vfx_blast_decal_01_n.tga` decodes with the blue channel **exactly 0 on every pixel**. That is correct data, not corruption — it is a two-channel normal map, storing X and Y and reconstructing Z at runtime, a standard technique. **[CONFIRMED — empirical.]** **A tempting but explicitly rejected hypothesis:** in the 12-texture sample, format `400` happened to coincide with every filename ending in `_n` (a common convention for normal-map textures) while `402` covered every other name — but the 1-texture sample (`misc-static.tga`, not a normal map by name) also reads format `400`, directly contradicting a "400 always means normal map" rule. **This remains rejected after the decode pass, and is now confirmed rejected rather than merely doubted:** `misc-static.tga` is format `400` and decodes to flat grey with a non-zero blue channel — an ordinary colour texture. The two-channel normal map noted above is also `400`. **The code identifies the block-compression layout only; it says nothing about how the texture is used.** **Treat the format code as a real, meaningful pixel-format identifier confirmed by its size math, and treat any naming-based association as coincidental, not a format rule.**

## 8. Type 18 "AL peg" — the always-loaded variant (added 2026-09-10)

Type 18 shares this document's format outright: the same `.cpeg_pc`/`.gpeg_pc` extensions as type 3, the same `.cvbm_pc`/`.gvbm_pc` alternates, and the same shared loader (§7's sibling trio). **There is no separate AL-peg file format** — what differs is what the type does *after* a successful load.

**"AL" means "Always Loaded", confirmed by the engine's own strings**, not inferred from the abbreviation: the binary carries `"Level Always Loaded Peg"` and `"Level Always Loaded"`, plus `"always loaded textures"` referenced from the zone streaming subsystem. **[CONFIRMED — empirical.]**

### 8.1 What the type does

The constructor calls the shared PEG loader with the same flag value type 17 uses, and — unlike types 3 and 17, which ignore the result — **checks it and fails the whole construction if the load failed**. On success it then pins the package's textures:

For each of the `count` per-texture records (`count` is an `i16` at runtime offset `+0x14`; records begin at `+0x30` with a **stride of `0x48` = 72 bytes**):

**[OPEN — desk review 2026-09-30: records begin at file offset `0x18` (§10.2, validated 70,524/70,524) while this runtime view puts the count at `+0x14` (same as the file) but the records at `+0x30`; either the object holding the c buffer has an undescribed `0x18`-byte prefix after `+0x14` or one of the two is wrong — to be settled against the executable (AL-peg ctor `0x005D78A0` and destructor `0x005D79B0`, `spec-low-mips.md` §3.1 table; the pin/unpin body they call has no address recorded here).]**

1. Compose the texture's name with the **platform-indexed `.cvbm_pc` extension** — the same alternate-extension table the registration row carries — into a 64-byte buffer. **[OPEN — desk review 2026-09-30: whether the extension *replaces* the name's `.tga` extension or is *appended*, and what happens to a name longer than the 64-byte buffer, are not stated; to be settled against the executable.]**
2. Hash it to a **1024-bucket** index (§8.2).
3. Look the name up. **If present, increment its reference count. If absent, allocate a slot, set the reference count to 1, and copy the 64-byte name into the registry's name table.**

The destructor is the exact mirror: same records, same bucket, **decrement the reference count and remove the entry when it reaches zero**. That symmetry is why type 18 is the only member of the trio with its own destructor — types 3 and 17 share one, because neither has anything to unpin. **[CONFIRMED — disassembly.]**

So an AL peg is a texture package whose every texture is **pinned resident for the level, with reference counting** so that several packages naming the same texture cooperate rather than fight. **[CONFIRMED — disassembly.]**

**Independent cross-check of §3.** This code walks per-texture records at a stride of **72 bytes** with the count in the object header — matching, from a completely different direction, the 72-byte per-texture record §3 established from the file bytes. **[CONFIRMED — disassembly.]** *(Desk review 2026-09-30: this cross-checks the stride only, not the record base — see the OPEN note above.)*

### 8.2 A third engine string hash

The bucket index comes from a hash this project had not seen before: fold each character to lowercase, then `hash = (hash * 0x21) XOR character`, and finally take `hash % bucket_count` (1024 here). It is a multiply-by-33 / XOR variant, and — because it returns a **bucket index rather than an identity** — it is used for table placement, not as a name key. **[CONFIRMED — disassembly.]**

**[Completed (desk review 2026-09-30):** the function is **`0x00dab330`** (`FUN_00dab330`, ≈174 call sites — `spec-extensionless-types.md` §4; emulated in `spec-lua-api-behaviour.md` §5.3). Stated in full: **start with `hash = 0`; for each byte of the name, `hash = (hash × 33) XOR lowercase(byte)`, wrapping at 32 bits; result `hash mod bucket_count`** (the bucket count is the function's second argument). `spec-lua-api-behaviour.md` §5.3's five emulated vectors (`"Tint_color"`/`0x20` → `0x5`, `"continuous_spawn_start"`/`0x20` → `0x16`, `""`/`0x20` → `0x0`, `"SAINTS_ROW_THE_THIRD"`/`0x100` → `0x7d`, `"a"`/`0x20` → `0x1`) reproduce only with initial value `0` and 32-bit wraparound (0/5 with djb2's `5381`; re-checked in this review). **OPEN — desk review 2026-09-30: signed vs unsigned modulo, the signedness of the character load (bytes ≥ `0x80`), and the hash width above the low bits cannot be decided by those vectors — both bucket counts are powers of two, so the modulo only masks the low bits; a non-power-of-two count (e.g. the 9,000-bucket interned-name table, `spec-customization-data.md` §5) and a non-ASCII byte are needed; to be settled against the executable.** Also: the always-loaded registry is not this hash's only user (`spec-lua-api-behaviour.md` names the team/gang-id table, mod 32, and camera-shake names; `spec-customization-data.md` the 9,000-bucket name table), and the call from the AL-peg pin routine with count 1024 is not anchored to a call-site address here.**]**

That makes **three distinct string hashes** now documented in this engine:

| Hash | Where | Role |

## Appendix: `.matlib_pc` (bonus, lighter-effort pass)

`.matlib_pc` is the material-definition format referenced by name from both `.asm_pc` manifests (`spec-asm-format.md` §4) and, per this pass, from texture-adjacent content generally. One real, fully-reliable sample (`vfx_decal_bullet_wood.matlib_pc`, the exact file already cross-validated by size in the `.asm_pc` spec — extracted here as the sole, and therefore trivially "first," entry of its own nested container) was inspected directly. **Confirmed structure, from this one sample (corrected and extended this pass — see `spec-geometry-format.md`, which re-derived this format precisely after finding it reused elsewhere):**

- **Fixed 32-byte header:** a constant leading value (`0x00043854` at offset `0x00` — present, unchanged, in every sample of this format seen anywhere, including inside `.ccmesh_pc`, §below); a field at offset `0x04` that is **now confirmed to be the exact byte length of the name table that follows** (checked precisely: it equals `name_table_end − 0x20` to the byte); a zero field at `0x08`; and the **texture-slot count** at `0x0C` (`3` in this sample). Bytes `0x10`–`0x1F` are zero-padding.
- Immediately followed by **exactly `count` null-terminated texture filenames**, back-to-back, matching the offset-`0x04` byte length exactly: `normal_blank_n.tga`, `vfx_wood_bullet_decal.tga` (the actual unique art asset — corrected this pass; an earlier draft transposed two words in this name), and `spec_blank_s.tga`. This is a material referencing a **normal map, diffuse map, and specular map** by name — the "blank"/generic names for two of the three slots indicate this particular material only customizes the diffuse texture and falls back to shared default normal/specular maps. **[CONFIRMED — empirical: the declared count, the declared byte length, and the actual names found all match exactly.]**

## 9. Registered types 10 `Pcust peg` and 14 `Pcust logo peg` — traced: stash-only, deferred into the same PEG validator as ID 3 (2026-09-20)

**ID 10, `LAB_009f0910` (84 bytes, 24 instructions).** Load the customization current-job pointer `DAT_0263e0f4`; return false unless the constructor's 2nd argument (the streaming container being loaded) equals job`+0x10`; copy the name (`0x41` bytes, bounded) to job`+0x68`; store primary buffer, primary length, secondary buffer, secondary length at job`+0xac`/`+0xb0`/`+0xb4`/`+0xb8`; return true. **ID 14, `LAB_009f0a60` (43 bytes, 15 instructions) is the same shape with two differences.** It uses a *different* global, `DAT_0263e0e8` (the current record of a separate 64-entry pool of `0x5c`-byte logo records), and it has **no container gate and no name copy** — only "is a logo record current?" — before storing the four raw values at record`+0x4c`/`+0x50`/`+0x54`/`+0x58`. **[CONFIRMED — disassembly.]**

### 10.4 Name table and the group rule

The name table starts at `0x18 + 72·count` and runs to the end of the file (header `0x08` minus that start = its length; 70,524/70,524 files consume exactly to EOF, no padding, no footer). It holds **one NUL-terminated name per record *group***, not per record: the validator points the `group_count` consecutive records starting at record `i` (count read from record `i`'s `+0x14`) at the same name, consumes exactly one name from the table, and continues at record `i + group_count`. A group count of `0` would make the walk make no forward progress, so `≥ 1` is a hard precondition (always `1` in shipped data, so names and records are 1:1 on all 70,524 files — "one name per texture" in §3.1 holds for the shipped population but is the special case). ### 10.5 The g-side data: alignment, level chain, cube layout

Each record's region starts at its `+0x00` offset into the g file. **Regions are laid end to end with every region start (and the file length) rounded up to 16 bytes** — the merge routine computes running offsets as `size` rounded up to the platform g-side alignment (`16` on PC, the `spec-resource-dispatch.md` §8 table value), and the population agrees exactly: `offset[i+1] = align16(offset[i] + size[i])` on 70,471/70,471 pairs, and `align16(last end) = len(g)` on 70,471/70,471 **[denominators (desk review 2026-09-30): 70,468 non-empty pairs for both gates — the 3 zero-texture pairs are vacuous; Team B 70,468/70,468 each, `team-b/HANDOFF.md` l.11085–11086]**. **Level chain (what the upload callback walks).** For a record with `w × h`, format `f` and `n` levels (`+0x23`): level `k` is read as `rows × row_bytes`, where the source row byte count comes from the format (§11) and the row count is `ceil(height / block_edge)`; the per-level source advance is `height × row_bytes / block_edge` (integer) **[CONFLICT / OPEN — desk review 2026-09-30: the two row formulas (rows read = `ceil(height / block_edge)`, pointer advance = `height × row_bytes / block_edge` truncated) agree whenever the height is a multiple of `block_edge` and differ for a DXT level whose height is not (e.g. a level halved from 12 to 6); the spec's own numbers cannot decide which the engine does, because every shipped DXT level is a power of two ≥ 4 (§12.4: no DXT width/height not a multiple of 4; the non-power-of-two shapes are `403`/`407` and single-level cubes). ## 12. Population validation of the code-derived layout (70,524 c-files / 70,471 pairs, 2026-09-20)

### 12.1 What the parser gates on (every byte accounted for)

There is no separate "footer" in a c-file or a g-file: §5/§6's footer wording referred to nothing that exists — the name table *is* the file's tail.

### 12.7 Corrections to earlier sections, and what remains open

Corrections (each struck through in place in §2–§6 with a pointer here): `0x04` is version + platform index, not one 4-byte version; `0x14` is *the* count, `0x10` a second copy, `0x12` a runtime flag, `0x16` a constant `16` — not "a capacity + flag"; record `+0x10/+0x12` are the flipbook grid, not "array size / face count"; `+0x14`–`+0x21` is not zero (group count, flags, an overwritten pointer slot, a merge-only field); `+0x22` is a one-byte animation rate and `+0x23` the level count; **`+0x24` is a 32-bit size** (§3's "2 bytes" and the `+0x26` "zero" field were one field misread); the true zero region is `+0x28`–`+0x47`, runtime-owned; **the level count is explicit (`+0x23`)**, not "consume until the size budget is exhausted"; **`403` = `D3DFMT_R5G6B5`**; §5's 8-byte gap is the 16-byte region alignment; the "footer" does not exist.

**Remaining OPEN (honest gaps):** (1) meaning of flag bits `0x0001`, `0x0004` (read by nothing in the scanned closure) and the effect of `0x0200` beyond "its inverse is a per-sampler SetTexture argument" — the command executor was not traced; (2) `+0x20`'s role beyond "read/rewritten by the merge routine" — no data exercises it; (3) roles of the three runtime dwords `+0x38/+0x40/+0x44`; (4) the reader of header `0x12` and use of header `0x16`; (5) whether the registry's second lookup table (`0x02A38140`, tried after the primary) is a fallback/alias namespace; (6) the `0x25B`/`603` alias; (7) the units of the animation clock at `0x029F4DB0`; (8) the device-mode global `DAT_03171ac8` that flips `Usage`/`Pool` (traced no further than "written by the device-creation function `FUN_0047ba00`"); (9) all of §12.6's never-exercised paths remain code-derived only. **Cross-spec notes (not edited here):** `spec-low-mips.md` should cite §10.7's runtime bits and the merge routine; `spec-resource-dispatch.md` §8's PEG alignments (`8`/`16`) are confirmed by §10.5 (the g-side regions are 16-aligned; `FUN_00dcf500` reads the c blob at alignment 8 when the g file exists and the g blob at the platform-table value, 16 on PC); §8.2's hash table gains a row — the texture registry uses the **rotate-6/XOR** hash (§10.6), not the multiply-33 one. **[See §10.6's CONFLICT / OPEN marker (desk review 2026-09-30): the address `FUN_00db09d0` cited there is not the catalogued rotate-6 function `FUN_00da7890`.]**
