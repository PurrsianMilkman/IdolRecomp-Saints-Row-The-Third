## 1. Correcting the starting assumption: it is not "just some `.xtbl` files inside `vehicles.vpp_pc`"

The original framing for this target assumed vehicle handling/stats data would be a well-scoped set of `.xtbl` files living inside `vehicles.vpp_pc`, made "effectively free" now that the `.xtbl` format itself is solved. That assumption does not hold, on two independent counts:

1. **`vehicles.vpp_pc` does not contain any `.xtbl` files at all.** Its top level holds exactly 372 per-vehicle `.str2_pc` bundles (e.g. `car_4dr_standard03_0.str2_pc`) plus one `vehicle_containers.asm_pc` manifest. **[CONFIRMED — empirical: every one of the 373 directory entries was enumerated and checked by extension.]** Opening one of these per-vehicle bundles (they're stored raw at the top level, so this is fully reliable) shows they hold that vehicle's 3D model/geometry data — a `.ccar_pc`/`.gcar_pc` paired container (a car-specific analogue of the `.cpeg_pc`/`.gpeg_pc` texture-pair format already documented, not further investigated this pass) plus a `.cvtf_pc` file originally guessed here to be a binary damage-deformation/collision index, based only on its table-like binary shape. **Correction (from the later geometry-focused pass, `spec-geometry-format.md` §5): direct string inspection shows this file is actually compiled, binary vehicle-customization data** — component-group names, option labels, wheel part names, and paint-color names, matching the `<vehicle_name>.xtbl` customization schema documented in §3 below. See `spec-geometry-format.md` §5 for the full finding; it also very likely resolves the missing per-vehicle `_cust.xtbl` reference flagged as open in `spec-customization-data.md`. **None of this — `.ccar_pc`/`.gcar_pc` model geometry or `.cvtf_pc` customization data — is handling/physics stats data.** (The `.cvtf_pc` reading is HIGH CONFIDENCE in `spec-geometry-format.md` §5, not CONFIRMED.)
2. **The actual vehicle stats tables live in `misc_tables.vpp_pc`** (and, for a handful of satellite tables, `da_tables.vpp_pc` and `patch_compressed.vpp_pc`) — the same central table archives already used for every other `.xtbl` target so far, not a vehicle-specific archive.

So the target genuinely needed its own investigation to find the right files — it was not a trivial "look inside the obviously-named archive" task, though the actual `.xtbl` parsing, once the right files were found, was exactly as easy as expected.

**Review status (2026-09-30): DESK-PASS, text fixes applied (header scope note; 372 + 1 = 373 tiles) — desk review (not re-derived from the executable).**

## 2. The bigger complication: the base game's own vehicle-stats tables are currently unreadable

> **⚠ RESOLVED 2026-09-20/24 — §7.9 item 1 and §7.11: the mode-(a) limitation is fixed (`spec-vpp-container.md` §7), and all 123 real `<name>_veh.xtbl` files have been read and validated. This section is kept as history.**

This is the important, non-trivial finding for this pass, and it needed to be surfaced honestly rather than forced into a "free win" shape.

**`misc_tables.vpp_pc` is a mode-(a) compressed container** (flags `0x4801`, mode-switch bit clear — see `spec-vpp-container.md` §3.2/§3.3), and **every single vehicle-relevant table inside it is a non-first entry**: `vehicles.xtbl` (directory index 263 of 1,342), `vehicle_defaults.xtbl` (index 272 — ~~by its size, ~96.7 KB, this is almost certainly where the actual per-vehicle handling numbers for the base game's ~100+ vehicles live~~ **[Corrected 2026-09-20, agent AF — §7.2: the loader reads only this file's `<Defaults>` element (one global default set); the per-vehicle numbers are in each `<name>_veh.xtbl`, listed by `vehicles.xtbl`, with group defaults from `vehicle_groups.xtbl`.]**), `generic_vehicles.xtbl` (index 146), `vehicle_groups.xtbl` (index 274), `vehicle_cameras.xtbl` (index 265), and every other vehicle-adjacent table checked. The one satellite table found in `da_tables.vpp_pc` (also mode (a)) and the one in `patch_compressed.vpp_pc` (also mode (a)) are likewise non-first entries.

Per the container format's own documented, closed-out known limitation (`spec-vpp-container.md` §3.2/§6 item 1): **only a mode-(a) container's first entry (index 0) is confirmed to decode to correct content; every other entry is currently unreliable.** This was independently re-confirmed here, concretely: attempting to locate any of the above entries' data using the directory's own declared `data_off` field lands at a byte position beyond the end of the file entirely (e.g. `vehicles.xtbl`'s declared data offset, added to the container's payload region, computes to a position over 56 MB into a 5.3 MB file) — a direct, unambiguous confirmation that `+0x08` is a *logical* (post-decompression) offset for these entries, not a physical one, exactly as already documented, and that no working decode recipe for it currently exists.

**Practical consequence: the base game's own `vehicles.xtbl` and (especially) `vehicle_defaults.xtbl` cannot currently be reliably extracted or read.** This is not a new problem specific to vehicle data — it's the same already-parked container-format limitation — but it does mean **this specific target is directly blocked by it**, which is worth flagging back explicitly rather than quietly working around. No new attempt was made to solve the underlying decode mechanism itself, per the standing direction to leave that investigation with the container-format work for now.

## 3. The workaround that made this pass productive anyway: DLC archives are stored raw

`dlc1.vpp_pc`, `dlc2.vpp_pc`, and `dlc3.vpp_pc` are **entirely uncompressed archives** (flags `0x0`) — every entry inside them, including their own vehicle-stat tables, is stored raw and therefore **fully, unconditionally reliable regardless of position in the directory**. **[CONFIRMED — empirical.]** Each DLC archive ships a small number of new vehicles (~~6–7 each~~ **7, 8 and 2 — 17 in total, §7.1/§7.7**), and for each one, two `.xtbl` files exist side by side:

- **`<vehicle_name>_veh.xtbl`** — the vehicle's **stats/handling/physics definition**. This is the file that answers this target's actual question, and it decoded cleanly and validated as well-formed XML for every sample checked.
- **`<vehicle_name>.xtbl`** — a separate **variants/customization-components definition** (paint variants, which cosmetic parts can spawn on which variant, spawn weights) — a different concern from handling stats, overlapping instead with the future customization-data target (#11). Not field-by-field documented here, beyond noting its existence and role, since it's out of this target's scope.

This gives a **complete, validated, real-world worked example of the handling/stats schema** — just not, unfortunately, values for the base game's ~100+ non-DLC vehicles, which remain blocked per §2 **[no longer blocked — §7.11]**. The schema itself is presumably identical between DLC and base-game vehicles (same table format, same engine consuming it), so this is a genuine, usable resolution of "what does the schema look like," even though "what are the actual values for every base vehicle" remains open.

**Review status (2026-09-30): DESK-PASS (§2–§3 history; 7 + 8 + 2 = 17 tiles) — desk review (not re-derived from the executable).**

## 4. `<vehicle_name>_veh.xtbl` — confirmed field schema

## 5. `Vehicle_Type` — confirmed polymorphic by vehicle class

`Vehicle_Type` wraps exactly one class-specific sub-element, and its shape differs meaningfully by what kind of vehicle it is. **Four distinct variants were directly observed:**

- **`Automobile`** (cars, trucks, SUVs) — a thin wrapper around `AutomobileFlags > Flag` (a list of string flags, e.g. `Is Tank`, `No Treads`, `Has Security Alarm`).
- **`Motorcycle`** (bikes) — observed as its own distinct tag name (not reusing `Automobile`), sub-fields not enumerated this pass.
- **`Helicopter`** — ground-independent rotor-craft physics: `Rotor_Center` (X/Y/Z), `Rotor_Radius`, `Steering_Accel`, `Elevation_Speed`/`Elevation_Accel`/`Elevation_Damp`, `Autolevel_Accel`, `Surfaces > Surface` (a list of aerodynamic control surfaces, each with `Type` — observed values `Wing`/`Elevator`/`Aeleron`/`Rudder` — plus per-surface offset/angle/lift/deflection tuning), `Pitch_Bias`, `Tail_Rotor_Center`, `Tail_Accel`, `Extra_Speed_Accel`, `AI_Extra_Speed_Accel`, `Drop_Off_Height`.
- **`VTOL`** (hybrid hover/flight vehicles — the DLC "flying bike"/"flying saucer" novelty vehicles) — combines **both** an `Airplane_Mode` block (`Engine_Params`, `Reverse_Speed`, the same `Surfaces` control-surface list as `Helicopter`, `Camera_Overrides`, `Pilot_Assist_Params`) **and** a `Helicopter_Mode` block (same shape as the standalone `Helicopter` variant above) as siblings — i.e. these vehicles are modeled as switching between two complete, independently-tuned flight models at runtime.

## 7. The runtime vehicle-info table and the `_veh.xtbl` → entry map (added 2026-09-20, agent AF)

**Added 2026-09-20 (agent AF, Ghidra project copy `gp_veh6` (evidence dump, not in repo)).** Answers `spec-vehicle-geometry.md` §10 item 6: the global vehicle-info table the `.ccar_pc` constructor consults, and how the `<name>_veh.xtbl` fields of §4–§5 land in it. Method: the constructor `FUN_00ab1080` was read to its table lookup (`FUN_00ac17b0`); the table's own accessor family (a run of small functions at `0x00ac1840`–`0x00ac2ac0`, all indexing the same array) was decompiled; then the named-string anchors of §4 (`Maximum_Speed`, `Roll_Torque_Factor`, `Wheel_Spring_Strength`, `Downshift_RPMs`, `Nitro_Capable` and the file names `vehicles.xtbl` / `vehicle_defaults.xtbl` / `vehicle_groups.xtbl`) were followed to the reader tree rooted at `FUN_00acbfc0` and the loader `FUN_00ace640`. No predicate search was used. Cleanroom: no decompiled code is reproduced; XML element names are data (as in §4); offsets, sizes and function addresses are evidence anchors. Labels: CONFIRMED — disassembly / CONFIRMED — empirical / HIGH CONFIDENCE / HYPOTHESIS / OPEN.

**Headline results**

- **The table is real, but it is the *parsed form of the `_veh.xtbl` schema*, not a link to `vehicle_defaults.xtbl`**: **132 (`0x84`) entries × `0xB80` bytes at `0x027C87B0`**, zero in the static image (it lives in `.data` beyond the raw-initialised part) and filled at start-up by the XML loader. One entry = one `<Vehicle>` element of a `_veh.xtbl`. **[CONFIRMED — disassembly.]**
- **Selection is by slot index, assigned in `vehicles.xtbl` order**, not by name-hash at load time (§7.1). At run time the index is a `u16` handle; name lookup is a linear hash scan (§7.1).
- **Name → offset map: all 134 element names §4–§5 list as confirmed are accounted for** (§7.4): **105** leaf fields resolved to a fixed entry offset (or an axle-/block-relative offset with a known base), **24** structural tags (containers, list items, selectors — no destination of their own), **3** consumed but not stored verbatim, and **2 that the engine never reads by name** (`Convertible`, `Vandalism_value`). ### 7.2 Where the numbers come from — three layers, and a correction to §2/§6 item 1 **[CONFIRMED — disassembly]**

The entry reader `FUN_00ACBFC0` (a `__thiscall`: ECX = destination entry) is called in two modes and every numeric field uses the same discipline — **initialise from a default, then overwrite only if the element is present** **[OPEN — desk review 2026-09-30: this conflicts with the "always write" accessors below, which leave an unspecified value when the element is absent; which accessor each field uses (in particular `Mass`, absent in 3/123 real vehicles, §7.11) and whether the group-row copy precedes it is to be settled against the executable (`FUN_00ACBFC0`, `FUN_00DACCB0`/`FUN_00DACD40`)]**:

1. **Global defaults.** `vehicle_defaults.xtbl` is opened and **only its `<Defaults>` child is read** (`FUN_00ACB5B0`) into a compact global block at `0x0282CB20…0x0282CF90` (not entry-shaped). **Consequence: `vehicle_defaults.xtbl` is one global default set, not the per-vehicle numbers.** §2 and §6 item 1's guess that it "is almost certainly where the per-vehicle handling numbers live" is **corrected** (its 96.7 KB is presumably mostly the embedded table description).
2. **Group defaults.** `vehicle_groups.xtbl` is opened; **each `<Vehicle_Group>` is parsed by the same entry reader in "defaults mode"** into row *n* of a second `0xB80`-stride table at **`0x0282CFA0`** (count at `0x0282CB10`, no bound check in the loader). A vehicle's `Group` text is hashed and matched against the rows' `+0x18` hash to choose its row; a pointer to that row is kept at entry `+0x480`. Group rows keep **raw XML units**; a vehicle row copies the group row's value, overrides it if the element is present, and **only then converts units** (so units are converted exactly once). `Mayhem_Value` (`+0x4AC`, default 5000) is read only in this group mode. **[OPEN — desk review 2026-09-30: whether every real vehicle's `Group` matches one of the 19 `vehicle_groups.xtbl` rows (§7.9 item 5's miss path) is to be settled against real data.]**
3. **Per-vehicle.** `<name>_veh.xtbl`'s `<Vehicle>` element, as §4 describes.

Accessor semantics (small functions at `0x00DABA10`–`0x00DACF60`; each looks up a child by **case-insensitive** name): **float** (`FUN_00DACD40` = "write only if the child is present", `FUN_00DACCB0` = "always write" ~~"0 if absent"~~ **CORRECTED 2026-09-20 by three independent agents (AH `spec-tables-weapons-combat.md` §1, AJ `spec-tables-traffic-ai.md` §1, AK `spec-tables-environment.md`): the always-writers do NOT clear their scratch buffer, so when the child element is absent the destination receives an UNSPECIFIED value (stack residue from an uninitialised 1 KiB buffer), not 0. A reimplementation must not rely on "0 if absent" for those fields; it should treat an absent element as undefined and use the shipped data's explicit presence (every shipped row supplies them)**), **u32** (`00DABE80` / `00DABDF0`), **signed int** (`00DABD20` / `00DABC70`), **u8** (`00DAC1D0`), **bool** (`00DAC510` / `00DAC480`: true for `true`/`yes`, false for `false`/`no`), **bounded string copy** (`00DABA70`, `00DABAB0`; NUL forced at `[size-1]`), **vec3** (children `X`,`Y`,`Z`: `00DACF20`), **float/int list** of `Element` children (`00DACE80`, `00DAC620`). The engine's float grammar is its own: optional `-`, integer digits, optional `.digits`, optional exponent; a leading `.` is accepted; **a leading `0x` reads as `0.0`**. Integer text accepts decimal or `0x` hex. **Element-name matching is case-insensitive** (`Center_of_Mass_Z_Offset` in a DLC file matches the reader's `Center_Of_Mass_Z_Offset`; the `Vtol` lookup matches the `VTOL` tag).
