### 1.2 The stunt-family shared shape — answered up front

**Yes, the `stunt_*` family shares one common scoring-parameter schema**, but not one common *function*: each of the 9 `stunt_*.xtbl` tables has its **own dedicated loader function** (9 distinct `FUN_00XXXXXX` entry points, one per file), not a single generic "stunt reader" parametrised by table name. What *is* shared, letter-for-letter, across all 9 loaders is:

1. The same open/first-child/close idiom and the same six scalar-accessor functions (§1.3 below).
2. A **reward triad** present in every one of the 9: `Max_Respect` (`s32`, floor 0), `Max_Lifetime_Respect` (`s32`, floor 0), `Max_Cash` (`f32`, floor 0.0).
3. A **record-notification triad** present in 8 of 9 (missing only from `stunt_hijacking`): `Record_Display_Time`, `Record_Queue_Time` (both optional `f32`, seconds→milliseconds, destination pre-zeroed then overwritten only if the element is present) and `Record_Threshold` (`f32`, divided by a percent-to-fraction constant — see §1.4).
4. The same validation idiom for paired Min/Max fields: if `Max ≤ 0` or `Max < Min`, **both** are reset to 0 (seen identically in `stunt_drifting`, `stunt_near_miss`, `stunt_back_seat_driver`, `stunt_oncoming`, `stunt_low_flying`, and reused again outside the family in `barnstorming`/`base_jumping`/`mugging_diversion`). **[Qualified 2026-09-30 (desk review): this document's own per-table text does not show one rule everywhere. `stunt_near_miss` tests `Max<1`, not `Max≤0` (§2.4). `barnstorming` has no Min/Max pair at all, only a single `Max_Distance` with a constant fallback (§3). `base_jumping` (`Max_Altitude`, `Max_Veh_Distance`, §4) and `mugging_diversion` (`Default_Max_Cash`, §6.2) **clamp `Max` up to `Min`** rather than resetting both to 0. Use the rule stated in each table's own subsection, not this summary.]**

Two of the nine (`stunt_wheels`, `stunt_jumping_diversion`) additionally share a **second-level** repeated sub-shape: several near-identical named sub-blocks (`Two_Wheels`/`Wheelie`/`Stoppie`; `Land_Distance`/`Air_Height`/`Fall_Dist`/`Pitch_Rotation`/`Roll_Rotation`/`Spin_Rotation` × 3 vehicle types) read by one shared literal-pointer-table loop inside that table's own loader (§2.8, §2.9) — this is *within-file* sharing, not shared across files. **§2** gives the full per-table field list; §2.1 states the shared idiom once and each subsection states only its table's own fields and deviations. **[CONFIRMED — disassembly, all 9 loaders individually read to their end.]**

### 1.5 A genuine engine quirk found in this group

**`stunt_peel_out.xtbl`'s `Record_Threshold` field is read and converted like a *time* field, not like every other table's percent-threshold field.** Every other table in this group that has a `Record_Threshold` (`stunt_drifting`, `stunt_near_miss`, `stunt_back_seat_driver`, `stunt_oncoming`, `stunt_low_flying`, `stunt_jumping_diversion`, `stunt_wheels`, `base_jumping`) reads it with the "always" `f32` accessor, clamps to ≥0, then divides by the percent-to-fraction constant (`DAT_012a2dd8`, §1.4) and leaves it as a float. `stunt_peel_out`'s loader instead clamps it to ≥0 and then runs it through the *exact same* `ROUND(x * DAT_012a2d90)` seconds→milliseconds idiom used for its own `Instance_Delay` field immediately above it in the same function, storing the result as an integer. **[CONFIRMED — disassembly, `FUN_006C0CF0`.]** This is consistent with a copy-paste slip in the original source (the `Record_Threshold` block was very likely cloned from the preceding `Instance_Delay` block and the conversion line never swapped) rather than a deliberate design difference — no other evidence in the shipped `stunt_peel_out.xtbl` row or its `TableDescription` (which describes `Record_Threshold` identically to every sibling table) suggests an intentional divergence. **A reimplementation reproducing retail behaviour exactly must special-case this one field.** **[OPEN — desk review 2026-09-30: the destination's width and signedness, and whether the consumer of this global reads it as a percent or as milliseconds, were not traced; reproduce it as stated only once the consumer is known; to be settled against the executable.]**

**Review status (2026-09-30): NEEDS-EXE: `FUN_006C0CF0` destination type and its consumer untraced — desk review (not re-derived from the executable).**

## 2. The `stunt_*` family — nine tables, one shared shape

### 2.1 Shared idiom (stated once; per-table subsections list only fields/deviations)

Each loader: opens its file (`FUN_00DAC9A0`), takes the single named row element, reads its own scalar fields with the accessors of §1.3, and closes the document. **Seven of the nine** (`stunt_drifting`, `stunt_hijacking`, `stunt_near_miss`, `stunt_back_seat_driver`, `stunt_oncoming`, `stunt_peel_out`, `stunt_low_flying`) write straight into individually-addressed global variables (a **flat-globals** layout — there is no single contiguous per-table record); the other two (`stunt_wheels`, `stunt_jumping_diversion`) are `__fastcall`/`__thiscall` functions taking a destination-record pointer, because they each hold **more than one** copy of the same sub-shape (three sub-stunts; three vehicle-type rows respectively) and it was more convenient for the original authors to index a small contiguous record than to name N globals. **[CONFIRMED — disassembly, all 9.]**

Every field below is validated against the real base-game row (`da_tables.vpp_pc`), which for every one of the nine tables is a **single row**, and every field the `TableDescription` documents as present in the shipped row is confirmed. Exact addresses (`FUN_00XXXXXX` for the loader, `DAT_00XXXXXX` for the destination globals) are recorded as evidence anchors in the harness output and are omitted from the prose below except where a specific offset relationship (a stride, an array capacity) is the finding itself. *[desk review 2026-09-30: so this document gives no destination address for any of the seven flat-globals tables; a runtime reimplementation would need them from the executable. Team B's readers do not use them.]*
