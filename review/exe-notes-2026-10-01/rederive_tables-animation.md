## §1.3 Additions to the shared grammar — `FUN_004BF650` / `FUN_004BF610` / `FUN_00DA7890`

**Verdict: CONFIRMED — disassembly for the hash used, the miss return, the index derivation and the rotate/XOR hash's byte handling; still OPEN for the bucket count; the duplicate-name policy is answered under §3.4 below from the inserter, not from these two lookup functions.**

**Evidence:** `func1/func_0x004bf650.txt`, `func1/func_0x004bf610.txt` (job ytgi); `func2/func_0x00da7890.txt` (job dvje).

`FUN_004BF650` (`0x004BF650–0x004BF691`):
- Hashes its single string argument with **`FUN_00D9E740` and seed `0`** (`0x004BF657–0x004BF65A`) — the table-driven CRC-32 family §1.2 cites. **The function does no string manipulation of its own**: whatever text the caller hands over (with or without `.animx`) is what gets hashed. Whether the extension is kept is therefore a property of each caller, not of this function; the lower-casing is §1.2's cited property of `FUN_00D9E740`, which is not in this index and was not re-read.
- Calls `FUN_00DAB2B0(hash, 0x1964)` (`0x004BF661–0x004BF669`; the constant is 6,500, the record cap) — not dumped; its return value is discarded. **HYPOTHESIS:** a bucket-reduction or range-assert step. The bucket count cannot be read from this dump.
- Loads `0x0340B220` into `EDI` and calls `FUN_004B8740(hash)` (`0x004BF672–0x004BF677`) — not dumped. Note the hashtable object the lookup is anchored on is **`0x0340B220`**, 8 bytes below the "buckets `DAT_0340B228`" the spec names; the spec's four column addresses may be fields of an object starting at `0x0340B220`.
- If the lookup returns `-1` the function **returns `0`** (not `-1`); otherwise it returns the dword at `0x0341E2D8 + 4·slot` — the value column.

`FUN_004BF610` (`0x004BF610–0x004BF642`): returns `-1` when the pointer is 0, or below `0x02EF2178`; otherwise computes `(ptr − 0x02EF2178) / 0x44` (magic-multiply by `0x78787879`, arithmetic shift 5, sign fix-up — i.e. a signed division by 68) and returns it only if it is **strictly less than the live count `DAT_03171BE8`** (signed compare at `0x004BF637`), else `-1`. There is **no upper bound against the 6,500 cap** and **no alignment check** — the live count is the only range guard. **[CONFIRMED — disassembly]** The `0` returned by `FUN_004BF650` on a miss maps to `-1` here, so the chained call's "`-1` on any failure" wording holds.

`FUN_00DA7890` (`0x00DA7890–0x00DA78C0`, 18 call sites listed in the dump header, matching the "≈18" figure):
- A null pointer returns `0xFFFFFFFF`; an empty string returns `0`.
- Each byte is loaded **sign-extended** (`MOVSX` at `0x00DA789C` and `0x00DA78B7`), so **a byte ≥ `0x80` enters the hash as a negative 32-bit value** (`0xFFFFFF80..0xFFFFFFFF`), and the loop stops at a zero byte. Bytes in `'A'..'Z'` (`0x41..0x5A`, tested as unsigned `c − 0x41 < 0x1A`) have `0x20` added; nothing else is folded. Per byte: rotate the accumulator **left** by 6, then XOR with the (folded, sign-extended) byte. Accumulator starts at 0. **[CONFIRMED — disassembly]** The dump's own decompile comment calls it "engine-wide"; that is a stale Ghidra-project annotation, and the 18-caller header line agrees with the spec's narrower count.

**Spec text change (§1.3):**
- In the `FUN_004BF650` bullet, after "hashes the name and looks it up in a generic open-chained string→pointer hashtable", insert: "— the hash is `FUN_00D9E740` with seed 0, computed over the text exactly as the caller supplies it (this function neither strips nor adds `.animx`); a miss returns 0, which `FUN_004BF610` turns into `-1`; the lookup is anchored on an object at `0x0340B220` and goes through `FUN_004B8740` after a `FUN_00DAB2B0(hash, 6500)` step (both untraced; bucket count OPEN) **[CONFIRMED — disassembly 2026-10-01 for the hash, seed, miss value and index derivation]**".

## §4 `anim_groups.xtbl` — key vs pointer storage, parent-slot value, name-array location

**Verdict: CORRECTED on the central claim. The group names are compiled into the executable; the file's `Name` is only *looked up* in that list, never hashed and never stored. `Parent` is CONFIRMED as a pointer to the parent's record. `FUN_004CCE70`'s direction is reversed.**

**Evidence:** `func1/func_0x004cccc0.txt` (body `0x004CCCC0–0x004CCE6B`, sole caller `FUN_004B1900` at `0x004B1A43`), `func1/func_0x004cce70.txt`, `glob/xref_0x03519834.txt`, and the `FUN_005D25F0` stores read under §1.4.

What `FUN_004CCCC0` does, in order:
- Zeroes the whole parent-link array `DAT_03171C24` over `DAT_03171C1C × 12` bytes (`0x004CCCC1–0x004CCCDB`). Then, for each of the `DAT_03171C1C` entries: if the dword at entry `+0x04` is zero (always true after that zeroing), it allocates through `DAT_03171BF8`'s allocator a buffer of `DAT_03171C08` bytes (the merged State/Action count, §5) and stores it at entry `+0x04`, and a buffer of `2 × DAT_03171C08` bytes stored at entry `+0x08`; then it zero-fills both buffers (`0x004CCD00–0x004CCD7E`). So **the second and third dwords of the 12-byte stride are written by this reader** — they are per-group arrays with one byte, respectively one 16-bit word, per State/Action registry entry.
- Opens the document at `0x03518C34` = `DAT_03518830 + 0x404` (slot 4) with arguments `(name, 0, 1)` (`0x004CCD80–0x004CCD89`) and iterates `Anim_Group` by first-child / next-sibling.
- Reads `Name` **as text** via `FUN_00DABA10` (`0x004CCDB6`) — **no hash is computed anywhere in this function** — and finds its index by a `_stricmp` scan over `DAT_03171C1C` entries of the pointer array that **`DAT_03519838` points to** (`0x004CCDD0–0x004CCDEE`: load the dword at `0x03519838`, index it by 4). If no entry matches, the scan falls off the end with index = count; nothing guards this.
- Reads `Parent` via `FUN_00DABA40` (`0x004CCDF6`; returns 0 when absent). If present: same `_stricmp` scan for the parent's index (again falling off to count if unmatched), then stores **the address of the parent's 12-byte record** (`DAT_03171C24 + 12·j`) into the first dword of this row's record (`DAT_03171C24 + 12·i`) (`0x004CCE2F–0x004CCE41`).
